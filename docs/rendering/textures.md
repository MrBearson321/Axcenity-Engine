# Cooked textures

How texture files get onto the GPU, and how cooking them ahead of time (roadmap L2, first part) makes that a file read and a quarter-size upload.

## Without a cooked copy

A texture file (PNG, JPEG, TGA or BMP: a SurfaceAppearance's map, a texture set's, or one a model uses) is decoded to RGBA8 by `assets` on a worker thread (`docs/project/assets.md`). The first frame that draws it then makes its mipmaps on the CPU, a 2×2 box average down to 1×1 (`render/src/renderer/gpu.rs`, `mip_levels`), and uploads every level: 4 bytes a pixel plus a third for the mips, about 85 MB for a 4096² map. A project with many 4K maps spent seconds of its first frame doing that (2.7 to 3 s of Render for Abandoned Farmhouse, `docs/benchmarks.md`).

## Cooking

`axcenity-cook` (editor only) cooks a texture file: decodes it, makes the same box-filtered levels down to 1×1, and BC7-encodes each one with Intel's ISPC compressor (`intel_tex_2`, "very fast" settings, opaque or alpha by whether any pixel is see-through). Levels smaller than a 4×4 block are padded by repeating their edge. The result is written to `.axcenity/imported/textures/<file name>-<hash of its project path>.axtex`. Like the rest of `.axcenity/`, it's this computer's: it isn't exported, backed up or put in version history, and deleting the folder only means cooking again.

- **Built games.** File > Build Game first cooks any texture the background thread hasn't reached (blocking, with a line in Output for how many), then packs each texture's current cooked copy into `game.axgame` at the same place (`project::pack_game`). Unpacking gives every file a new modified time, so the player matches a copy to its texture by the texture's bytes (reading and hashing the file, much less than its decode: about 650 ms for a 4K JPEG here). The source files ship too: UI images and anything on the CPU still read their pixels.
- **When.** The editor cooks every image under `assets/` that has no current cooked copy on a thread of its own each time a project opens, with half the machine's cores, stopping between textures if another project opens (`editor/src/cooking.rs`). `axcenity-editor --cook <project folder>` does the same from the command line, printing each texture, and exits with 1 if any failed (for benchmarks and scripts). A texture is cooked once; editing the file makes its copy out of date, and the next open cooks it again. After cooking, it deletes every copy in `.axcenity/imported/` (cooked textures, cached simpler meshes, cooked models) whose source file is no longer in the project, and half-written ones over an hour old (`remove_orphaned_copies`, `assets/src/orphaned.rs`): each copy is named after its source (`cache_stem`, the file name and a hash of its path), so a deleted, renamed or moved file's copies are found by name.
- **What isn't cooked.** A texture whose width or height isn't a multiple of 4 (BC7 textures start with whole blocks) stays RGBA, and so do generated textures (built-in surfaces, terrain weights, UI images drawn at their full size).
- **While the project is open.** The cooking thread then waits. Whenever the editor's file watcher reports a file that takes an asset ID (a texture, model, font, sky or sound under `assets/`) as imported, added, edited or deleted, `asset_file_changed` asks it for another pass (`Cooker::cook_again`), so a new or edited texture is cooked (and given its ID) within moments rather than at the next open. Changes that arrive while a pass runs make one more pass.
- **Images inside a model.** A `.glb`, `.gltf` with `data:` images or `.fbx` dropped into `assets/` by hand keeps its maps inside it. After the texture files, each pass cooks those in place (`axcenity_cook::cook_embedded`): every embedded image that importing didn't copy out to `<model folder>/textures/` is cooked, with the same format choice (BC5 for a normal map by its name, BC7 otherwise), to `.axcenity/imported/textures/embedded-<hash of the image's bytes>.axtex` (`embedded_cooked_path`). Packs often embed one texture in many models (Abandoned Farmhouse's 29 `.glb` files embed 144 maps, 21 different), so the copy is named by the bytes alone and made once for the whole project, in the format the first model to need it chose. Its stamp is the image's length and hash, so it's used only for the same bytes. Each model gets a note beside it (`<model's cache_stem>-embedded.done`: the model's stamp and the hashes of the copies it uses). The note keeps those copies: the pass ends by deleting copies no note lists, along with the notes of models that are gone (`remove_orphaned_copies`). Once every image of a model is cooked, the note also lets later passes skip it until it changes. Built games pack each model's copies and note (`embedded_cooked_files`), each shared copy once.
- **The file** (`assets/src/cooked.rs`): `AXTEX`, a format version, the source's length, modified time and a 64-bit hash of its bytes, then the format (BC7), size, whether it has alpha, the average of about 4,096 of its pixels, each level's length, and the levels, largest first. A cut or mismatched file is ignored.

## Loading a cooked texture

`Assets::texture` (and a model's textures, by the project path of their file) uses the cooked copy when it's current: the source file has the length it recorded and the same modified time, or, if only the time differs (a copied project), the same bytes. A built game's files get their modified times back when it unpacks (`.axgame` version 2, roadmap M9), so its cooked copies pass on the length and time without hashing their sources. A texture embedded in a model is matched by its embedded bytes against the file importing copied it out to, or, when there is none, against its copy cooked in place (`cooked_in_model`). While such an image is in use, every model that asks for the same copy gets the same `Image` (`shared_cooked`), so it's read and uploaded once. A cooked model (`.axmodel`) records such an image as `ImageOrigin::InModel` with its hash, and loading it reads the cooked copy without opening the model's images; the image's pixels, if the CPU asks, are read again from the model (`PixelSource::InModel`). Anything else decodes the source as before, so a stale copy is never drawn.

A cooked `Image` holds its BC7 levels and decodes its source file only if something on the CPU asks for its pixels (`Image::rgba`: the Model Studio, thumbnails, color grading strips). Loading a model reads `Image::has_alpha` and `Image::sampled_average` instead, which a cooked image answers from what was recorded at cooking, so loading never decodes it.

## Drawing

`TextureSource::bc7_levels` hands the renderer the levels. A surface texture with them goes up as `Bc7RgbaUnorm` (read through a `Bc7RgbaUnormSrgb` view for colors, as RGBA8 is), with no mipmaps to make and a quarter of the bytes, when the device has `TEXTURE_COMPRESSION_BC`. The player's and the editor's devices ask for it whenever the GPU has it (every desktop GPU, and lavapipe). Otherwise, for UI images and terrain weights (drawn at full size from their pixels), and for levels that don't match the size, the renderer takes `rgba()` and the old path.

**Normal maps** are cooked as BC5 instead: two channels, red and green, in the same 16 bytes a block, each kept with twice BC7's care, which keeps a normal map's fine detail from blocking. The cook picks BC5 for a file whose name says it's a normal map (`Rock_Normal.png`, `T_Bench_N.png`: `axcenity_cook::format_for`, from `texture_roles`), and cooks again a normal map whose current copy is still BC7 (`cooked_format`). `scene` hands a BC5-cooked image to the renderer as BC5 (`TextureSource::bc5_levels`, `Bc5RgUnorm`) only where it's a material's normal map, under a key of its own (`NormalTexture`); used anywhere else, the same image is decoded to RGBA, so a misnamed color map still draws right. A BC5 normal map sets `MapsUniform::specular`'s y, and the shader works out blue (the normal's Z) from red and green as `sqrt(1 - x² - y²)`, also when a GPU without BC compression draws it from its pixels.

The texture quality and the GPU's largest size skip the largest levels as they do for RGBA, but the largest level kept must still be whole 4×4 blocks; the texture budget (`texture_budget.rs`) shrinks a BC7 texture down to its 4×4 level at most, copying whole blocks (`Texels::max_dropped`, `Texels::stored_size`). `GpuTexture::texels` says which a texture is; `RenderStats` counts BC7 textures at their real size (16 bytes a block).
