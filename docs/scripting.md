# Scripting (Lua and blocks)

Read before working in the `script` or `blocks` crates, or adding anything to the Lua API.

## Language

- **Lua 5.4** via `mlua` (vendored). Not Luau, not LuaJIT.
- Types for tooling come from a generated **Lua Language Server definitions file** (`---@class`, `---@param` annotations), checked in at `definitions/axcenity.lua`. The generator is `crates/script/src/definitions.rs`: classes, properties and enums come from `core`, while functions, globals and value types are described there by hand. Every public API addition must update it, then run `cargo run -p axcenity-script --bin lua-definitions`. Tests fail (so CI fails) if a property or event has no description, if a global or library function is missing from the descriptions, or if the checked-in file is out of date.
- **In a project** (built in Phase 16, chosen by the developer): the editor's **File > Set Up VS Code Autocomplete** writes `.axcenity/axcenity.lua` (the definitions), `.luarc.json` (Lua 5.4, `.axcenity` as a library, `io`/`debug`/`package` turned off) and `.vscode/extensions.json` (suggests the `sumneko.lua` extension) into the project. The last two are only written if missing, since they may hold the creator's settings. Opening a project in the editor rewrites `.axcenity/axcenity.lua` when it's out of date (`crates/editor/src/autocomplete.rs`). Checked with the real Lua Language Server (`lua-language-server --check`): every example has no warnings, and mistakes such as `part.Size = 5`, `task.wiat()` and `io.write` are flagged.
- **Children by name** are typed as the union of every class (`Part|Model|Folder|...`), not plain `Instance`: with `Instance`, `workspace.Pad.Color = ...` was flagged as a field Instance doesn't have. For the same reason `require` takes an `Instance`.

## API style: Roblox-familiar, not Roblox-compatible

- Reuse familiar names and patterns: `Instance.new("Part")`, `part.Parent = workspace`, `part.Touched:Connect(fn)`, `Vector3.new`, `task.wait` / `task.spawn` / `task.delay`.
- Classes are PascalCase, properties are PascalCase, methods are called with `:`, events are `RBXScriptSignal`-like objects with `:Connect` (but don't name anything with `RBX`).
- Clean up Roblox quirks when it helps beginners. Don't chase full compatibility.
- Never use Roblox's name, logos or assets.

## API so far (Phase 33)

- Globals: `game`, `workspace`, `script` (the running Script, LocalScript or ModuleScript), `print`, `require(module)` (see Modules), `Instance.new(className)`, `Vector3.new(x, y, z)`, `Color3.new(r, g, b)`, `Color3.fromRGB(r, g, b)`, `UDim2.new(xScale, xOffset, yScale, yOffset)`, `UDim2.fromScale(x, y)`, `UDim2.fromOffset(x, y)`, `Enum` and `task` (see Execution model).
- `game:GetService(name)` returns a service by class name (`Workspace`, `Players`, `ReplicatedStorage`, `ServerScriptService`, `StarterPlayer`), or `UserInputService`; a wrong name lists the choices. `Instance.new("Player")` is an error: Players are made when someone joins.
- Instances: `Name`, `ClassName` (read-only), `Parent` (an Instance or `nil`), every property in `core`'s class table, and `:FindFirstChild(name, recursive?)`.
- **Children by name** (decided in Phase 4): `workspace.Block` returns the first child named `Block`. Methods and properties win over children with the same name. A name that's none of these errors with `X is not a valid member of Workspace "Workspace"`.
- **Enums** (decided in Phase 4): `Enum.Material.Neon`, `Enum.PartType.Ball` and (Phase 14) `Enum.KeyCode.W`. Enum items are `LuaEnumItem { enum_type, name }` in `types.rs`; `KeyCode` isn't a property type, so it isn't a `Value`. Enum properties also accept the item's name as a string (`part.Material = "Neon"`); a wrong name errors and lists the choices. Reading always gives an enum item, which prints as `Enum.Material.Neon` and has `.Name`.
- `Vector3`: `.X .Y .Z .Magnitude .Unit`, `+ -`, `*` and `/` by a number or another Vector3, unary `-`, `==`. Prints as `1, 2, 3`.
- `Color3`: `.R .G .B`, `==`. `Color3.new` rejects channels outside 0 to 1 with a hint to use `fromRGB`, matching the world file's check (Roblox allows them silently).
- **UI Instances** (Phase 22): `ScreenGui` under `Workspace` contains `Frame` and `TextLabel` instances. `Position` and `Size` are `UDim2` values; each `.X` and `.Y` exposes `.Scale` and `.Offset`. The player and editor Play viewport recompute layout after scripts each frame, including after a resize.
- Numbers are Lua 5.4 numbers, so `print(part.Position.Y)` shows `5.0`.
- **Events** (decided in Phase 7): `part.Touched` is a Signal. `signal:Connect(fn)` returns a Connection with `:Disconnect()` (calling it twice is harmless) and `.Connected`. `Touched` handlers get the other part. Event names come from `ClassName::events()` in `core`, plus `INSTANCE_EVENTS`, which every class has; `instance.Key` checks them after properties and before children, and assigning to one explains how to connect instead. Connections to a destroyed Instance are dropped at the next step. `:Once` and `:Wait` aren't built yet.
- **Change events** (Phase 16): every Instance has `Changed` (handler gets the property's name, as a string), `ChildAdded` and `ChildRemoved` (handler gets the child), and `instance:GetPropertyChangedSignal("Position")` (handler gets nothing; a wrong name lists the choices). `Name` and `Parent` count as properties. They fire whoever made the change: a script, physics (a falling part's `Position` and `Orientation`, every physics step it moves) or the editor during Play. Setting a property to the value it already has isn't a change. Unlike Roblox, physics movement does fire them (the plan asks for it). See Execution model for when they run.
- **`RunService`** (Phase 16, chosen by the developer): `game:GetService("RunService")` (or `game.RunService`) has `Heartbeat`, which fires once a frame after physics and `Touched`, on both sides, with the frame's length in seconds. Not an Instance (like `UserInputService`), so it isn't in the Explorer. No `RenderStepped` or `Stepped` yet.
- **MeshPart** (Phase 17): `Instance.new("MeshPart")` works, with `Anchored`, `Position`, `Orientation`, `Size` and `MeshId` (a model's path in the project, such as `"assets/models/pyramid.gltf"`; `.gltf`, `.glb` and `.fbx` files work, and `#` after the file picks objects in it: `"assets/models/props.fbx#Bench"`), and fires `Touched` like a Part. Setting `MeshId` loads that model the first time it's drawn; a path outside the project is refused, and a model that can't be loaded is reported once and drawn as a grey box. It has no `Color` or `Material`: it uses the file's materials.
- **SurfaceAppearance** (Phase 21): `Instance.new("SurfaceAppearance")` inside a MeshPart replaces the texture maps of the model's material named by its `MaterialName`, with the properties in `docs/rendering.md` (maps are texture paths in the project, such as `"assets/textures/wood.png"`). `Enum.TextureChannel` (`Red`, `Green`, `Blue`, `Alpha`) is for its `…Channel` properties, which also take item names (`look.RoughnessChannel = "Green"`).
- **Sound** (Phase 29, extended after it): put a `Sound` Instance in the Workspace (or a part), set `SoundId` to a project-relative audio file (such as `"assets/audio/chime.wav"`), then call `sound:Play()` (from the start) or `sound:Stop()`. `sound:Pause()` and `sound:Resume()` carry on from where it was. `Playing` is true while it plays: setting it to false pauses and true resumes, and a Sound saved with `Playing` true starts when the game starts, with no script. `Volume` is a non-negative linear amplitude multiplier (1 is original level, 0 is silent), `PlaybackSpeed` scales speed and pitch (1 is normal, from 0.01 to 20), and `Looped` repeats the entire file; changes to all three apply to a sound that's already playing. `Ended` fires (on both sides) when a sound that isn't looped plays to its end, after `Playing` goes false; `Stop` doesn't fire it. Supported files are WAV, FLAC, Ogg Vorbis and MP3. Playback runs in the host, not Lua (see `GameAudio` in `audio`); stopping editor Play drops its audio and stops all playback.
- **ParticleEmitter** (Phase 37): put one in a part (`Instance.new("ParticleEmitter")`, parent a Part or MeshPart) and it gives off `Rate` particles a second while `Enabled`, from random points inside the part, out along `Direction` (relative to the part) at `Speed` within a cone `SpreadAngle` degrees wide, living `Lifetime` seconds (±20%). `Acceleration` (world studs/s²) and `Drag` move them, and with `WindAffectsDrag` on, Drag slows them toward `workspace.GlobalWind` so the wind carries them; `Size`/`SizeEnd`, `Color`/`ColorEnd` and `Transparency`/`TransparencyEnd` blend from birth to death; `Rotation` and `RotSpeed` turn them; `LightEmission` (0 paints, 1 adds light) and `Brightness` set how they glow. `ParticleType` (`Enum.ParticleType`: `Circle`, `Spark`, `Smoke`, `Fire`, `Star`, `Magic`; also takes the name) picks a built-in picture, and `Texture` (a project image such as `"assets/particles/spark_01.png"`) replaces it. `emitter:Emit(count)` gives off a burst now (up to 1000), even while not Enabled. Particles are simulated by the host (`scene::Particles`), not Lua: they aren't Instances, aren't saved, and scripts can't read them.
- **Animator** (Phase 38): put one in a MeshPart whose model is animated (an FBX with a skeleton, or animated objects) and set `Controller` to an animator controller file in the project (`"assets/animations/hero.controller.json"`; importing an animated FBX makes one). During Play it starts in the controller's default state and plays it on the model. `animator:Play("Walk", blend?)` switches to a state from its start, blending from the pose now over `blend` seconds (0.25 if left out, 0 snaps; it must be a number 0 or more, and the state a string; an unknown state is reported in Output and changes nothing). `animator.CurrentState` is the state's name (read-only: setting it explains to use `Play`; empty for an Animator the host hasn't run, such as one just made with `Instance.new`). `Enabled` false holds the pose; `Speed` scales every state (0 pauses). `animator.StateChanged` fires with the new state's name and the old one's, after the frame's Heartbeat. `AnimationEvent` is declared for clip events (Phase 39). Live state (parameters, `CurrentState`, the requested state) is `core::AnimatorState`, kept in the `World` beside the Instances rather than as properties, so it's never saved; hosts prime their Animators before scripts start, so `CurrentState` is set from the first line of a script.
- Parts (Phase 35) also have `Transparency` (0–1), `CanCollide` (off: passed through, still fires `Touched`), `EmissiveColor` and `Emission` (a glow of any color). `WindAffected` (Part and MeshPart, default false) lets `workspace.GlobalWind` (a Vector3 in studs/s, default zero, saved in the world file only when set) push an unanchored part.
- `Part.Anchored` (default `false`): unanchored parts fall under physics. Setting `Position` or `Orientation` on one teleports it and stops it; physics writes both back as the part moves. See Physics in `docs/architecture.md`.

## Errors

- Every message starts with `path:line:`, using the path from the project folder (`scripts/build.server.lua:3: Part.Size must be a Vector3, not a number`). Engine errors take the line from the Lua call stack.
- Scripts see the same plain strings through `pcall` and `xpcall`, which are thin Lua wrappers around the real ones, so pausing inside a `pcall` will still work.
- Output is a list of `OutputLine`s (`Print` or `Error`) that the host takes with `take_output()`: the player prints them, and the editor's Output panel shows them during Play (`Print` as info, `Error` in red).

## Sandbox

Each script gets its own restricted environment. Remove or replace `io`, `os` (keep only safe time functions), `debug`, `load`, `loadfile`, `dofile`, `require` (replaced by an engine module loader), and `collectgarbage` beyond safe options. Treat all script code as untrusted.

- Since Phase 4 the environment is built from an **allowlist** (`crates/script/src/sandbox.rs`): the safe base functions, per-script copies of `coroutine`, `math`, `string` (without `dump`), `table` and `utf8`, and `os.clock/date/difftime/time`. `_G` is the script's own environment, and only source text loads, never bytecode.

### Hardened in Phase 15

- **String metatable**: every string shares one metatable, whose `__index` was the real `string` table. It's now a hidden copy without `dump`, and `getmetatable("")` returns `"The metatable is locked"` (as in Roblox). A script's `string.upper = ...` only changes its own copy.
- **`collectgarbage`** only takes `"count"` (memory in use, in KB). Anything else errors: the engine runs the collector for everyone.
- **`setmetatable`** refuses a metatable with `__gc`: Lua runs finalizers with hooks off (so the watchdog couldn't stop one) and at unpredictable moments.
- **`coroutine.resume/wrap/status/close`** are engine versions (`watchdog.rs`): errors come back as plain `path:line:` strings like `pcall`'s, `wrap` doesn't add a second location, and a coroutine the watchdog stopped looks dead and can't be resumed or closed.
- Engine objects' metatables (Instances, Vector3, ...) are locked by mlua: `getmetatable(workspace)` is `false`; `sandbox_tests.rs` checks this and every other escape attempt (missing `io`/`debug`/`load`/`package`/..., bytecode, `os` beyond the clock, cross-script and cross-side globals, `require` of paths and libraries).
- **Not covered** (out of scope for v1, noted for later): memory limits (a script can allocate until the process runs out), and C functions that run long by themselves (a huge `string.rep`, a pathological pattern in `string.find`): the watchdog only sees Lua instructions.

## Modules (decided in Phase 15, chosen by the developer)

- Roblox's way: a `scripts/**/*.module.lua` file becomes a **ModuleScript** in **ReplicatedStorage** (named after the file), and `require(game.ReplicatedStorage.Utils)` runs it. Only ModuleScripts can be required: a string (`require("utils")`), a path, a library name or another Instance is an error that explains what to pass. So nothing outside the project can be loaded.
- A module runs **once per side**, the first time a script there requires it, in its own environment (`script` is the ModuleScript); every later `require` on that side gets the same value. The server and the client each run their own copy.
- It must return exactly one value (usually a table), or `require` errors. An error while loading reaches the requiring script (with the module's path and line), and the module is tried again at the next `require`. A syntax error names both files: `scripts/main.server.lua:1: scripts/m.module.lua:3: ...`.
- The module's code runs in the requiring coroutine, so it may `task.wait`; a second script requiring it meanwhile waits until it's loaded. Modules that require each other (in the same coroutine) error instead of hanging.
- The host passes ModuleScripts to `ScriptRuntime::start_script` like any script; they only register their code (`modules.rs`), so pass them first (`project::script_order` sorts them first). A ModuleScript made with `Instance.new` has no code and can't be required.

## Execution model

- Every script body and every event handler runs as a **coroutine**.
- The **scheduler** (`crates/script/src/scheduler.rs`) owns all paused coroutines. `task.wait(t)` yields, and the scheduler resumes it once `t` has passed (frame order step 2, `ScriptRuntime::step`).
- **The clock is game time**, the sum of the frame times the host passes to `step`, not the computer's clock. The player caps a frame at 0.1 s, so after a stall waiting scripts don't all fire at once. Tests drive the clock exactly.
- `task` (decided in Phase 5, matching Roblox):
  - `task.wait(seconds?)` returns the seconds that really passed. Left out, 0, negative or NaN means "until the next step", so `while true do task.wait() end` runs once a frame. A task is never resumed in the step that scheduled it.
  - `task.spawn(fn, ...)` runs `fn` **right away** until it finishes or waits, then the caller continues. Returns the coroutine.
  - `task.delay(seconds, fn, ...)` starts `fn` once `seconds` have passed (at the next step at the earliest). Returns the coroutine.
  - Both take functions only, not coroutines. `task.cancel` and `task.defer` don't exist yet.
- **Resume order**: earliest due first; ties in the order they were scheduled. A task within 1 µs of due counts as due, so float rounding in summed frame times never costs a whole frame. A `task.wait(1)` loop still drifts by up to a frame per wait when frames are uneven (as in Roblox); use the returned time for exact timing.
- `task.wait` inside a script's own coroutine (`coroutine.wrap`) pauses just that coroutine and returns control to whoever resumed it; the scheduler resumes it later. It also works inside `pcall`.
- No legacy `wait`, `spawn` or `delay` globals (decided in Phase 5): only `task.*`.
- Event handlers fired in the same frame run in a deterministic order: touches in the order physics found them (sorted pairs per step), then for each pair the first part's handlers and then the other's, each in the order they were connected. Handlers run **immediately** when the event fires (step 4), each as a new coroutine, so a handler that calls `task.wait` pauses only itself and the scheduler resumes it later. A handler disconnected by an earlier handler in the same firing doesn't run. An error in a handler is reported and the handler stays connected, as in Roblox.
- **Watchdog** (built in Phase 15, `watchdog.rs`): Lua calls a hook every 1000 instructions in every coroutine. A coroutine may run **3 seconds** without pausing (`WATCHDOG_LIMIT`, chosen by the developer; `ScriptRuntime::set_watchdog_limit` changes it, for tests). The budget starts when the scheduler resumes it (or the host starts a script), so code that pauses now and then is never stopped. When it's used up, the hook **yields** the coroutine and nothing ever resumes it; the scheduler reports `path:line: this script ran for 3 seconds without pausing, so it was stopped. ...`. A yield can't be caught by `pcall` and runs no handlers or `__close`, so a script can't keep itself alive. Code that can't yield (Lua inside a C function, such as a `table.sort` comparator) gets an error instead, which the engine's `pcall`/`xpcall` pass on rather than catch (yielding is preferred because Lua leaves hooks off in a coroutine that an error from a hook ended). A coroutine that resumed the stopped one with `coroutine.resume` shares the used-up budget, so it's stopped too if it keeps running; one that `task.spawn`ed it gets a fresh budget. Other scripts carry on as normal. The game and the editor freeze for up to 3 seconds, then carry on.
- **Change events are deferred** (decided in Phase 16): the World keeps a numbered log of every change (`World::record_changes`, `take_changes`; `core::Change`), and `ScriptRuntime::fire_changes` fires them, in order, Scripts then LocalScripts. Every runtime entry point (`start_script`, `input`, `step`, `fire_touched`, `heartbeat`) calls it before and after running scripts, so a script's changes fire right after it pauses or finishes (not in the middle of it, like Roblox's deferred events), and physics' and the editor's changes fire at the next call. A handler only hears about changes made after it was connected (each handler remembers `World::next_change_number`), so `part.Name = "A"; part.Changed:Connect(f)` doesn't run `f`. Handlers' own changes fire in further rounds, at most 10 (`MAX_CHANGE_ROUNDS`) per call; past that the rest wait for the next call and Output says once that a handler keeps changing what it listens to, so a loop never freezes the game. Changes to an Instance that's gone by then are skipped.
- Errors in one script never stop other scripts. Report them to Output with the script path and line. An error in a `task.spawn` or `task.delay` function is reported the same way and doesn't stop the script that started it.

## Server and client

- `Script` runs on the server side. `LocalScript` runs on the client side (input, camera, UI).
- `RemoteEvent` sends messages server ↔ client. v1 uses an **in-memory loopback transport**, so keep the transport behind a trait so a real network can replace it.
- Client-only APIs (input, camera, local UI) error in a `Script` with a helpful message, and vice versa.
- File naming: `*.server.lua`, `*.client.lua` and (Phase 15) `*.module.lua`, which both sides can require.

### Decided in Phase 14

- **Two interpreters**: `ScriptRuntime` owns a server `Context` and a client `Context` (`crates/script/src/context.rs`), each its own `mlua::Lua`. So the sides can't share globals, library tables or even the string metatable. Both use the one `World` (lent to whichever side runs). One client: the player on this device.
- **Where things live** (chosen by the developer, Roblox's layout): LocalScripts in `StarterPlayer.StarterPlayerScripts` (they run from there; no copying into a `PlayerScripts`), RemoteEvents usually in `ReplicatedStorage`, and a `Players` service. `StarterPlayerScripts` counts as a service (can't be moved or deleted).
- **Start order**: Scripts first, then LocalScripts, each by path. The player **joins** (a `Player` named `Player` goes into `Players` and becomes `LocalPlayer`) just before the first LocalScript starts, or at the first frame if there are none.
- **RemoteEvent API** (chosen by the developer, Roblox's shapes): `remote:FireServer(...)` (client), `remote:FireClient(player, ...)` and `remote:FireAllClients(...)` (server); `remote.OnServerEvent` handlers get `(player, ...)`, `remote.OnClientEvent` handlers get `(...)`. Calling with `.` instead of `:` explains to use a colon.
- **What can be sent**: nil, booleans, numbers (whole numbers stay whole), strings, tables (nested, any keys), Vector3, Color3, enum items and Instances. A function, coroutine or other engine object is an error (Roblox silently sends nil; an error teaches more), and so is a table that contains itself. Arguments become `RemoteValue`s (plain data), so the receiver gets copies. An Instance arrives as the same Instance (one World), or nil if it was destroyed meanwhile.
- **Delivery**: messages go into the sender's outbox, then the `Transport` (`remote.rs`: `send`, `receive(side)`; `Loopback` is two queues). In frame step 2 the server takes its messages and fires `OnServerEvent`, runs its due tasks, then the client does the same. So a key press in step 1 reaches the server in the same frame, and a server reply reaches the client in that frame too; messages sent later arrive next frame. A message with no handler connected is dropped (Roblox queues it).
- **Input** (`client.rs`): `game:GetService("UserInputService")` (also `game.UserInputService`) with `InputBegan` / `InputEnded` (handler gets an `InputObject` with `.KeyCode`, and `gameProcessedEvent`, always false until UI exists) and `:IsKeyDown(Enum.KeyCode.X)`. Keyboard only. Keys are named by their place on a US keyboard, with Roblox's names (`Up`, `Return`, `LeftShift`, `Zero`); the host sends `KeyEvent`s with `ScriptRuntime::input` in frame step 1. A repeat of a held key isn't a new press.
- **Camera** (chosen by the developer): `workspace.CurrentCamera` with `Position` and `Orientation` (read and set; degrees like a Part, X pitch, Y yaw, Z ignored) and `LookVector` (read). Setting moves the view, and the player can still fly on from there; no `CameraType` yet. The host passes the camera in with `set_camera` each frame and applies `take_camera_move` before drawing.
- **Wrong side**: `sides.rs` lists every side-only API (`SIDE_ONLY_APIS`: UserInputService, CurrentCamera, LocalPlayer, FireServer, OnClientEvent on the client; FireClient, FireAllClients, OnServerEvent on the server) with a message such as "UserInputService only works in a LocalScript, because input comes from the player's keyboard. This is a Script, which runs on the server: read the input in a LocalScript, and send it to the server with a RemoteEvent's FireServer." Reading one on the wrong side raises it as `path:line:` error. The editor uses the same list for its warning badges.

## Blocks to Lua

- Block scripts are JSON files ending in `.server.blocks.json` or `.client.blocks.json` (format in `docs/project-and-export.md`). The editor shows them Scratch-style: a palette by category on the left, and a canvas of stacks, each under an event block ("hat"), or loose (an unattached stack, which doesn't run). Blocks snap together, C-shaped blocks hold stacks, and reporters (round for values, pointed for true or false) drop into slots; a pointed reporter fits any slot, a round one only round slots. Client-only blocks (keys, button clicks) are only offered in client block scripts, and the canvas shows a Server or Client badge.
- There is no separate runtime: **blocks always translate to Lua**, using the same `ScriptRuntime` and API as handwritten scripts. Objects are named by their path under the Workspace (`Pad.Chime` is `workspace.Pad.Chime`, or `workspace["Red Ball"]` for names that aren't Lua names).
- Variables belong to the whole block script, as in Scratch: each is declared once at the top as `local name = 0`. Loops that may run long (forever, repeat until, wait until) wait a frame each time round (`task.wait()`), so the game keeps running.
- "View as Lua" shows the generated Lua beside the canvas, readable and with no markers in it. `Translation::block_lines` maps each block to the line its code starts on, so a runtime error's line highlights the block it came from (in red).
- One-way only. Don't build Lua-to-blocks conversion.
- Every block must correspond to a real Lua API. Don't add block-only features. The blocks and what they become:

| Category | Block | Lua |
|---|---|---|
| Events | when game starts | `task.spawn(function() … end)` |
| | when *part* is touched | `part.Touched:Connect(function(otherPart) … end)` |
| | when *key* key pressed (client) | `UserInputService.InputBegan:Connect(function(input) if input.KeyCode == Enum.KeyCode.Key then … end end)` |
| | when *button* is clicked (client) | `button.Activated:Connect(function() … end)` |
| | every frame | `RunService.Heartbeat:Connect(function(deltaTime) … end)` |
| | when *sound* ends | `sound.Ended:Connect(function() … end)` |
| Control | wait, wait until | `task.wait(n)`; `while not (c) do task.wait() end` |
| | repeat *n* times, forever, repeat until | `for _ = 1, n do … end`; `while true do … task.wait() end`; `while not (c) do … task.wait() end` |
| | if, if/else, stop this script | `if c then … else … end`; `do return end` |
| Motion | move to, move by, turn to, turn by, set anchored | `Position =`, `Position = Position + v`, `Orientation =`, `Orientation = Orientation + v`, `Anchored =` |
| Looks | set color, set text, show, hide, show page, set *property* | `Color =`, `Text = tostring(v)`, `Visible = true/false`, `layout.CurrentPage = page`, `object.Property = v` |
| Sound | play, stop, pause, resume, set volume | `:Play()`, `:Stop()`, `:Pause()`, `:Resume()`, `Volume =` |
| Variables | set, change by, *variable* | `name = v`, `name = name + n`, `name` |
| More | print, destroy | `print(v)`, `object:Destroy()` |
| Operators | + − × ÷ mod ^, pick random, join, round/abs/floor/ceiling/sqrt, < = > ≤ ≥ ≠, and, or, not | Lua operators; `math.random(math.floor(a), math.floor(b))`; `tostring(a) .. tostring(b)`; `math.floor(x + 0.5)`, `math.abs` …; `not` |
| Sensing | touching part, key pressed? (client), *property* of *object* | `otherPart` (inside "when touched" only), `UserInputService:IsKeyDown(Enum.KeyCode.Key)`, `object.Property` |
