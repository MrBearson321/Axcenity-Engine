# Execution model

Coroutines, task.wait, the watchdog, and when change events fire.

- Every script body and every event handler runs as a **coroutine**.
- The **scheduler** (`crates/script/src/scheduler.rs`) owns all paused coroutines. `task.wait(t)` yields, and the scheduler resumes it once `t` has passed (frame order step 2, `ScriptRuntime::step`).
- **The clock is game time**, the sum of the frame times the host passes to `step`, not the computer's clock. The player caps a frame at 0.1 s, so after a stall waiting scripts don't all fire at once. Tests drive the clock exactly.
- `task` (decided in Phase 5, matching Roblox):
  - `task.wait(seconds?)` returns the seconds that really passed. Left out, 0, negative or NaN means "until the next step", so `while true do task.wait() end` runs once a frame. A task is never resumed in the step that scheduled it.
  - `task.spawn(fn, ...)` runs `fn` **right away** until it finishes or waits, then the caller continues. Returns the coroutine.
  - `task.delay(seconds, fn, ...)` starts `fn` once `seconds` have passed (at the next step at the earliest). Returns the coroutine.
  - Both take functions only, not coroutines.
  - (Phase 32) `task.defer(fn or thread, ...)` runs it at the **next step** (Roblox runs it later in the same frame), after the current code finishes or pauses. Returns the coroutine.
  - (Phase 32) `task.cancel(thread)` drops it from the scheduler and closes it, so it never starts or resumes; a finished thread is fine, the running one is an error. A cancelled `InvokeServer` caller's answer resumes nothing.
  - (Phase 32) `task.synchronize()` and `task.desynchronize()` do nothing: scripts run on one thread.
- **The waiting queue** (M6) is a binary heap of (due, order), so a step costs nothing for tasks that aren't due and 10,000 waiting coroutines don't cost a scan per frame. `task.cancel` and dropping a script's tasks leave tombstones, skipped when they come up and cleared once they outnumber the tasks, and `has_waiting` counts only the live ones. Handlers are dropped by key when their Instance goes away (`World::take_destroyed` lists what was destroyed; a Tween's when nothing holds it), not by looking at every handler each frame. A handler on something already gone is noted at `Connect` and dropped at the next step.
- **Resume order**: earliest due first; ties in the order they were scheduled. A task within 1 µs of due counts as due, so float rounding in summed frame times never costs a whole frame. A `task.wait(1)` loop still drifts by up to a frame per wait when frames are uneven (as in Roblox); use the returned time for exact timing.
- `task.wait` inside a script's own coroutine (`coroutine.wrap`) pauses just that coroutine and returns control to whoever resumed it; the scheduler resumes it later. It also works inside `pcall`.
- No legacy `wait`, `spawn` or `delay` globals (decided in Phase 5): only `task.*`.
- Event handlers fired in the same frame run in a deterministic order: touches in the order physics found them (sorted pairs per step), then for each pair the first part's handlers and then the other's, each in the order they were connected. Handlers run **immediately** when the event fires (step 4), each in a coroutine of its own, so a handler that calls `task.wait` pauses only itself and the scheduler resumes it later. A coroutine whose handler finished without pausing is reset and reused for a later handler call (`handler_threads.rs`, roadmap M6), except one a script got from `coroutine.running()` (the sandbox's version notes those), one with a task still waiting, or any while the debugger is on; so scripts can't tell it from a new coroutine. A handler disconnected by an earlier handler in the same firing doesn't run. An error in a handler is reported and the handler stays connected, as in Roblox.
- **Watchdog** (built in Phase 15, `watchdog.rs`): Luau calls an interrupt at every function call and loop iteration in every coroutine; every 1000 interrupts it reads the clock. A coroutine may run **3 seconds** without pausing (`WATCHDOG_LIMIT`, chosen by the developer; `ScriptRuntime::set_watchdog_limit` changes it, for tests). The budget starts when the scheduler resumes it (or the host starts a script), so code that pauses now and then is never stopped. When it's used up, the interrupt **yields** the coroutine and nothing ever resumes it; the scheduler reports `path:line: this script ran for 3 seconds without pausing, so it was stopped. ...`. A yield can't be caught by `pcall` and runs no handlers, so a script can't keep itself alive. Code that can't yield (Lua inside a C function, such as a `table.sort` comparator) gets an error at the next interrupt instead, which the engine's `pcall`/`xpcall` pass on rather than catch. When the stopped coroutine is one the script made (`coroutine.resume`), the task running it may run 1000 more interrupts of its own to finish its line, then is stopped too (so `while true do coroutine.resume(...) end` ends); one that `task.spawn`ed it gets a fresh budget. Other scripts carry on as normal. The game and the editor freeze for up to 3 seconds, then carry on.
- **Debugger** (v2 Phase 4, `debugger.rs`; editor only): `ScriptRuntime::enable_debugger` sets Luau's step hook and turns on single-step mode for every coroutine the scheduler resumes (coroutines they create inherit it), so every Luau instruction then calls into Rust, which is why the player never turns it on, and no Lua can. It also compiles scripts at debug level 2, which keeps local names. `set_breakpoints` takes lines by script path. When a line with a breakpoint is about to run in a coroutine the scheduler resumed, the hook reads the call stack's script functions and their locals, then **yields** the coroutine, like the watchdog, and the scheduler **holds** it instead of dropping it: `pause()` reports the path, line and frames. (Locals are read before the yield because afterwards Luau reports the innermost function one instruction early.) While paused, anything the scheduler is asked to resume (due waits, `task.delay`s, event handlers, Console commands) waits in order, and a coroutine that gets control back (one that `task.spawn`ed the paused one) is held at its next instruction. `continue_from_pause` resumes the paused coroutine, then the rest in order; a breakpoint reached on the way pauses again and holds the rest. Luau runs the hook again for the instruction a coroutine yielded at, so the debugger remembers where each one stopped (line and call depth) and doesn't stop it there again until it reaches another line of that function. So a loop written on one line pauses only once. A breakpoint in a coroutine the script made itself (`coroutine.wrap`) or in Lua called from a C function (a `table.sort` comparison) can't pause: the line runs, and Output says so once per breakpoint. The step hook, `lua_singlestep` and `read_frames` are the workspace's only `unsafe` code (decided in v2 Phase 4); the `debug` library is never loaded. Values show as `tostring` does, except tables, which are listed raw (up to 8 entries, nested ones as `{…}`) so inspecting runs no script code (no `__tostring`, `__pairs`). Each script side has its own debugger; `pause()` asks the server side first. Roadmap G6: `resume_from_pause(world, Resume)` continues or steps. A step remembers the paused coroutine with its line and call depth (`lua_stackdepth`), and the hook pauses it at the next line the step reaches (Into: any new line or depth; Over: a new line at that depth or shallower; Out: shallower), only where the coroutine can yield (`lua_isyieldable`), so inside a C function it goes on to the next line where it can. A breakpoint pausing first ends the step, and so does the coroutine finishing. `set_pause_on_error` makes a failed scheduler coroutine pause: the scheduler calls `debugger::failed` before `leave`, and since Luau keeps a failed coroutine's stack, `read_frames` reads it as at a breakpoint (`Pause::error` holds the message; nothing is held for it, so Continue runs the rest). `read_frames` also reads each frame's function (`lua_getinfo` "f") for its upvalues and environment; `evaluate(world, frame, expression)` compiles `return (expression)` with an environment table of those upvalues and locals whose `__index` is the frame's environment, and runs it on its own coroutine under the watchdog. A `nil` local isn't in that table, so it falls through to a global of that name. Breakpoint rules (`set_breakpoint_rules`, `BreakpointRule`): the hook stops at a ruled breakpoint as at any other (so the frame's locals are read), and once it has yielded the scheduler calls `debugger::settle`, which evaluates the condition, counts the hit and writes a logpoint's message; when the breakpoint shouldn't pause, the stop is dropped and `scheduler::resume` resumes the coroutine again in its own loop, so a logpoint in a long loop never nests, and the watchdog's clock isn't restarted between those resumes, so an endless loop with a logpoint is still stopped. Only a stop the breakpoint made (not a step or a pause request) is ruled. `request_pause` sets a flag the hook checks like a breakpoint at any script line where the coroutine can yield; continuing, or a pause on the other side, clears it. `Local::fields` lists a table's entries for the Locals view (`EXPANDED_ENTRIES`).
- **Change events are deferred** (decided in Phase 16): the World keeps a numbered log of every change (`World::record_changes`, `take_changes`; `core::Change`), and `ScriptRuntime::fire_changes` fires them, in order, Scripts then LocalScripts. Every runtime entry point (`start_script`, `input`, `step`, `fire_touched`, `heartbeat`) calls it before and after running scripts, so a script's changes fire right after it pauses or finishes (not in the middle of it, like Roblox's deferred events), and physics' and the editor's changes fire at the next call. A handler only hears about changes made after it was connected (each handler remembers `World::next_change_number`), so `part.Name = "A"; part.Changed:Connect(f)` doesn't run `f`. Handlers' own changes fire in further rounds, at most 10 (`MAX_CHANGE_ROUNDS`) per call; past that the rest wait for the next call and Output says once that a handler keeps changing what it listens to, so a loop never freezes the game. Changes to an Instance that's gone by then are skipped. After the rounds, `fire_changes` also stops scripts whose Instance was destroyed and starts cloned scripts that are now where they run (see `Clone` and `Destroy` in [api-core.md](api-core.md)).
- **Each coroutine belongs to a script** (unified Phase 24): the scheduler knows which script is running (`scheduler::running_script`, set by `resume_as`). A script's body runs as it; a handler belongs to the script that connected it and runs as it; `task.spawn`, `task.delay` and `task.wait` inherit it; held coroutines keep it. So `ScriptRuntime::reload_script` can disconnect one script's handlers and drop its waiting coroutines (`Connections::forget_script`, `Scheduler::forget_script`) and leave the others alone. Each side's `Modules` also remembers which scripts required each module, and which modules required it while loading (`modules::replace`). Console commands belong to no script.
- Errors in one script never stop other scripts. Report them to Output with the script path and line. An error in a `task.spawn` or `task.delay` function is reported the same way and doesn't stop the script that started it.
