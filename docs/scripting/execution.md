# Execution model

Coroutines, task.wait, the watchdog, and when change events fire.

- Every script body and every event handler runs as a **coroutine**.
- The **scheduler** (`crates/script/src/scheduler.rs`) owns all paused coroutines. `task.wait(t)` yields, and the scheduler resumes it once `t` has passed (frame order step 2, `ScriptRuntime::step`).
- **The clock is game time**, the sum of the frame times the host passes to `step`, not the computer's clock. The player caps a frame at 0.1 s, so after a stall waiting scripts don't all fire at once. Tests drive the clock exactly.
- `task` (decided in Phase 5, matching Roblox):
  - `task.wait(seconds?)` returns the seconds that really passed. Left out, 0, negative or NaN means "until the next step", so `while true do task.wait() end` runs once a frame. A task is never resumed in the step that scheduled it.
  - `task.spawn(fn, ...)` runs `fn` **right away** until it finishes or waits, then the caller continues. Returns the coroutine.
  - `task.delay(seconds, fn, ...)` starts `fn` once `seconds` have passed (at the next step at the earliest). Returns the coroutine.
  - Both take functions only, not coroutines. `task.cancel` and `task.defer` don't exist yet.
- **Resume order**: earliest due first; ties in the order they were scheduled. A task within 1 µs of due counts as due, so float rounding in summed frame times never costs a whole frame. A `task.wait(1)` loop still drifts by up to a frame per wait when frames are uneven (as in Roblox); use the returned time for exact timing.
- `task.wait` inside a script's own coroutine (`coroutine.wrap`) pauses just that coroutine and returns control to whoever resumed it; the scheduler resumes it later. It also works inside `pcall`.
- No legacy `wait`, `spawn` or `delay` globals (decided in Phase 5): only `task.*`.
- Event handlers fired in the same frame run in a deterministic order: touches in the order physics found them (sorted pairs per step), then for each pair the first part's handlers and then the other's, each in the order they were connected. Handlers run **immediately** when the event fires (step 4), each as a new coroutine, so a handler that calls `task.wait` pauses only itself and the scheduler resumes it later. A handler disconnected by an earlier handler in the same firing doesn't run. An error in a handler is reported and the handler stays connected, as in Roblox.
- **Watchdog** (built in Phase 15, `watchdog.rs`): Lua calls a hook every 1000 instructions in every coroutine. A coroutine may run **3 seconds** without pausing (`WATCHDOG_LIMIT`, chosen by the developer; `ScriptRuntime::set_watchdog_limit` changes it, for tests). The budget starts when the scheduler resumes it (or the host starts a script), so code that pauses now and then is never stopped. When it's used up, the hook **yields** the coroutine and nothing ever resumes it; the scheduler reports `path:line: this script ran for 3 seconds without pausing, so it was stopped. ...`. A yield can't be caught by `pcall` and runs no handlers or `__close`, so a script can't keep itself alive. Code that can't yield (Lua inside a C function, such as a `table.sort` comparator) gets an error instead, which the engine's `pcall`/`xpcall` pass on rather than catch (yielding is preferred because Lua leaves hooks off in a coroutine that an error from a hook ended). A coroutine that resumed the stopped one with `coroutine.resume` shares the used-up budget, so it's stopped too if it keeps running; one that `task.spawn`ed it gets a fresh budget. Other scripts carry on as normal. The game and the editor freeze for up to 3 seconds, then carry on.
- **Debugger** (v2 Phase 4, `debugger.rs`; editor only): `ScriptRuntime::enable_debugger` adds a line hook beside the watchdog's (every Lua line then calls into Rust, which is why the player never turns it on, and no Lua can). `set_breakpoints` takes lines by script path. When a line with a breakpoint is about to run in a coroutine the scheduler resumed, the hook **yields** it, like the watchdog, and the scheduler **holds** it instead of dropping it: `pause()` reports the path, line and the call stack's script functions with their locals. While paused, anything the scheduler is asked to resume (due waits, `task.delay`s, event handlers, Console commands) waits in order, and a coroutine that gets control back (one that `task.spawn`ed the paused one) is held at its next line. `continue_from_pause` resumes the paused coroutine exactly where it stopped (Lua doesn't run that line's hook again), then the rest in order; a breakpoint reached on the way pauses again and holds the rest. A breakpoint in a coroutine the script made itself (`coroutine.wrap`) or in Lua called from a C function (a `table.sort` comparison) can't pause: the line runs, and Output says so once per breakpoint. Locals are read with Lua's C API after the yield (`read_frames`, the workspace's one `unsafe` block, decided in v2 Phase 4); the `debug` library is never loaded. Values show as `tostring` does, except tables, which are listed raw (up to 8 entries, nested ones as `{…}`) so inspecting runs no script code (no `__tostring`, `__pairs`). Each script side has its own debugger; `pause()` asks the server side first.
- **Change events are deferred** (decided in Phase 16): the World keeps a numbered log of every change (`World::record_changes`, `take_changes`; `core::Change`), and `ScriptRuntime::fire_changes` fires them, in order, Scripts then LocalScripts. Every runtime entry point (`start_script`, `input`, `step`, `fire_touched`, `heartbeat`) calls it before and after running scripts, so a script's changes fire right after it pauses or finishes (not in the middle of it, like Roblox's deferred events), and physics' and the editor's changes fire at the next call. A handler only hears about changes made after it was connected (each handler remembers `World::next_change_number`), so `part.Name = "A"; part.Changed:Connect(f)` doesn't run `f`. Handlers' own changes fire in further rounds, at most 10 (`MAX_CHANGE_ROUNDS`) per call; past that the rest wait for the next call and Output says once that a handler keeps changing what it listens to, so a loop never freezes the game. Changes to an Instance that's gone by then are skipped.
- Errors in one script never stop other scripts. Report them to Output with the script path and line. An error in a `task.spawn` or `task.delay` function is reported the same way and doesn't stop the script that started it.
