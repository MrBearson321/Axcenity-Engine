# Server and client

Scripts, LocalScripts, RemoteEvents, input, and the camera.

- `Script` runs on the server side. `LocalScript` runs on the client side (input, camera, UI).
- `RemoteEvent` sends messages server ↔ client. v1 uses an **in-memory loopback transport**, so keep the transport behind a trait so a real network can replace it.
- Client-only APIs (input, camera, local UI) error in a `Script` with a helpful message, and vice versa.
- File naming: `*.server.lua`, `*.client.lua` and (Phase 15) `*.module.lua`, which both sides can require.

### Decided in Phase 14

- **Two interpreters**: `ScriptRuntime` owns a server `Context` and a client `Context` (`crates/script/src/context.rs`), each its own `mlua::Lua`. So the sides can't share globals, library tables or even the string metatable. Both use the one `World` (lent to whichever side runs). One client: the player on this device.
- **Where things live** (chosen by the developer, Roblox's layout): LocalScripts in `StarterPlayer.StarterPlayerScripts` (they run from there; no copying into a `PlayerScripts`), RemoteEvents usually in `ReplicatedStorage`, and a `Players` service. `StarterPlayerScripts` counts as a service (can't be moved or deleted).
- **Start order**: Scripts first, then LocalScripts, each by path. The player **joins** (a `Player` named `Player` goes into `Players` and becomes `LocalPlayer`) just before the first LocalScript starts, or at the first frame if there are none.
- **RemoteEvent API** (chosen by the developer, Roblox's shapes): `remote:FireServer(...)` (client), `remote:FireClient(player, ...)` and `remote:FireAllClients(...)` (server); `remote.OnServerEvent` handlers get `(player, ...)`, `remote.OnClientEvent` handlers get `(...)`. Calling with `.` instead of `:` explains to use a colon.
- **What can be sent**: nil, booleans, numbers (whole numbers stay whole), strings, tables (nested, any keys), Vector3, Color3, enum items and Instances. A function, coroutine or other engine object is an error (Roblox silently sends nil; an error teaches more), and so is a table that contains itself. Arguments become `RemoteValue`s (plain data), so the receiver gets copies. An Instance arrives as the same Instance (one World), or nil if it was destroyed meanwhile.
- **Delivery**: messages go into the sender's outbox, then the `Transport` (`remote.rs`: `send`, `receive(side)`; `Loopback` is two queues). In frame step 2 the server takes its messages and fires `OnServerEvent`, runs its due tasks, then the client does the same. So a key press in step 1 reaches the server in the same frame, and a server reply reaches the client in that frame too; messages sent later arrive next frame. A message with no handler connected is dropped (Roblox queues it).
- **Input**: see [Input (Phase 30)](#input-phase-30) below. Keys are named by their place on a US keyboard, with Roblox's names (`Up`, `Return`, `LeftShift`, `Zero`). A repeat of a held key isn't a new press.
- **Camera** (chosen by the developer): `workspace.CurrentCamera` with `Position` and `Orientation` (read and set; degrees like a Part, X pitch, Y yaw, Z ignored) and `LookVector` (read). Setting moves the view, and the player can still fly on from there; no `CameraType` yet. The host passes the camera in with `set_camera` each frame and applies `take_camera_move` before drawing. While a `ThirdPersonController` owns the view, scripts still read that camera, and a move they write is not applied (`docs/scripting/api-character.md`).
- **Loading screen** (`client.rs`): `game:GetService("ReplicatedFirst")` (also `game.ReplicatedFirst`; not an Instance, like RunService) has `RemoveDefaultLoadingScreen()`, LocalScripts only. It sets a flag the host takes each frame (`ScriptRuntime::take_loading_screen_removed`) to let the project's loading screen go; see [project/export.md](../project/export.md).
- **Graphics settings** (`user_settings.rs`): `game:GetService("UserGameSettings")` (also `game.UserGameSettings`; not an Instance), LocalScripts only, reads and changes this computer's graphics settings: `GraphicsQuality` and the overrides. Fields, enums and how hosts apply and save them: [rendering/settings.md](../rendering/settings.md).
- **Wrong side**: `sides.rs` lists every side-only API (`SIDE_ONLY_APIS`: UserInputService, CurrentCamera, LocalPlayer, FireServer, OnClientEvent, UserGameSettings, RemoveDefaultLoadingScreen on the client; FireClient, FireAllClients, OnServerEvent on the server) with a message such as "UserInputService only works in a LocalScript, because input comes from the player's keyboard. This is a Script, which runs on the server: read the input in a LocalScript, and send it to the server with a RemoteEvent's FireServer." Reading one on the wrong side raises it as `path:line:` error. The editor uses the same list for its warning badges.

### Input (Phase 30)

Code: `crates/core/src/input.rs` (the input map, `InputEvent`, held `InputState`), `crates/script/src/input.rs` (the Lua API), `crates/player/src/input.rs` and `crates/editor/src/viewport/game_input.rs` (the hosts), `crates/ui/src/gamepad.rs` (controllers).

- **Events in.** Hosts send a frame's `InputEvent`s with `ScriptRuntime::input_events` in frame step 1 (`input` still takes plain `KeyEvent`s). Each is a key, a mouse button (with its position), the mouse's movement for the frame (one event, its delta in pixels), the wheel (notches), a touch, or a controller's button, stick, connect or disconnect. Positions are physical pixels from the top left of the window (the player) or the viewport (the editor). Controllers are numbered from 0 (`Gamepad1`) in the order first seen, up to four, and read with `gilrs`.
- **`gameProcessedEvent`** is the event's `processed`: true for a click on a TextButton or TextBox, or on a widget or scroll bar; for keys typed into a TextBox (the player; the editor's Play still keeps typed keys from scripts); for a key or controller button that moved focus; and for the wheel over a ScrollingFrame. Scripts still get those events. Actions, `ContextActionService` and the built-in controllers don't use them (`InputState::follow` leaves out a taken press, and its release).
- **`InputObject`**: `KeyCode` (`Unknown` for the mouse and touches; `ButtonA`… for controller buttons, `Thumbstick1`/`Thumbstick2` for sticks), `UserInputType` (`Keyboard`, `MouseButton1`–`3`, `MouseMovement`, `MouseWheel`, `Touch`, `Gamepad1`–`4`), `UserInputState` (`Begin`, `Change`, `End`, `Cancel`), `Position` (Vector3: pixels, Z the wheel's notches; a stick's -1 to 1, up positive) and `Delta`.
- **`UserInputService`** events: `InputBegan`, `InputChanged` (mouse movement, wheel, touch moves, sticks), `InputEnded`, `TouchStarted`/`TouchMoved`/`TouchEnded` (before the Input… event), `GamepadConnected`/`GamepadDisconnected` (with `Enum.UserInputType.GamepadN`). Methods: `IsKeyDown` (keyboard), `IsMouseButtonPressed`, `GetMouseLocation`, `GetMouseDelta` (this frame's movement; zero on a frame without), `GetConnectedGamepads`, `IsGamepadButtonDown`, `GetGamepadState` (an InputObject per button and stick). Fields: `MouseBehavior` (`Enum.MouseBehavior.Default`, `LockCenter`, `LockCurrentPosition`) and `MouseIconEnabled`; hosts read them each frame (`ScriptRuntime::mouse`). LockCenter holds the cursor hidden in the middle (the player grabs it, and puts it back in the middle each frame where the system only confines it), LockCurrentPosition hidden where it is; the mouse's movement still arrives, so `GetMouseDelta` can turn a camera. Right-button look holds it too, as before.
- **The input map** (`input.json`, [project/layout.md](../project/layout.md)): named actions, each an axis or not, bound to keys and controller buttons (`Space`, `ButtonA`), mouse buttons (`MouseButton1`), four keys as an axis (`W,A,S,D`: up, left, down, right), a stick (`Thumbstick1`) or `MouseMovement`. The defaults: `Move` (W,A,S,D; the arrows; the left stick), `Look` (the mouse; the right stick), `Jump` (Space, A), `Run` (LeftShift, L3), `Crouch` (C, B), `Interact` (E, X), `Primary` (MouseButton1, R2), `Secondary` (MouseButton2, L2), `Menu` (Escape, Start), and the UI's `UINavigate` (arrows, d-pad, left stick), `UIConfirm` (Return, A), `UIBack` (Escape, B), `UINext` (Tab, R1; Shift+Tab is previous) and `UIPrevious` (L1). Keys and sticks add up to at most 1 long, a stick has a 0.15 dead zone, and `MouseMovement` adds its pixels on top. A project without the file uses the defaults; a damaged one is reported and uses them too. The editor edits it in File > Input… (`app/input_settings.rs`); a change is written at once and used from the next Play.
- **Actions in scripts**: `UserInputService:IsActionPressed(name)`, `:GetActionAxis(name)` (Vector2, right and up positive), `:GetActionInputs(name)` (the inputs' names) and `:RebindAction(name, inputs)` (a table of `Enum.KeyCode` items, mouse buttons or `MouseMovement` from `Enum.UserInputType`, or input names such as `"W,A,S,D"`). An unknown action is an error listing the actions. A rebind is kept as the SaveService setting `Input/<name>` (its inputs' names, separated by spaces), so it's saved in slots and comes back when one loads; `ScriptRuntime::input_map` is the project's map with those settings applied, which hosts read every frame.
- **`ContextActionService`** (LocalScripts only): `BindAction(name, handler, createTouchButton, ...inputs)` binds `Enum.KeyCode` or `Enum.UserInputType` items (`Keyboard` for any key, `GamepadN` for anything on that controller) at priority 2000; `BindActionAtPriority(name, handler, createTouchButton, priority, ...inputs)`; `UnbindAction(name)`, `UnbindAllActions()`, `GetBoundActionInfo(name)` (`priorityLevel`, `inputTypes`, `createTouchButton`, `stackOrder`, or an empty table). On each input's Begin, Change and End, only the highest-priority action that wants it runs (the latest bound, of equal ones), as `handler(actionName, inputState, inputObject)` in its own coroutine. Binding a name again replaces it; a stopped or reloaded script's bindings go. Not yet: `Enum.ContextActionResult.Pass` (a handler can't pass the input down) and touch buttons (`createTouchButton` is kept but nothing is drawn).
- **Controls menu**: the ribbon's UI group has **Controls** (`app/controls_ui.rs`), which inserts a hidden ScreenGui `Controls` (a row per non-axis game action, its `Binding` button showing the inputs) and `scripts/Controls.client.lua`. In the game, Menu shows and hides it; clicking an action's button and pressing a key, controller button or mouse button rebinds the action with `RebindAction`.
