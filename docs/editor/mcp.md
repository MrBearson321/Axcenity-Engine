# MCP server for AI clients

`axcenity-editor --mcp <project>` serves a project to AI clients (Claude Code, Cursor, Codex, local models) over the Model Context Protocol, on stdin and stdout: in the editor window that has the project open, if it takes AI connections ([In the open editor](#in-the-open-editor)), otherwise by opening the project without a window. Editor-only: the player and server never link it (`scripts/check-platform.sh` checks). The design, the full tool inventory and the decisions behind it are in `docs/research/mcp/`; this file is what exists now.

The protocol half is the `mcp` crate (`axcenity-mcp`): `rmcp` on a thread of its own, tool specs and their flat JSON schemas, argument checks and the one error shape. The tools are the editor's, in `editor/src/app/mcp.rs` and one file per tool in `app/mcp/`, so they work through the same `EditorApp` code the panels use. Each call is handed to the thread that owns the `EditorApp` as a `Job` and runs one at a time; a panic in a tool becomes an `internal` error instead of ending the server.

## Running it

```
axcenity-editor --mcp [--check] <project folder> [--profile lite|standard|full] [--mode read|edit|full] [--allow-import <folder>]…
```

`--check` doesn't serve: it opens the project, prints `ok`/`warn`/`FAIL` lines (the project, the mode, whether the call log can be written, the profile's tool count and token cost, each `--allow-import` folder) and then the lines to add the server to Claude Code, `mcpServers` JSON clients, VS Code and Codex, with this binary's and the project's full paths and the other flags filled in (`app/mcp/check.rs`); it exits with 1 if anything failed. The user guide is [docs/mcp/README.md](../mcp/README.md).

The server runs on a thread with a 64 MB stack (`mcp::STACK_SIZE`): opening a project takes more than the 1 MB Windows gives a program's first thread in a debug build. `--project <folder>` works in place of the positional folder. If the folder isn't a project it says why on stderr and exits with 1. stdout carries only protocol messages; everything else goes to stderr. Closing stdin ends the server. Object edits stay in memory until `project_save`: closing without saving loses them (the undo history goes with the process). `script_write` saves its file at once, as Insert Script does. `--allow-import` (repeatable) names a folder `asset_import` may copy from; without one, nothing outside the project is read.

### In the open editor

Settings ▸ AI connections ▸ Allow AI connections (off by default, saved with the editor's settings, not the project) lets clients work in the window you have open (`app/mcp/live.rs`). While it's on and a project is open, the editor listens on a loopback port (`127.0.0.1`, a port the system picks) and writes `.axcenity/mcp-endpoint.json` (`port`, `token`, `pid`) into the project, written whole and removed when it stops (the setting turned off, another project opened, the editor closed). `--mcp` reads that file first: if the editor answers, the process only relays stdin and stdout to it, and the client's calls change what's on screen, as steps in the editor's own Undo. The connection's first line is the relay's hello (`token`, `profile`, `mode`, `allow_import`); the editor answers `ok` or `no <why>` (a wrong token: the editor restarted). The token is 128 bits from the standard library's randomly seeded hasher, so only programs that can read the project's files can connect. Both ends set `TCP_NODELAY`, so an answer goes out at once (with Nagle's algorithm a short answer waited about 40 ms for the delayed ACK); a call waits at most one frame ([measurements](../mcp/benchmarks.md#in-the-open-editor)).

Each connection is served by `rmcp` on a thread of its own (`axcenity_mcp::serve_tcp`); its calls come to the main thread as jobs and run at the start of a frame (`EditorApp::ai_frame`, after files changed on disk are read), one at a time, for up to 4 ms a frame before the window draws again. A call wakes an idle window (`Setup::waker`, a repaint). Each client is a session of its own (its mode, profile, import folders, undo label and `Before AI session` version), and all share one change log, so `history changes` says `by you` for the asking client's own changes and `by others` for the user's and other clients'. The page lists the connected clients and gives the `claude mcp add` line for the open project. While the game is playing in the editor, every call that changes anything is refused (`busy`): Play shows another world. A long call, such as `game_run` for 60 seconds, holds the window until it ends; the Toolbox tools are the exception, because their slow half doesn't touch the editor: `toolbox_search` and the download of `toolbox_get` run on a thread of their own (`mcp::after` leaves a `Later` in the session, `Live` keeps it pending and wakes a frame when it's done), and only the quick part (writing the answer, installing into the project, the undo step) runs on the editor. The client's next calls wait behind it, so its answers stay in order; if Play started meanwhile, the install is refused (`busy`) and the download is kept. A server without a window runs both halves at once.

Without the window, `--mcp` writes `.axcenity/mcp-headless.lock` while it serves (removed on exit), and the editor warns in Output when it opens a project that has one: the two would overwrite each other's saves. Such a server also refuses every call that changes anything while an editor that takes AI connections has the project open (it probes the endpoint before each one), saying to restart the server so it connects to the window. A client that was already running connects to the editor only when its server restarts.

Both protocol eras are served: the `initialize` handshake (2025-11-25 and earlier) and the stateless 2026-07-28 one (`server/discover`, version in `_meta`).

### Connecting a client

Every client's config, profiles for local models and troubleshooting are in the user guide, [docs/mcp/README.md](../mcp/README.md); `--check` prints the lines for this machine. In short, Claude Code: `claude mcp add axcenity -- axcenity-editor --mcp /path/to/project`; JSON clients: `{"mcpServers": {"axcenity": {"command": "axcenity-editor", "args": ["--mcp", "/path/to/project"]}}}`.

## Profiles

Each tool belongs to a profile; a server lists the tools of its profile and the smaller ones. `standard` is the default. The test `every_tool_is_short_flat_and_in_budget` holds each profile's `tools/list` under its token budget (about lite 2100, standard 4500, full 6500; lite was raised from 2000 so it could save), checks names and one-sentence summaries, and that no schema uses `oneOf`, `anyOf` or `$ref`.

## Naming objects and values

- An object is named by ID or path. An ID is the arena index, with `.generation` when that isn't 0 (`"17"`, `"17.2"`); every result shows IDs. A path is names from a service down, joined by `/` (`"Workspace/House/Door"`, `game/` in front is allowed; `"game"` is the root). A deleted object's ID is `stale_id`; a path two siblings share is `ambiguous` and lists their IDs; a script's file (`scripts/X.server.lua`) given as an object names the script's object in its service; a wrong path suggests the objects called exactly that name anywhere (a bare `"Block"` → `"Workspace/Block" (ID 12)`), or else the closest names.
- Values are in `world.json` form, compact: `[x,y,z]` vectors, `[r,g,b]` colors 0–1, numbers to 3 decimals, enum items as strings (`"Rain"` or `"Precipitation.Rain"`; a wrong one lists the right ones), object references as quoted IDs (results add the target's class and name).

## Results and errors

Results are short text, one line per object, so small models can read them. A failed call is a tool result with `isError` and two lines:

```
error not_found: no class "PointLite"
fix: did you mean PointLight?
```

Codes: `bad_args`, `not_found`, `stale_id`, `ambiguous`, `unknown_property`, `bad_value`, `locked`, `not_allowed`, `needs_confirm`, `too_large`, `busy`, `unsupported`, `internal`. An argument the tool doesn't take, of the wrong type, or missing is `bad_args`, which names the tool's parameters. A number, list or object sent as JSON text (`"[1,0,0]"`, `"3"`) is taken as that value first (`Args::check`; small models quote arrays and keep doing it when told not to); text parameters stay text. Only an unknown tool name is a protocol error.

### What changed

`history {"action":"changes"}` answers "what changed since I last looked?" without reading the scene again (`app/mcp/changes.rs`). The host keeps the edit world's change log on and moves what it records into the session's `ChangeLog` (the last 20,000 changes) before and after every call: changes from between calls are someone else's (the user's, in the live editor, or another client's), changes during a call are this client's. Each change gets a number; the answer starts `mark <n>`, the number the next change will get, and `since` (default: the mark the last answer gave, so the first ask covers the whole session) asks for what came after one. One line per object, at most 30: `added 20 Part "Wall" in Workspace`, `removed 44 Part "Old"`, `moved 17 Part "Door" to Workspace/Shed; set Position`, `set 12 Part "Block": Color, Transparency` (attributes and `tags +Enemy -Old` too). What came inside something added isn't listed again, alike objects with the same change fold into one line (`added 40× Part "Fence" in Workspace (101, 102, …)`), and with both sides present the lines are grouped `by you:` and `by others…:` (an object both changed is listed once, under others). A whole-world step (opening a level, undoing a prefab Apply) swaps the world rather than changing it, so a mark from before it, or one older than the log keeps, gets "read the scene again" instead of a wrong list. Terrain voxels, files and Play aren't object changes and aren't listed.

### Prompts and resources

Two prompts (`app/mcp/prompts.rs`, served by `axcenity_mcp::PromptSpec`) give a fixed recipe instead of relying on the model to plan; a client shows them as commands (Claude Code: `/mcp__axcenity__axcenity_build`). `axcenity_build` (`goal`, required) walks through looking, planning sizes in studs, making a Model and its parts (one `batch` where the profile has it), checking, and saving; `axcenity_fix` (`problem`, optional) runs `project_check` and `game_run`, fixes scripts with exact edits, and checks again at most three times. Each names only the tools the server lists: `lite` gets no `batch` step.

Resources mirror read tools (`axcenity_mcp::ResourceSpec`); reading one runs the tool, so nothing is resource-only: `axcenity://project` (`project_info`), `axcenity://scene` (`scene_inspect`), and the templates `axcenity://object/{id}` (`object_get`), `axcenity://docs/{class}` (`docs`) and `axcenity://script/{path}` (`script_read`). The value in a template is percent-decoded (`Workspace%2FDoor`). A tool error comes back as a protocol error.

## Edits and safety

- **Modes** (`--mode`, reported by `project_info`): `read` refuses every tool that changes anything (`not_allowed`, naming the flag that allows it); `edit` (default) runs edits and asks first for destructive ones; `full` runs everything without asking. Each tool has one safety class (read, add, modify, destructive), which sets its MCP annotations (hints that only repeat the spec's defaults are left out, to save tokens); the tool itself decides per call whether a call asks first (a 3-object delete doesn't, a 300-object one does).
- **One undo step per call.** `app/mcp/ops.rs::write` works like a plugin call: it copies the world, runs the change with the world's change log on, and records the objects the log names as one step (`History::record_edits`) labelled `AI (<client>): <what>`, where the client is its self-reported `clientInfo.name`. If the change fails part way (a bad value on the third object), the copy is put back, so a failed call changes nothing and leaves no step.
- **Asking first.** In `edit` mode a destructive call without `confirm` changes nothing and returns `needs_confirm`: `preview: …` and a fix line with a 6-character token. The same call again with `"confirm":"<token>"` runs it. A token (`axcenity_mcp::Confirms`) is bound to the tool, its arguments (all but `confirm`) and the history's revision, works once (a wrong try uses it up too), and expires after 2 minutes.
- **A version first.** The session's first write keeps the project files as a pinned version, `Before AI session (<client>)`, in Version History (`project::record_checkpoint`), so everything the session saved can be rolled back.
- **The log.** Every call adds a line to `.axcenity/mcp-log.jsonl` in the project (never exported): `time` (Unix seconds), `session`, `client`, `tool`, `class`, `args` (cut at 300 characters), `result` (`ok` or the error code) and `undo` (the step's label).
- Only what the editor lets you change: objects in the Workspace, ReplicatedStorage and Lighting (`tree::check_editable`), never services, Players or locked objects. No Lua runs, no shell or network, and no files are written but scripts (`script_write`), material files (`material_edit`), clip files (`anim_edit`), imports (`asset_import`), level, prefab, input, collision-group and renamed or deleted asset files (the full profile's tools, as the editor's own actions write them) and what Save writes; no file outside the project is read except from an `--allow-import` folder. Paths a tool takes are project-relative, with no `..`.
