# Script editing

Script tabs, saving, renaming, reloading files changed on disk (scripts keep their state, like s&box's hotload), and rebuilding the engine. The bar above a Script or LocalScript's tab picks Code, Blocks or Graph (the Graph view: `docs/scripting/graphs.md`).

- **Tabs** (v3 phase 1, chosen by the developer): every open script, stylesheet and block script is its own dock tab (`Pane::Script`), like the other panels, so it can be dragged beside the viewport, split or floated, and several can show at once. A new tab opens beside the script tab used last (wherever it was dragged), or else beside the Scene View; opening one that's open brings it to the front. The title shows the class icon in its colour, the name, `●` when unsaved and a warning sign for side warnings. Double-click a Script in the Explorer (or right-click > Open) to open it; a double-click on any other row opens what it has (`app/open.rs`, `explorer::opens_with`, cohesion pass CW3.2): UI in the UI Designer, an Animation's clip or an Animator's state machine in the Animation tab, and a part or Model selected and framed in the viewport (the camera swings round to it, at once with reduced motion; a Model's branch also opens or closes). A Folder or service only opens or closes. Tabs close with ×; a tab with unsaved changes asks "Save changes?" (Save saves only that script), and the tab stays until the script is closed. Play brings the Scene View to the front. Script tabs aren't saved in the panel layout; Reset Layout puts open ones back beside the Scene. `ScriptTabs` (`crates/editor/src/scripts.rs`) keys tabs by file path and gives each an id that survives renames and Code/Blocks switches; `Layout::sync_scripts` makes the dock match it each frame.
- **In a Collaborate session** (C7, `docs/research/collaborate.md` §4.1): a Lua script or stylesheet tab edits the file's live document, with everyone at once. Each frame `team_live_docs` (`app/team.rs`) sends the tab's typing and takes others' in (`ScriptTab::take_remote_text`, which moves the cursor and selection past the changed span); in a live tab Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y go to the document (`ScriptTab::live_undo`), which undoes only this member's typing. While a live tab has the focus its selection goes out in presence (`ScriptTab::cursor`, as sticky indexes); others' come back as `ScriptTab::others` and are drawn over the text by `scripts/others.rs` (C8, §5.7). Live tabs never lock and never show the changed-on-disk bar: the host writes the file about two seconds after typing stops, and reading it only updates what the tab counts as saved (`sync_tab`). Other documents keep the lock.
- **Code editor**: egui's `TextEdit` in code mode, monospace, line numbers in a gutter, long lines scroll sideways instead of wrapping (so the numbers line up), Tab indents. Lua highlighting is a small hand-written tokenizer (`editor-kit`'s `lua_syntax.rs`, no new dependency): keywords, `true`/`false`/`nil`, engine and standard globals, numbers, strings (including `[[long]]` ones) and comments, in VS Code-like colors for the dark and light themes. Script tabs stay editable during Play, and saving one runs it again in place (see Live scripts).
- **Completion and signature hints** (G4 stage 1; `script_completion.rs`, the popup `scripts/assist.rs`): typing `.` or `:` in a Lua code tab lists what can follow, and Ctrl+Space lists what fits the word being typed (keywords, the script's locals and parameters, globals). Typing narrows the list (exact case first); Up and Down pick, Enter or Tab puts the pick in (instead of a new line or an indent), Escape, moving the cursor or typing anything else closes it, and a click picks too. The selected row shows how it's written (`Part.Anchored: boolean`) and its doc. Typing `(` or `,` in an engine call shows its signature above the cursor with the current argument highlighted, until the cursor leaves the call. The entries come from `axcenity_script::api_reference()`, the same tables as the luau-lsp definitions file and the API Reference (each `ApiEntry` now carries its `value` type and whether it's a `library` member). Types are followed through a chain (`game:GetService("Players").LocalPlayer`, `workspace.Door.Handle` against the world being edited, `["Name"]`, `FindFirstChild`/`WaitForChild("Name")`, `FindFirstChildOfClass("Part")`, `Clone()`, `Instance.new("Part")`) and through a local's declaration (`local p: Part`, `local door = workspace.Door`, typed parameters, `for _, child in x:GetChildren()`), up to 6 locals deep. There's no type checking: what it can't follow offers nothing. Inside a string that is a call's first argument it offers the names that call takes (`script_completion/arguments.rs`; the list's quote icon): `GetService`/`FindService` the services (the game tree's and every API type documented as `GetService("Name")`), `Instance.new` and the `…OfClass` finds the classes, `IsA` and the `…WhichIsA` finds the abstract classes too (`BasePart`), `GetPropertyChangedSignal` the receiver's properties, `GetAttribute`/`SetAttribute`/`GetAttributeChangedSignal` the receiver's attributes in the world being edited (every attribute in the world when the receiver isn't known), `FindFirstChild`/`WaitForChild` the receiver's children, `FindFirstDescendant` its descendants and `FindFirstAncestor` its ancestors, and the tag methods the world's tags. Nothing else is offered inside strings, and nothing inside comments or numbers, or in stylesheets. A 5,000-line script completes in well under a frame (the test allows 250 ms in debug).
- **Go to Definition** (competitive roadmap item 4, G4's gap; `script_completion::definition_at`, handled in `scripts.rs` and `app/open.rs`): F12, or Ctrl+click (Cmd+click on macOS), on a name in a Lua code tab goes to where it's defined. A local, `local function`, global `function`, parameter or loop variable moves the cursor to the line that declares it (the nearest declaration before the cursor, as Lua scopes do; a global function anywhere in the script). A chain that names an Instance in the world being edited (`workspace.Door`, `game:GetService("ReplicatedStorage").Shared`, through locals) opens it as a double-click on its Explorer row does: a script (a ModuleScript a `require` names, too) in its tab, anything else selected and framed. An API member or global (`part.Touched`, `task.wait`) opens Help > Learn on its API Reference entry (`StartScreen::look_up_reference`). Keywords, strings, comments and names it can't follow do nothing. It reads the same chains as completion, so it follows no more than completion does (no type checking).
- **Errors and warnings** (G4 stage 2; `luau_check.rs`, `app/luau_checks.rs`): with luau-lsp installed, each Lua code tab is checked by `luau-lsp analyze` once its code has stayed the same for 0.4 s, on a background thread (one run at a time, each script's latest text only). Errors get a red wavy underline and lints (such as an unused local) an amber one; hovering one shows luau-lsp's message and kind. A line above the code counts them and names the first error; clicking it goes to that line. Underlines stay while typing until the next check comes back. A saved tab's errors are also listed in Output as `path:line:` links, once for each new set. **Checked against the whole project** (scripting priority 2): each check gets `EditorApp::project_files`, every Lua script as the editor has it (`project.scripts`, `object_files`, and open tabs' unsaved text) plus a Rojo-style sourcemap of the game tree down to each script (a service's script by `ScriptFile::instance`, a script inside an object by its `SourceFile`; a block script's Lua as `<path>.lua`). The checker mirrors them under `project/` in its temp folder (rewriting only changed files) and runs `luau-lsp analyze --platform roblox --sourcemap sourcemap.json`, so `require(game.ReplicatedStorage.Builder)` and `require(game:GetService("ReplicatedStorage").Builder)` reach the module's file and its return type: a missing function or a wrong argument type is an error in the script that requires it. The definitions it uses leave out the engine's `declare function require(module: Instance): any` (`checker_definitions`), which would hide luau-lsp's own; Roblox's platform takes its API only from the definitions given, which are the engine's. The project is gathered again when a tab goes quiet with new text and every second while tabs are open; a check is keyed by the script's path and the project's stamp (`check_key`), so editing or saving a module checks every open tab again. `require(script.Parent.X)` isn't followed (luau-lsp types `script` from the engine's definitions, not the sourcemap), and children's types aren't either (`workspace.Door.Anchored = 5` isn't flagged). Every example's scripts check without errors this way (`every_example_script_checks_without_errors`). The run uses the sandbox's disabled globals, as File > Set Up VS Code Autocomplete does (VS Code still checks each file on its own, on the standard platform); its files are in a folder of its own under the system temp folder; a run over 10 s is stopped, and one that fails says why in Output once. **luau-lsp ships with the editor** (`luau_lsp.rs`): `packaging/luau-lsp.toml` pins one release (1.70.1) and each OS's archive by size and SHA-256, and every package carries it as `tools/luau-lsp` (`tools/luau-lsp.exe`) beside the editor with its MIT license (`packaging/fetch_luau_lsp.py`, run by `stage.py`; `scripts/check-packages.py` checks it's there and prints that version). `luau_check::find` takes `AXCENITY_LUAU_LSP` first (a path naming nothing finds nothing), then that shipped copy, then one the editor downloaded, then `luau-lsp` on the PATH, then the server inside the newest VS Code Luau extension (`~/.vscode/extensions/johnnymorganz.luau-lsp-*/bin/server`). An editor built from source has no `tools/`, so while none is found a bar above each Lua code tab says type checking needs it and offers **Download (5 MB)** and **Not now** (`scripts::server_bar`, `ServerNote`); Settings > External tools > Luau language server shows which one is used and where it came from, with the same download. The download (`luau_lsp::Download`, a thread of its own, through the updater's resumable `download` and `extract`) fetches the pinned archive for this OS and architecture into `<data>/Tools/`, refuses it unless size and hash match, unpacks it beside its final folder and moves it to `<data>/Tools/luau-lsp-<version>/` whole, then checks start with it at once. Updating the pin: change the version, sizes and hashes in the TOML and run the luau-lsp tests with it (`AXCENITY_LUAU_LSP_DOWNLOAD=1` also runs a real download). Without it, the editor's own checks still underline (`script_completion/lint.rs`, run on the same 0.4 s pause, on the UI thread since they take well under a frame): a syntax error from the Luau compiler, as the script would be compiled (`axcenity_script::find_syntax_error`; when there is one it's the only finding), and names the API says can't be there, followed through the same types as completion: an Instance method that doesn't exist (`part:Destory()`, an error, with the nearest names), an `Enum` or `Enum` item that doesn't exist (an error), a property or method missing from a value type (a warning), `workspace.Dor` when the Instance being edited has no such child or member (a warning that suggests `WaitForChild("Dor")`, since a child may be added while the game runs), and the names in `GetService("…")`, `Instance.new("…")` and `GetPropertyChangedSignal("…")`. What completion can't follow is never reported, so they can miss problems but shouldn't report one that isn't there. Scripts over 300 KB get the syntax check only. With luau-lsp, its findings come first and the editor's own are kept only on lines luau-lsp says nothing about; saved tabs' findings go to Output either way. Tested with luau-lsp 1.70.1 (and 1.53.0 before it). Tests never start it unless they turn it on (`LuauChecks::enabled`); the luau-lsp tests skip without it.
- **Insert Script** (toolbar **Script** button, or Insert ▸ Script on any Explorer row) makes `scripts/Script.server.lua` (or `Script2`… if taken, including by a file that only differs in capitals) containing `print("Hello world!")`, plus its Script in ServerScriptService, then selects and opens it. It's a file operation, so it isn't an undo step.
- **Scripts inside objects** (G2; format and loading in `docs/project/world.md`): a script whose `SourceFile` names a file, usually in `objects/`, is an ordinary Instance in the tree; the file is shared by every copy of its object. With a part, Model or Folder selected (saved and editable), Insert Script puts the new script inside it and makes `objects/<object name>/Script.server.lua` (or `Script2`…), as one undo step that takes the file away again (`insert_object_script`). Open (double-click, the row menu, or Properties' open button) opens the shared file's tab; saving it writes the file and, during Play, reruns every copy in the game (`Session::reload_copies`, one "Reloaded Open.server.lua in 2 copies" line). **Attach by dragging**: dragging a Script or LocalScript row from its service (a file in `scripts/`) onto an object in the Explorer (saved, not locked, not a service or a script; `tree::check_attach`) asks "Attach it?" and then moves its file to `objects/<object>/` (a number added if the name is taken) and puts a script naming it inside the object in place of the one in the service, as one undo step that moves the file back (`app/files/attach_script.rs`; undo puts the service's Script back in `project.scripts` through `follow_service_script_files`). Its tab and breakpoints follow the file. A ModuleScript stays where `require` finds it; a block script is switched to Code first; a tab with unsaved changes is saved first. Rename and Delete change only the Instance (undoable), never the file; Duplicate, copy and move work as for any Instance. **Make Unique** (row menu) copies the file next to it (`Open 2.server.lua`, `project::numbered_path`) and points that copy at it, one undo step. Properties shows `SourceFile` with a picker that only takes a file inside the project with the class's ending. The editor keeps these files' text by path (`OpenProject::object_files`), not as `project.scripts` entries; Play finds the scripts in the world being played. The watcher also watches `objects/`; a changed file is taken in and rerun in Play (`object_file_changed`), and never makes a script in a service. Block scripts inside objects open in a Blocks tab from any copy (`open_object_blocks` reads the file into a blocks document); saving writes the shared file and keeps `object_files` in step, never adding a Script of its own. **Code, Blocks and Graph** (cohesion pass CW3.3): the view bar switches a shared file too, like Rename or Move…: `project::plan_switch` replaces `Open.server.lua` with `Open.server.blocks.json` (or back) holding the converted script, and every copy, level and prefab naming it is pointed at the new file as one undo step ("Switch Open to Blocks"); the tab follows it (`move_object_files` treats a file and its switched path as a move). Find in Scripts and Ctrl+K search list each file once, however many copies use it (Replace All keeps `object_files` in step). Properties' pencil button on `SourceFile` opens Rename or Move… for the file (`AssetBrowser::start_move`): the new path must stay in `objects/` with the same ending, and every script naming it, in the world, levels and prefabs, is pointed at it as one undo step; the file's tab follows it (`move_object_files`, run by `write_package_files` for every editor write, undo included). Asset Check and packages: `docs/editor/assets.md`, `docs/project/packages.md`.
- **Saving** (chosen by the developer): one Save (Ctrl+S, File > Save, the "Save changes?" prompt, Play's autosave) writes `world.json` and every script tab with unsaved changes. Unsaved tabs show `●` and count toward the title's `*`. `world.json` is written when the world changed, or on a plain Save with nothing else to save (as before), but never over a world file the editor didn't load (see Damaged files) unless the world changed.
- **Rename and delete** (chosen by the developer): F2 / Edit > Rename in the Explorer renames the `.server.lua` file in its folder, all at once on Enter. The Properties Name box stays read-only for Scripts, so the file isn't renamed at every key. Names must be valid file names on every OS (Windows rules: none of `/ \ : * ? " < > |`, no `CON`, `COM1`…, no trailing dot or space). Delete asks "Delete X? This deletes the file. It can't be undone." Neither is an undo step; Scripts are never in the undo history.
- **Order**: Scripts in ServerScriptService are kept in file path order (the order they start in), also after inserting or renaming.
- **Watching the folder** (polling until roadmap I10, which added OS events and kept polling as the fallback): `project::Watcher` (`project/src/watch.rs`, wrapped for egui by the editor's `watcher.rs`) runs a background thread that checks `world.json`, every script, every stylesheet and every file under `assets/` (hidden folders skipped) by modification time and size. It looks when the OS says something in the folder changed (the `notify` crate: inotify, FSEvents, ReadDirectoryChangesW; hidden top folders and the top `target` folder aren't watched, and events only in hidden folders are ignored) and every 5 s in case an event was lost; where the OS can't watch the folder (`Watcher::uses_events` is false, and a line on stderr says so) it looks every 0.5 s instead. A saved file is reported in about 0.1 s with events, against 0.1-0.6 s polling. It sends the changed paths, and wakes egui only when something changed, so an idle editor stays idle. A file still changing 0.1 s after a change is seen (a program halfway through saving it) waits for the next look. The editor reads each changed file and compares its text with what it last read or wrote, so its own saves are ignored. A changed script updates its tab; if the tab has unsaved changes, it keeps them and shows a bar with **Reload from disk** (saving replaces the file). A new file adds a Script; a deleted one removes it (its tab closes, or stays with "deleted; Save to write it back" if it had changes). A changed `world.json` is reloaded (new undo history, selection cleared) unless the world has unsaved changes; then the editor keeps its world, and the other file is kept as `world.backup.json` on the next save. During Play, a changed script the game runs reloads in place (see Live scripts) and assets reload at once; changes to the world and stylesheets, and new or deleted scripts, wait until Stop (`OpenProject::after_play`).
- **Live asset reload** (unified Phase 23; `app/files/watch.rs`, `asset_file_changed`): a changed file under `assets/` is swapped in, in edit mode and during Play, without reopening the project or stopping the game. `Assets::reload` (`assets/src/reload.rs`) reads again every model picked from it (MeshParts redraw with the new model, which has a new key, so the renderer uploads it and physics rebuilds the hull; their own properties stay), a texture (SurfaceAppearances, ImageLabels and terrain layers draw the new one), every material built on it, or the fonts. A file beside a model that the model reads (a glTF's `.bin`, its textures) reads the model again too. A model or texture whose size and time are those it was read with (the editor's own import) is left alone. During Play, the session's `Animators::reload` rebinds a changed clip, state machine or linked model file at the next frame, and each Animator stays in the state it was in, matched by name, at the same point in it; `GameAudio::reload` decodes a changed sound again, so a Sound uses it the next time it plays. The Assets panel lists the file again with a new thumbnail. Output says "Reloaded `<path>`." when something used it. A file that now fails to load keeps its last good version on screen and is reported once ("Could not reload `<path>`: …. The last good version stays."), until a good version loads. The player does the same with `--watch` (`player/src/watch.rs`: assets only, a project folder only); without the flag, and for a built game, nothing is watched.
- **Live scripts** (unified Phase 24; `EditorApp::reload_in_play`, `Session::reload_script`, `ScriptRuntime::reload_script`): when a Script, LocalScript, ModuleScript or block script changes during Play, from a tab's Save (`write_tab`) or from another editor (the watcher), it runs again in place. Its `Connect`ed handlers are disconnected and its waiting coroutines (`task.wait`, `task.spawn`, `task.delay`) are dropped, then the new code runs as a new start (fresh globals, the same `script`) against the live game world. A changed ModuleScript loads again the next time it's required, with every module that required it while loading, and the scripts that required any of them run again, in the order they first started. Every other script, and the world's state, carry on. Output says "Reloaded Door.server.lua". A file with a syntax error isn't run: the error shows with its `path:line:` link, Output warns that the last good version still runs, and the old code carries on. A script destroyed in the game isn't reloaded. Saving still writes the file, and the next Play runs it too.
- **Keeping state across a reload** (unified Phase 89, like s&box's hotload; `blocks::hot_reload` wraps, `script/src/hot_reload.rs` keeps): in the editor's Play (`ScriptRuntime::enable_hot_reload`, set in `play.rs`; the player never wraps), each script's and module's top-level `local`s are rewritten as they load, on the same lines, so a reload can carry them over: before the old run stops, getters it registered read each local (`snapshot`); in the new run a local whose key (its name, `name#2` for a second one) and initializer text (hashed, whitespace ignored) match takes the old value and skips its initializer, so `local part = Instance.new("Part")` doesn't make a second part. Functions, threads, connections and `nil` are never kept, so code and handlers always come from the new run. A local whose initializer was edited takes the new value (unlike s&box, where changed defaults wait for a restart); `-- @reset` at the end of the line, an initializer that uses the name it declares (`local print = print`) or `...` always run the initializer. A ModuleScript that loaded as a table runs its new code at once (`Context::reload_module_keeping`), and the new table's contents are copied into the table scripts already hold (`hot_reload::merge_into`), so they see the new functions and keep running without starting again (a module that returns something else reloads as in Phase 24). Output says "Reloaded Door.server.lua, kept count and part". Code the Luau reader can't read, or wrapped code that doesn't compile, loads as written and reloads from scratch. Threads that were waiting (a `while` loop with `task.wait`) start again in the new run, with the kept values.
- **Rebuilding the engine** (unified Phase 25; `rebuild.rs`, `relaunch.rs`, `app/engine.rs`): only a debug editor built with the dev-only `engine-dev` feature (unified Phase 89) and run from its source tree has this (`EngineSource::for_rebuilds` is `None` otherwise, and `EngineSource::find` in release builds, which don't keep the path, so there's no Settings page, watcher or build; the player never depends on the editor). Engine hot-patching (Phase 26, `subsecond` and `dx`) was removed in Phase 89: game files hot reload, engine code rebuilds and relaunches. Settings > Engine > **Rebuild when engine code changes** (saved between runs) watches `crates/**` (`.rs`, `Cargo.toml`, `.wgsl`/`.glsl`/`.hlsl`; `target` and hidden folders skipped) with `project::Watcher::start_listing`, and on a change runs `cargo build -p axcenity-editor --message-format=json --target-dir target/relaunch` in the background: the same (debug) profile, but its own target folder, so the running program is never locked on Windows. Changes during a build start another when it ends. The bottom-right note shows crates compiled out of the last build's count. Compiler errors go to Output as `path:line:column: error[code]: message`; clicking one opens the file at that line in VS Code (`code --goto`, when it's on the PATH) or with the system's program. A failed build says so and leaves the running editor as it was. **Rebuild Now** builds without a change.
- **Relaunch**: a build that succeeds offers **Relaunch** in a bottom-right note (or relaunches at once with **Relaunch automatically after a build**). Relaunch writes a handoff folder in the editor's data folder (`<eframe storage>/Relaunch/handoff-<pid>`, never the project): the open project, the world as world-file text when it has unsaved changes (Terrain landscapes in files beside it), the open script and stylesheet tabs with their unsaved text, unsaved block scripts, the layout, the viewport camera, the selection (by `Locator`: class, name and which of that kind, from the root down), and during Play the game world. It saves the settings, copies the built program to `target/relaunch/run/` (so the next build can write over the original) and starts the copy with `--resume <folder>`, then closes without asking about unsaved changes. The new editor opens the project from its files, `relaunch::morph`s its world into the carried one (matching Instances keep their IDs, so scripts and documents still point at them; scripts and Players aren't in world files and stay), marks it unsaved, reopens the tabs, and resumes Play from the carried game world (morphed from a copy of the edit world, so IDs match for Keep), with no loading screen; scripts start again against it, and physics and animation start fresh from those positions. It deletes the handoff, and Output says the undo history starts fresh. Unsaved Event Graphs and behavior trees aren't carried: Relaunch asks to save them first.
- **Restart now** (any build; `EditorApp::restart_editor`, `relaunch::restart`): for a setting read only at start (Hardware ray tracing), Settings > Graphics > Ray tracing and the viewport's ray tracing badge offer **Restart now** while a restart would change what the GPU was opened with (`needs_restart`). It writes the same handoff as Relaunch (refused, and said why, while an Event Graph, behavior tree, data table or material is unsaved), saves the settings, and starts `std::env::current_exe()` again with `--resume <handoff>`, which every build accepts.
- **Damaged files**: opening reports each file that can't be loaded in Output ("Skipped a damaged file: …", with the line for bad JSON) and loads the rest. A damaged `world.json` gives an empty Workspace with a hint; fixing the file elsewhere loads it. Saving over a world file the editor never loaded first renames it to `world.backup.json` (`world.backup2.json`… if taken), so nothing is lost.
- **Breakpoints** (v2 Phase 4): clicking a line number in a code tab sets a breakpoint there (a red dot; hovering shows a faint one), and clicking again clears it. They're kept by file path (`ScriptTabs::breakpoints`), whether or not the tab is open, follow a renamed script, and last until the editor closes. They don't move when lines are added above them, and a line with no code (blank, a comment) never stops. Right-clicking a line number opens the breakpoint's window: a condition, a hit count and a log message (Save sets the breakpoint too, Remove Breakpoint clears it; a condition that isn't a Lua expression isn't saved). A breakpoint with a condition or hit count is a red dot with a light middle, a logpoint a red diamond; the rule goes with its breakpoint (renames, clearing). Block tabs have no gutter. What a breakpoint does in Play: `docs/architecture/play-mode.md`.
- **Find in Scripts** (unified Phase 70; `find_in_scripts.rs`, `app/find_in_scripts.rs`): Ctrl+Shift+F (Cmd+Shift+F), Edit > Find in Scripts…, or the command palette opens a window that searches every Lua script and block script as the editor has them (a tab's unsaved code, a block script's unsaved blocks; a UI Event Graph's LocalScript is left out, since it's made from its graph). **Aa** matches case, **ab** whole words, **.\*** makes the query a regular expression (the `regex` crate; a bad one says why). In a block script it matches each text of a block (target paths, names, messages, variables; not the block's kind), as one result per text. Results are listed by script; clicking one opens the script with the cursor on that line, or the block script with that block highlighted. **Replace All** (not during Play) replaces every match (a regex's replacement may use `$1`), writes each script it changed (so their unsaved edits are saved with it), and is one undo step (`History::record_blobs`) that puts the files, the open tabs and the block scripts back; files the editor writes this way are taken in quietly (`EditorApp::take_script_text`, from `write_package_files`). A replacement that would leave a block script unreadable is refused.
- **Error links**: Output lines of kind Error that start with `<path>.lua:<line>:` underline that part, and clicking opens the script at that line (cursor placed, scrolled into view, the line highlighted until the code is edited).
