# Editor plugins

Lua plugins that extend the editor (Phase 54). Editor-only: built games and the player never have plugin code. The plugin API is the `plugins` crate (`axcenity-plugins`); the editor runs plugins in `app/plugins.rs`, and keeps their state and the Plugins panel in `plugins.rs`. `examples/hello-plugins` has two worked examples.

## Where plugins come from

- A plugin is a folder with a `plugin.json` and an `init.lua`, in the project's `plugins/` folder or in the editor's own `Plugins` folder (in its data folder, beside the settings), which every project gets. Project plugins are listed first, each group by folder name. A folder without `plugin.json` isn't a plugin.
- `plugin.json`: `{ "name": "Align to Grid", "version": "1.0.0", "permissions": ["files"] }`. `name` and `version` are needed; `permissions` is optional, and `files` is the only one. Unknown keys are an error, shown in the Plugins panel.
- `require("name")` in a plugin loads `name.lua` from the plugin's folder (once). Any `.css` in the folder styles the plugin's dock tabs, never the game.
- `plugins/` is never packed into a built game (`project::pack_game`) and its stylesheets aren't the project's (`project::find_stylesheets` skips it). The platform check scripts check that `axcenity-player` doesn't depend on `axcenity-plugins` (`scripts/check-platform.sh`).
- Plugins start when a project opens (and again when the world is replaced, such as the world file reloading). A plugin reloads when its `plugin.json`, `.lua` or `.css` files change on disk (two watchers, one per folder); a new or removed folder makes the editor look for plugins again. A plugin whose dock UI vanished (a Console command's undo swaps the whole world) starts again.
- **Plugins panel** (View ▸ Panels, or the Plugins ribbon tab when no plugin has a toolbar): each plugin's name, version, where it is, whether it may use project files, an on/off box, Reload, Export, and its errors (the last 20). **New Plugin…** scaffolds a folder with `plugin.json` and a starter `init.lua` (in the project's `plugins/` or the user's `Plugins`). **Import plugin…** installs a shared package. Which plugins are off, and every plugin's settings, are kept in `Plugins.json` in the editor's data folder, by the plugin's key (`project/<folder>` or `user/<folder>`).

## Creating and sharing

- A shared plugin is a zip of the plugin folder with the suffix `.axcenity-plugin` (`plugins::bundle`: `pack`, `preview`, `install`, `scaffold`). It may only contain `plugin.json`, `.lua` and `.css` (flat in the zip, or under one top folder). Unsafe paths and other file kinds are refused.
- **Export** on a plugin in the Plugins panel writes that package. Creators send the file (or put it beside asset packs); there is no hosted plugin store yet.
- **Import** is in the Plugins panel and in the Toolbox's **Packs ▸ Import plugin…** menu: the package unpacks into the open project's `plugins/` (or the user's `Plugins` with no project), then the editor rescans and opens the Plugins panel. A folder that already exists is left alone.
- `examples/hello-plugins` remains the worked reference; New Plugin… writes the same shape of starter.

## The plugin API

Each plugin runs in its own sandboxed interpreter (`script::EditRuntime`): the scripts' sandbox and Instance API on the edit world, server side, `RunService:IsStudio()` true and `IsRunning()` false. Plugins only run while editing; during Play their buttons are off and nothing calls them.

- `plugin:CreateToolbar(name)` and `toolbar:CreateButton(id, tooltip, icon)`: a ribbon group on the ribbon's **Plugins** tab. `icon` is a Phosphor icon name from a short list (`grid-four`, `magnet`, `ruler`, `paint-brush`, `wrench`, …), or one symbol; anything else is a puzzle piece. A button has `Click`, `Enabled` and `SetActive(bool)`.
- `plugin:CreateDockWidget(id, { Title = "…" })` returns a ScreenGui outside the tree for the plugin's UI: Frame, TextButton, TextLabel, Slider and the other UI Instances, parented to it with the normal API. It's laid out alone by `ui::UiInteraction::only`, styled by the plugin's `.css`, and drawn in a dock tab (`Pane::Plugin`, opened beside Properties, never saved in the layout). Its `Enabled` shows or hides the tab; closing the tab turns it off. Buttons fire `Activated`, `MouseEnter` and `MouseLeave`; widgets' `ValueChanged` and other change events fire for changes the pointer makes. Being outside the tree, it's never saved, shown in the Explorer, or undone.
- `Selection:Get()`, `Selection:Set(list)` (only Instances in the game) and `Selection.SelectionChanged` (the editor's changes, not the plugin's own `Set`). Also `game:GetService("Selection")`.
- `ChangeHistoryService:SetWaypoint(name)`, `Undo()` and `Redo()`. Also `game:GetService("ChangeHistoryService")`.
- `plugin:GetSetting(key)` / `SetSetting(key, value)`: nil, booleans, numbers, strings and tables of them, kept per plugin.
- `plugin:ReadProjectFile(path)` / `WriteProjectFile(path, text)`: only with the `files` permission, and only inside the project. A path is relative with `/`; absolute paths, `..`, `\`, `:` and links that lead out of the project are refused (`plugins::files`).
- `plugin:GetMouse()`: `Hit` (a CFrame on the part under the mouse, or 1000 studs along the view), `Target`, `Button1Down`, `Button1Up` and `Move`, over the Scene View. `plugin:Activate(true)` takes the left button from selecting and dragging; `Deactivate()` and `IsActivated()`; `plugin.Deactivation` fires when it's taken back.
- **Viewport drawing** (roadmap G10; `plugins::draw`, painted by `viewport/plugin_drawings.rs`): `plugin:DrawLine(from, to, options)`, `DrawBox(at, size, options)` (`at` a CFrame, or a Vector3 for a box lined up with the world), `DrawSphere(center, radius, options)` (three rings) and `DrawText(position, text, options)` (a label that keeps its size, up to 200 characters). `options` is `{ Color = Color3, Thickness = points }` (orange and 2 unless given; `Thickness` is the text size for `DrawText`, 14 unless given; widths are kept between 0.5 and 32). Each returns a drawing with `Remove()` and `SetColor(color)`; `plugin:ClearDrawings()` removes them all. Drawings are retained: they stay until removed, so a plugin redraws only when something changes (Align to Grid in `examples/hello-plugins` redraws on `SelectionChanged`). They're drawn over the scene, never hidden by parts, only while editing; they go when the plugin stops or reloads. A plugin keeps at most 10,000 at once (more is an error), and positions must be finite. The editor reads them after each call into the plugin (`Plugin::take_drawings`, only when they changed). Drawing is never an edit, so it makes no undo step.
- **Handles** (roadmap G10; `plugins::draw`, input and drawing in `viewport/plugin_handles.rs`): `plugin:CreateHandle(position, { Color, Size, Axis })` puts a dot in the Scene View that the user drags while editing. With `Axis` (a Vector3) it slides along that direction, drawn with a line through it; without, it moves in the plane facing the camera. The Move snap (its step, when on) applies to the move from where the drag started. `Size` is the dot's radius in points (3 to 24, 7 unless given). A handle has `Position` (setting it moves it without firing anything), `Dragged(position)` each time the mouse moves it, `DragEnded(position)` when the button is let go, and `Remove()` (which also disconnects its events). A press on a handle takes the left button, so it neither selects nor drags parts; Alt+drag still orbits, and while a plugin has the button (`Activate(true)`) handles don't take it. Edits a plugin makes in `Dragged` merge into one undo step until a waypoint, so set one in `DragEnded`. At most 256 handles per plugin; they go when the plugin stops. `examples/hello-plugins`' Part Tools puts a height handle on top of the selected part.
- **Properties rows** (roadmap G10; `plugins::rows`, drawn by `properties/plugin_rows.rs`): `plugin:AddPropertyRow({ Attribute, Default, Class, Label, Tooltip, Min, Max })` shows an attribute as a row of its own, and `plugin:AddPropertyButton({ Label, Class, Tooltip })` a button. Rows show in the Properties panel while one Instance is selected and it `IsA` their `Class` (every Instance when left out), in a section named after the plugin, below the panel's own sections. An attribute row shows the attribute, or `Default` (in weaker text) until it's set; `Default` also gives its type. Numbers stay between `Min` and `Max`, and with both the row is a slider. Editing the row sets the attribute exactly as the Attributes section does (its own undo step, `Set attribute Speed of Crate`), then fires the row's `Changed(instance, value)`. A button row's `Activated(instance)` runs in the plugin like a toolbar click, so its edits are an undo step too. Rows are declared, not drawn by Lua, so no plugin code runs while the panel draws. `Remove()` takes a row away; at most 64 rows per plugin, and they go when the plugin stops. A bad `Attribute` name, a missing `Default` or `Label`, an unknown `Class` or `Min` over `Max` is an error. Align to Grid in `examples/hello-plugins` adds a Snap to Grid button to every part.
- **Importers and the Assets panel** (roadmap G10; `plugins::assets`): `plugin:AddImporter({ Name, Extensions })` imports file kinds the editor doesn't import itself (its own kinds, such as models, images, sounds, skies, prefabs and packages, stay its own). Such a file, picked with Import… (each importer adds a filter there) or dropped on the window, goes to the importer's `Imported(name, contents)`: its name without folders, and its bytes as a string (up to 16 MB). The first running plugin that takes the ending wins. What the plugin makes is an undo step like any of its calls; a `SetWaypoint` names it. `plugin.AssetImported(path)` fires after the editor imports a file itself, with the copy's path in the project (`app/plugins.rs`: `import_with_plugin`, `plugins_asset_imported`). `plugin:AddAssetAction({ Label, Extensions, Tooltip })` adds an item to the Assets panel's right-click menu for the project's own assets with those endings (all of them when `Extensions` is left out), firing `Activated(path)` (`asset_browser/panel.rs`, `BrowserAction::PluginAction`). Both have `Remove()`; at most 32 per plugin together.
- **Commands** (API 3, P7.4; `plugins::actions`): `plugin:CreateAction({ Id, Text, Shortcut, Tooltip })` adds a command that Ctrl+K lists as `Text` (the `Id` when left out) under **Plugin › <name>**; searching its `Id` finds it too. It fires `Triggered` when picked there or when its `Shortcut` is pressed while editing (not while typing in a text box). A shortcut is Ctrl, Shift and Alt with a letter, a digit or F1 to F12 (`"Ctrl+Shift+L"`; Cmd on macOS); without Ctrl or Alt only F1 to F12 are taken, so a plugin can't take a key that's typed. A shortcut the editor already uses stays the editor's, and Ctrl+K shows it as `(the editor's)`. Making a command with the same `Id` again changes that one (`app/plugins.rs`: `plugin_shortcuts`, `trigger_plugin_action`; `app/command_palette.rs`: `Command::PluginAction`).
- **Explorer items** (API 3): `plugin:AddExplorerAction({ Label, Class, Tooltip })` adds an item to the Explorer's right-click menu, on rows of `Class` (or a class that is one, such as `BasePart`; every row when left out). It fires `Activated(instances)` with the selection, which holds the row right-clicked. Its edits are an undo step like any call. Commands and Explorer items have `Remove()`; at most 32 per plugin together, and they go when the plugin stops.
- **`plugin.ModelImported(root, path)`** (API 3) fires when the editor imports a model (glTF, GLB, FBX, OBJ or a converted USD), once for each top Instance the import makes, with the model file's path in the project. It fires before the import is placed, so what the plugin changes on those Instances (a name, attributes, collision) is part of the import's own undo step; its other edits are a step of their own (`plugins_model_imported`).
- **`plugin.Unloading`** (API 3) fires before the plugin stops: when it's reloaded or turned off, and when the world it edits is put away (the project closes, another project or level opens, or the world is reloaded from disk; `replace_world`). Not during Play, when plugins don't run. `SetSetting` there is saved.
- **`plugin:OpenScript(script, line)`** (API 3) opens a Script, LocalScript or ModuleScript in a code tab, with the cursor at `line` when given; another Instance is an error. **`plugin:Notify(text)`** shows a short notice (up to 200 characters) with the plugin's name.
- **`plugin.ApiVersion`** is 3: 1 was Phase 54's API (toolbars, dock widgets, Selection, ChangeHistoryService, settings, files, the mouse), 2 added viewport drawing, handles, Properties rows, importers and Assets panel items, 3 added commands with shortcuts, Explorer items, `ModelImported`, `Unloading`, `OpenScript` and `Notify`. It goes up when the API grows (`PLUGIN_API_VERSION`); names are never taken away, so a plugin written for 1 runs unchanged.
- `Destroy` on an Instance in the game only takes it out of the tree (as the editor's Delete does), so it can be undone. Change events fire for the dock tabs' own changes, not for the plugin's edits or the editor's.

## Undo

Every call into a plugin runs on the edit world with its change log on, after a copy of the world is taken. Afterwards the Instances the log names (in the game, before or after) become an undo step (`History::record_edits`, `history/edits.rs`): each one's place in the tree, fields, attributes and tags before and after. Later calls merge into that step until the plugin calls `SetWaypoint(name)`, which ends it and names it; several waypoints in one call make several steps (each waypoint keeps a copy of the world). A step with no waypoint is named after the plugin.

## Errors

A plugin's errors read `plugins/<folder>/init.lua:12: message` (`Plugins/<folder>/…` for the user's), go to the Console with their trace, and are kept in the Plugins panel. A plugin that doesn't compile, or has a bad `plugin.json`, doesn't start; one that errors while running keeps running. An engine crash inside a plugin call is caught (`play::guard`) and reported the same way.

## Autocomplete

`definitions/axcenity-plugin.d.luau` declares the plugin API for luau-lsp, kept by hand (a `plugins` test checks it names the whole API). File ▸ Set Up VS Code Autocomplete writes it to `.axcenity/axcenity-plugin.d.luau`; it isn't added to the project's luau-lsp settings, because game scripts don't have these globals, so add `"@axcenity-plugin": ".axcenity/axcenity-plugin.d.luau"` to `luau-lsp.types.definitionFiles` in a workspace for plugins.
