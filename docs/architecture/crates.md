# Crates

Which crate owns what, and what it may depend on. Read this before adding a crate or a dependency.

| Crate | Owns | May depend on |
|---|---|---|
| `core` | Instance tree, arena, properties, events, services | nothing engine-internal |
| `assets` | the asset system: loading glTF/FBX models (with FBX skeletons, skin weights and takes, and levels of detail simplified by `meshopt`), posing them, reading project files (`Assets`) and importing models | nothing engine-internal; plain data out |
| `cook` | cooking textures ahead of time (roadmap L2): mip levels BC7-encoded with `intel_tex_2` into `.axcenity/imported/textures/` ([../rendering/textures.md](../rendering/textures.md)); editor only, never in the player | `assets` |
| `anim` | animation: clip and animator controller files, state machines and blending, and `Animators`, which plays every Animator and poses its MeshPart | `assets`, `core` |
| `audio` | Kira playback for project sounds: `GameAudio` applies queued `SoundAction`s (declared in `core::sound`, with the mix the world describes), keeps playback in line with each Sound, and spatializes emitters against the camera; SoundGroup buses, sound effects and ReverbZones (Phase 52) | `assets`, `core` |
| `gameplay` | game systems moved out of `script` (roadmap L7), each a `script::GameSystem` that adds services and a per-frame step: Debris so far ([game-systems.md](game-systems.md)) | `core`, `script` (its public API only) |
| `sim` | the frame every host runs (roadmap M1): `Sim`, the `Schedule` step order, `HostIo`, and `script_runtime()`, the `ScriptRuntime` with `gameplay`'s systems that every host builds ([frame-loop.md](frame-loop.md)) | `anim`, `assets`, `character`, `core`, `gameplay`, `nav`, `physics`, `script`; never `render`, `egui`, `winit` or audio output |
| `blocks-runtime` | persisted block-script data, node graphs (the UI Event Graph, and the nodes behavior trees offer) and their one-way Lua translation: what games need to load block scripts and graphs | nothing engine-internal |
| `blocks` | the block editor's side: re-exports `blocks-runtime` and adds `from_lua` (with its Luau reader), which turns code back into blocks | `blocks-runtime` (`core` and `script` only in tests) |
| `render-types` | the renderer's plain data shared with scripts and servers: `GraphicsSettings`, `Capabilities`, `EffectiveGraphics`, `Camera` (no GPU code) | nothing engine-internal |
| `render` | `wgpu` renderer; re-exports `render-types` | `render-types`; takes a draw list |
| `scene` | Instance tree → draw list (`build_draw_list`, including terrain chunks and UI layout), the shared `FlyCamera`, viewport picking (`pick`) | `core`, `assets`, `render`, `terrain`, `ui` |
| `terrain` | terrain algorithms over `core::TerrainData`: brushes, generation, erosion, chunk meshes, file codecs | `core` |
| `physics` | `rapier3d` integration, breaking joints, shattering Fractures | `core`, `assets` (`mesh_edit` only in tests) |
| `mesh_edit` | editing meshes: plane cuts that close their holes, convex Voronoi pieces, writing them as `.glb`, and generating a Fracture's pieces (Phase 42), and solid modeling's booleans (Phase 50; the Model Studio builds on it) | `core`, `assets` |
| `procedural` | what SplineMeshes and SplineScatters make along their splines (bent pieces, scatter layouts on the surface below) and keeping it up to date (`Generators`), and flattening terrain under a spline (Phase 74) | `assets`, `core`, `terrain` |
| `character` | kinematic third-person walk and run, and seats (which play an Animator's `Sit` state, read with `anim`); queries physics, never the reverse | `core`, `anim`, `assets`, `physics` |
| `nav` | the navigation mesh, built from `physics::solids`, paths across it, the `NavigationAgent` stepper, and behavior trees (checked and run, read from their files with `serde_json`); neither `physics` nor `character` may depend on it | `core`, `assets`, `physics`, `character` |
| `save` | save slots and checkpoints: `Saves` (player data, settings, the active checkpoint), world state snapshots and their restore, slot files in the player's data for the game (`game_folder`); never the project folder | `core` |
| `script` | Luau (`mlua`), sandbox, scheduler, engine API, TweenService (eased by `anim`'s curves), SaveService (over `save`; places the player character found by `character`), UserGameSettings (holds `render-types`' `GraphicsSettings` and `Capabilities`), Humanoids (MoveTo paths on `nav`'s mesh), `UnionAsync` and friends (booleans by `mesh_edit`, behind the default `csg` feature), and what SplineMeshes and SplineScatters make, each step (`procedural`) | `anim`, `character`, `core`, `mesh_edit` (feature `csg`), `nav`, `physics`, `procedural`, `assets`, `render-types`, `save` (and `glam` for CFrame math); never `render` or `audio`, so the server links no GPU or audio output |
| `ui` | UI Instance layout, CSS cascade (`taffy`), transitions (eased by `anim`'s curves), screen-space draw data, and keyboard and controller focus (game controllers read with `gilrs`) | `anim`, `core`, `render` |
| `project` | project folder load and save, including CSS and block-script sources, upgrading older projects (animation files through `anim`), the editor's asset check, and the file watcher (`Watcher`, OS events with a polling fallback; the editor, and the player with `--watch`) | `anim`, `assets`, `blocks-runtime`, `core`, `terrain` |
| `testing` | the game test runner (Phase 53): spec files' tests, each in a fresh headless copy of its level (`TestGame`), JUnit XML, and the `axcenity-test` binary | `assets`, `character`, `core`, `project`, `script`, `sim` |
| `net` | multiplayer (Phase 63): renet channels over UDP or the in-memory loopback, the join handshake (versions, password, `MaxPlayers`), LAN discovery, and `Network`, which does `NetworkService` requests and keeps `Players` in step | `core`, `script` |
| `server` | the `axcenity-server` binary: a game's Scripts and physics headless, hosted with `net` | `assets`, `core`, `net`, `physics`, `project`, `release`, `save`, `script`; never a window, GPU or audio output |
| `plugins` | the editor's Lua plugins (Phase 54): `plugin.json`, finding plugin folders, project-only file access, and the plugin API, run in `script`'s `EditRuntime` against the edit world | `core`, `script` |
| `toolbox` | the Axcenity Toolbox, finding and fetching assets online (`docs/research/asset-sources/`): the `AssetSource` trait and `AssetRecord`, the ambientCG, Poly Haven and Openverse sources, the central asset directory, its SQLite metadata database (`rusqlite`) and verified downloads into it, licence codes, the HTTPS client with size limits, the rules for untrusted downloads, the library (favourites, collections, recents), provenance and `CREDITS.txt`, the Blender library migration, Toolbox packs, the `axcenity-toolbox` CLI and its Python package; the editor's Toolbox tab uses it; editor only, never in the player | nothing engine-internal |
| `collab` | Team Create's sync core (TC1 of [../research/team-create.md](../research/team-create.md)): operations and transactions, applying them with the conflict rules and exact undo, ID blocks, roles, and the host and client state machines; no network, files or UI yet | `core` |
| `collab-server` | Team Create's self-hosted server (TC7): the `axcenity-collab` binary hosts a project folder like the hosting editor (`collab::hosted`), saves it every 30 s, recovers a crashed run from the journal, and takes admin commands (members, invites, roles, save, quit) on its terminal; members and keys stay in its own data folder | `collab`, `core`, `project` |
| `mcp` | the editor's MCP server for AI clients, engine-free: tool specs and flat JSON schemas (`ToolSpec`, `Profile`, `Class`), argument checks, the one error shape (`ToolError`), and `rmcp` over stdio on a thread of its own, handing calls to the editor as `Job`s ([../editor/mcp.md](../editor/mcp.md)); the tools are the editor's (`editor/src/app/mcp/`); editor only, never in the player or server | nothing engine-internal |
| `release` | the engine version and release channel, this build's provenance (`--version`), and the release history in `releases/`: its checks and the Version Explorer's queries; the `axcenity-release` CLI (`check`, `prepare`, `query`). | `updater` | the `axcenity-updater` binary each release ships beside the editor, and the editor's update steps: download with resume and SHA-256 checks (real HTTPS behind the `http` feature), safe zip and tar.gz unpacking, staging and hand-over, then the folder swap, `--version --json` check and roll back after the editor exits | `release` only; no egui, no engine crates |

| `editor-kit` | the editor's shared UI base (roadmap G11, the first step of splitting the editor): the design system (`theme`), controls (`widgets`), narrow-panel layouts (`responsive`), colour swatches (`color_palette`), Lua syntax colours, mouse-wheel and screen-space helpers, and drawing tests' offscreen `snapshot`s (with `theme::run` and `test_context`, behind its `test-support` feature, turned on only from `[dev-dependencies]`). | `editor` | `egui` editor app (binary) | `anim`, `assets`, `audio`, `blocks`, `character`, `cook`, `core`, `editor-benchmark`, `editor-kit`, `editor-model-studio`, `editor-node-graph`, `editor-toolbox`, `editor-tools`, `gameplay`, `mcp`, `mesh_edit`, `nav`, `net`, `physics`, `plugins`, `procedural`, `project`, `release`, `render`, `save`, `scene`, `script`, `sim`, `terrain`, `testing`, `toolbox`, `ui`, `updater` |

Block scripts are translated to Lua at project load and run through the same `ScriptRuntime` as handwritten scripts. Hosts hand queued sound actions to their `GameAudio` after script steps, and fire `Ended` for the sounds it reports finished; the player owns playback for its lifetime, while editor Play owns a separate `GameAudio` that is dropped on Stop.

Rules:
- `player` must **never** depend on `editor`, `egui`, `blocks` (the block editor's side), `plugins` or `cook`. It loads block scripts and UI Event Graphs through `project`, which translates them with `blocks-runtime`. The platform check scripts check this (`scripts/check-platform.sh`, "The player has no editor code").
- `render` never sees Instances, scripts or the editor. Something outside it turns the world into a draw list (meshes, materials, transforms, lights, camera).
- `ui` reads the Instance tree and adds screen-space layout data to the render draw list; `render` remains Instance-free.
- Don't let crates depend on each other in a cycle. If two crates need each other, move the shared type into `core`.
- Pin dependency versions in the workspace's root `Cargo.toml` (`[workspace.dependencies]`).
- Development-only dependencies sit behind a crate feature. The editor's `hot-patch` feature (`subsecond`, `dioxus-devtools`, `dioxus-cli-config`) is off by default, and nothing else, the player included, can turn it on.

## Where the big files split

A large module is a parent file plus a folder of the same name. The parent keeps the types and the entry points; each child holds one responsibility, as another `impl` block or as free functions, and starts with `use super::*;`. A `tests.rs` beside the parent holds its tests. Library crates re-export moved public items with `pub use`, so paths such as `axcenity_project::create_script` did not change.

| Parent | Children |
|---|---|
| `editor/src/app.rs` | `assets`, `behavior_trees`, `chrome`, `commands`, `edits`, `files`, `session`, `settings`, `terrain`, `tree_ops`, `ui_graphs` |
| `app/chrome.rs` | `panes` (dock panels), `menus` (title and menu bar), `toolbar` (ribbon and tools), `windows` (shortcuts, versions, pause and overlay widgets) |

| `editor-tools/src/posing.rs` | `tree` (the drawer's bone tree and folds) |
| `editor/src/asset_browser.rs` | `packages` (model folders), `scan` (finding asset files and their kinds), `thumbnails` |
