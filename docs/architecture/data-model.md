# Data model

How Instances are stored and looked up.

- One tree of **Instances**: class, `Name`, `Parent`, children, typed properties and events.
- Instances live in an **arena** and are referenced by **generational IDs** (index plus generation). Never use `Rc<RefCell<…>>` parent/child pointers.
- **Network IDs** (Phase 64): a replica world (`World::empty_replica`) holds its server's Instances at their own IDs (`World::create_at`, `Arena::insert_at`) and gives its own Instances IDs from 2³¹ up, which the server never uses (`InstanceId::is_local`). So `InstanceId::to_bits` is the same number for the same Instance on every device. ServerScriptService and ServerStorage are `World::server_only_services`.
- An ID can outlive its Instance. Every lookup returns an `Option` or `Result`; never assume the Instance still exists.
- An Instance can be the top of a placed **prefab copy** (Phase 49): `Instance::prefab` is its `PrefabLink` (`World::set_prefab`, not a `Change`). `core::prefab` matches a copy to what it was made from, works out its overrides and re-makes it from a new source (`sync`); see `docs/project/world.md`.
- Besides its properties, an Instance has **attributes** (name to `Value`, sorted) and **tags** (in the order added). Change them through `World::set_attribute`, `add_tag` and `remove_tag`, which record `Change::Attribute` and `Change::Tag`. `World::tagged` and `all_tags` only count Instances inside `game`.
- A property can point at another Instance (`Value::Instance`, `ObjectValue.Value`). It holds an `InstanceId`, so it can go stale like any other; `World::duplicate` points a copy's references into the copy when the target was copied too.
- **Walking a subtree**: `World::descendants_iter` goes through everything below an Instance, parents before children in child order, without collecting a `Vec` (it keeps one position per level it goes into, and none below a flat parent). Use it when only reading; it borrows the World, so keep `World::descendants` (the same order, collected) where the loop changes the world. Both still walk every Instance below, so for "every X" use the index below.
- **Class and tag index** (`core/src/index.rs`, roadmap M2): the World lists what's in the game (everything below `game`, not `game` itself and not detached Instances) by class and by tag, kept up to date by `create`, `set_parent`, `destroy`, `add_tag` and `remove_tag`. Services aren't listed by class (use `World::service`), but a tag on a service is. `World::all_of(class)` and `all_where(picker)` go through a class without walking, by ID; `tagged_iter(tag)` does the same for a tag, in O(number tagged).
  - **Order**: the index is in ID order, which is deterministic but isn't tree order (a reparented Instance keeps its old place in the IDs). Use `all_of`/`all_where`/`tagged_iter` only when what you do with each Instance doesn't depend on the others. `World::all_below(under, picker)` gives the same list and order as filtering a walk from `under`; `in_tree_order` sorts any list that way by walking only the branches leading to it (it costs a look at the siblings along the way, so sorted lookups in one large flat parent still scan that parent, though without touching its children's properties). `tagged` and `GetTagged` keep tree order.
  - `World::check_index` compares the index with a walk. Every game test runs it every 60 frames in debug builds.
- **Structure versions**: `World::structure_version` goes up on any change of parent, including inside a detached Model. `World::structure_version_of(service)` goes up only for changes inside that service (a child of `game`; StarterPlayerScripts counts as StarterPlayer), so a reader of one service can skip work when another changes. Collision-group edits count as a Workspace change, since physics reads them with the parts. Physics and streaming use the per-service versions; replication, which covers several services, uses the global one.
- **Hashing**: long-lived maps keyed by engine IDs (the World's per-Instance animation and terrain state, streaming's hidden and shown sets, the renderer's mesh, texture and material caches) use `rustc_hash::FxHashMap`/`FxHashSet`, which is faster for small integer keys. Keep std's `HashMap` (SipHash) for keys that come from players, the network or files, such as names and strings, where an attacker could pick colliding keys. Nothing may depend on a hash map's iteration order: sort, or use a `BTreeMap`, where order shows.
