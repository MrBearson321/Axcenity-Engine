# Networking

Hosting, joining and finding games (Milestone 14). Phase 63 is the transport, hosting and joining. Phase 64 (so far, for hosted games): a device that joins follows the server's world as a replica and runs only its LocalScripts there, RemoteEvents and RemoteFunctions cross between devices, and Players carry `UserId` and `DisplayName`. Phase 65: parts move by quantized motion within each player's budget and are smoothed on their device, and the level state follows the server. Phase 66: each player's device moves their own character, and assemblies the server gives it, with no delay; the server checks them. Phase 67: editor Play with several clients and an emulated network, the Profiler's Network section, chat, `Player:Kick`, and players' saves kept on the server. Single-player and the editor's Play are a listen server: the player on that device plays on the server's World, as `--host` does (chosen by the developer on 2026-10-29, so every example plays as before: the player test `dump_every_example`, run with `--ignored` and `AXCENITY_DUMP=<file>`, writes each example's output and part positions after three seconds, and gave the same for all 55 before Phase 64 (`0e52920`) and after Phase 67, but for hello-particles' random sparks).

## Crates

- `net` (`axcenity-net`): the transport, the join handshake, LAN discovery, the wire format (`wire.rs`), replication (`replicate.rs`) and `Network`, which the hosts run. It depends on `core` and `script`.
- `server` (`axcenity-server`): the dedicated server binary.
- `script`'s `NetworkService` (`network.rs`) never touches the network: it queues `NetworkRequest`s, and the host answers them.

## Transport

`net::transport` uses `renet` 2 (reliable-ordered and unreliable channels) over UDP through `renet_netcode` (netcode's connection handshake, 15-second timeout and disconnect reasons). The in-memory loopback has the same `Server` and `Client` interface; `Network::host_in_memory` and `join_through` use it.

- Channel 0 is reliable-ordered, channel 1 unreliable (`Channel`). The unreliable channel carries motion (below).
- The loopback can emulate a worse network (`Conditions`: `latency` added to each packet each way, give or take `jitter`, and the share `loss` dropped; `Server::emulate`, `Network::emulate`). `Network::stats` gives each connection's round trip, loss and bytes a second (renet's numbers), and the bytes sent over a loopback.
- Netcode runs unsecured: there's no account service to hand out connect tokens, so packets aren't encrypted. This is enough for direct-address and LAN play, which is all there is (no relay or matchmaking).
- Scope: local multiplayer, the server/client architecture and testing in controlled environments (loopback, LAN, a local `axcenity-server`) come first. Internet-hosted dedicated servers are a future objective: deployment, hosting, server management and secure netcode (roadmap M11) wait until the multiplayer systems are mature ([development policy](../development-policy.md#dedicated-servers-and-hosting)).
- Netcode's protocol id is the same for every game and version. Games and versions are told apart by the handshake, which can say why it refuses; netcode would drop the packets silently.
- A server listens on IPv4 (`0.0.0.0`), and joining prefers an address's IPv4 form.

## Handshake

The joining player's first message, on the reliable channel as JSON, is `Hello`: `PROTOCOL_VERSION` (10 since roadmap M7, 12 since Phase 81, 13 since roadmap R16.2 added the DataLayerService, 14 since multiplayer readiness MP2 added rejoin keys), the game's name, its version (`version` in `axcenity.json`, `"1.0"` when it isn't set), the player's name, the password, their `user_id` (missing from older engines, read as 0) their engine's class-defaults fingerprint (`defaults`, roadmap M7) and their rejoin key (`rejoin`, 0 for none; missing from older engines, read as 0). The host checks them in this order and refuses with a reason worded for each side (`handshake::admit`):

| Check | The player's `ConnectionFailed` reason | The host's log |
|---|---|---|
| Network protocol | "The server uses network protocol 1 and you use 2: play the game with the same Axcenity version." | "refused a player using network protocol 2; …" |
| Class defaults (`handshake::class_defaults`, a fingerprint of every class's default properties; replicas are sent only what differs from them) | "The server's Axcenity makes Instances with other defaults than yours: play the game with the same Axcenity version." | "refused a player whose Axcenity has other class defaults" |
| Game | "The server runs "Castle", not "Keep"." | "refused a player of another game, …" |
| Version | "Version mismatch: the server runs version 1.0 of "Castle" and you have version 2.0." | "refused a player with version 2.0 of "Castle": this server runs version 1.0" |
| Password | "This game needs a password." or "Wrong password." | "refused a player with the wrong password" |
| `Players.MaxPlayers` (8; the host's own player counts) | "The game is full (8 of 8 players)." | "refused a player: the game is full (8 of 8)" |

A refused connection stays open for a second, so the reason arrives, then closes. A connection that says nothing for 10 seconds is closed. A player who hears nothing back for 10 seconds gives up ("The server didn't answer the join request."). Netcode's own failures become reasons too: "No game answered at …", "The connection timed out…", "The server is full." and "The server closed the connection."

Accepted, the player gets `Welcome`: their id (a listen server's own player is 1), name, made unique (a second `Player` is `Player2`), display name (the name they asked for) and user id, everyone already in, and a rejoin key (`rejoin`: 64 random bits from `ring`, never 0) for coming back after a lost connection ([Reconnecting](#reconnecting)). `Joined` and `Left` keep every roster the same. `Hello` and `Refused` must stay readable by later engines; raise `PROTOCOL_VERSION` when a message changes.

## Players

On the host, `Network::receive` turns the roster into Players: `ScriptRuntime::add_remote_player` makes a Player in `Players` with its `DisplayName` and `UserId` (on a team; `PlayerAdded` fires; their character comes in the next `step_players`, Phase 66), and `remove_player` fires `Players.PlayerRemoving`, then destroys the Player and its character. On a player's device, Players come with the server's world: one that arrives fires `PlayerAdded` in its LocalScripts (`add_replicated_player`), and one the server removes fires `PlayerRemoving` there before it goes. A failure, a refusal or `Disconnect` removes every other player, from a replica too.

- `Player.UserId` is the install's identity: a random whole number from 1 to 2⁵³−1, kept in `user-id.txt` in the saves folder (`axcenity_save::user_id`, beside every game's save folder), made the first time. There are no accounts. A dedicated server has no player, so no UserId. The editor's tests use a fixed one so they never write it.
- `Player.DisplayName` is the name they joined with; `Name` is that, numbered if taken. Both are read-only to scripts.

## The wire

Every message but the two below is [postcard](https://docs.rs/postcard) (compact binary serde) after a format byte (`handshake::Message::to_bytes`), since roadmap M7 (protocol 10): S10k's snapshot is 1.0 MB instead of 14.4 MB of JSON, which was too big for the reliable channel's 5 MiB, so no player could join it. `Hello` and `Refused` stay the JSON object they always were (`{"type":"Hello",…}`), so any engine can still read a join request and say why it refuses. Set `AXCENITY_NET_JSON=1` on a device to send JSON instead (after its own format byte) while debugging; every device reads both. Postcard needs every field written in order, so the wire types (`wire.rs`, `replicate.rs`, `handshake.rs`) use serde's plain layout: no `skip_serializing_if` and no `#[serde(tag)]`. Motion and own-character packets are their own fixed binary layout, as before.

## Worlds and replication

Each device has its own World. The server's is the game; a player's device that joined keeps a **replica**: `World::empty_replica` (the services only, at the same IDs, with the device's own string table, language, UI settings, collision groups and volume), filled with `World::create_at`. The replica's arena holds the server's Instances at their own IDs and puts the device's own (what LocalScripts make) in a range the server never uses (`InstanceId::is_local`), so an `InstanceId` is the network ID: `to_bits` and `from_bits` name the same Instance everywhere.

- **What's sent** (`replicate.rs`): `game`'s properties and every service but the server-only ones, ServerScriptService and ServerStorage (`World::server_only_services`), with everything inside, but for what a switched-off data layer has parked inside its `DataLayer` (roadmap R16.4: `World::is_server_only` covers it; the layers themselves are sent, [../editor/layers.md](../editor/layers.md#in-a-game)) and what SplineMeshes and SplineScatters made (Phase 74): each device makes that itself from the same settings ([splines.md](splines.md)). A player's replica has those two services, empty.
- **Joining**: the host sends `Snapshot` (which Player is theirs, then each service's properties and every Instance, parents first). The device stops every script (`ScriptRuntime::become_client`), swaps its world for the replica, copies its own copy's Terrain landscapes by ID, sets `LocalPlayer`, and starts the game's ModuleScripts and LocalScripts again (`Network::set_client_scripts`; the same game version loads them at the same IDs). Scripts inside objects (G2) that the replica doesn't have at their IDs, such as templates in ServerStorage, only give their code (`ScriptRuntime::know_code`), and those the server placed (a clone of a template) start with it then or when they arrive (`docs/project/world.md`). `PROTOCOL_VERSION` 11 added the scripts' `SourceFile` property. From then on only LocalScripts run there; Scripts given to `start_script` are skipped.
- **Streaming** (Phase 80): with `Workspace.StreamingEnabled` on, each player gets only what's within their radius, a unit at a time, and what leaves it is removed from their device ([streaming.md](streaming.md)).
- **Each frame**, in network send, `Replicator::frame` compares the world with what it last sent and sends `Update`: made Instances, changed names, parents, properties, attributes and tags, and Instances destroyed, taken out of the game or moved into a server-only service. It's reliable, with the server's clock (`time`). Only an Instance whose `revision_without_motion` changed is compared (a part that only moved isn't: its motion goes by `motion`, below), and it's compared in place, copying only what differs (roadmap M7). A made Instance (in a snapshot too) carries only the properties that differ from its class's defaults, since the replica makes it with those; Metalness and Roughness go along with a Material that isn't the default, because setting the Material resets them. Instance properties are applied last, so they can name an Instance later in the update. Comparing, rather than reading `core`'s change records, means nothing is missed though the scripts take those records first.
- **Runtime IK** (Phase 79): an `IKControl`'s `Weight` and `Target` are Instance properties, so they replicate like any other (test: `an_ikcontrols_weight_and_target_a_server_script_sets_reach_every_device`); each device solves IK and foot placement itself.
- **Animators** (Phase 78): an Animator's parameters and layer weights live beside the Instances (`core::AnimatorState`), so each update carries those that changed (`Update::animators`, `WireAnimator`; all of them in a snapshot), applied after the Instances. Bools and Numbers go when they change, a Trigger only when it's set (each device uses up its own), and a layer weight as where it's heading and the seconds of fade left, so each device fades it itself. Protocol 8. Test: `animator_parameters_and_layer_weights_a_server_script_sets_reach_every_device`.
- **Motion** (`motion.rs`): a BasePart's `Position`, `Orientation`, `AssemblyLinearVelocity` and `AssemblyAngularVelocity` aren't in updates once the part is on a device. Each frame each player's `MotionSender` (which re-reads a part only when its `Instance::motion_revision` changed) adds to every moved part's priority (how far it is from what they have, times nearness to their character: 1 / (1 + distance / 64)) and sends the highest first while their budget lasts (`MOTION_BUDGET`, 24 000 bytes a second, saved up for at most a quarter second). A part is 32 bytes: its network ID, its position to 1/128 stud, each angle to 360/65536°, and its velocity to 1/32 stud a second, in packets under 1000 bytes on the unreliable channel. A part still for `SETTLE_TIME` (0.2 s) is sent once more, exactly, in a reliable update, so a lost packet never leaves it elsewhere. 200 moving crates stay under 32 000 bytes a second per player (`two_hundred_moving_crates_stay_under_the_bandwidth_budget_per_client`).
- **Smoothing**: a player's device shows parts `DELAY` (0.1 s) behind the newest motion it has, blending the two states around that moment (angles the short way round), with its clock drifting toward the server's. A part that starts moving after standing still starts from where it stood. A reliable update that places a part (made, or settled) makes older motion stale.
- **Levels**: an update carries `LevelService`'s level and the added ones (with their Models' IDs) when they change, and a snapshot always does, so a player who joins mid-game has the same added levels. When the server loads another level, `LevelLoaded` fires on the players' devices and their loading screen shows (`ScriptRuntime::follow_levels`).
- **A device's own changes** to its replica stay on it, until the server changes the same thing.
- **A device following a server** (`axcenity-player --join`, or `NetworkService:Join`) doesn't step Humanoids, players, agents, prompts, tools, health or touches: the server does. It moves only its own character (below), and steps physics only for an assembly the server gave it, with every other unanchored part held still (`Physics::set_held`, `Network::held_parts`). After leaving, it keeps the last world without the other players.

## Characters and network ownership

Phase 66 (`ownership.rs` in `net`, `ownership.rs` in `script`).

- **Players' characters.** A player who joins from another device gets their first character from `step_players`, as the local player does (the dedicated server now runs `step_players` first in its frame). Each device's controllers move only its own player's character (`Controllers::set_players` with `Network::other_characters`); the others' are moved by their devices, and the host's physics holds them still.
- **Own character.** Each frame a joined device sends its character's parts (the ones that changed; all of them every half second), whether Run is held (`Network::set_running`) and the seat it sits in, on the unreliable channel (`Owned`, tag `O`). The motion the server sends never moves those parts on that device.
- **The server's check** (`CharacterCheck`): the character's root part (PrimaryPart, else HumanoidRootPart, else its first part) may go across the ground as far as its controller's `WalkSpeed` (or `RunSpeed` while running or in Run) allows, 15% faster for packets that arrive bunched together, with a quarter second saved up plus 2 studs; and rise as far as `JumpHeight` launches it. More than 30 studs at once (`TELEPORT_DISTANCE`) is always refused. Movement under 1/64 stud (`ROUNDING`, the wire's rounding of positions to 1/128 stud) costs nothing, so a character standing still is never moved back; the first update has a full quarter second saved up; and falling never counts toward the 30 studs (only across and up do), since a character falls faster the longer it falls (MP1's bots walked off maps and were moved back every frame). A Seated character or a custom `Movement` is only checked for teleports. What passes goes into the server's world (the other players see it by motion, smoothed); what fails stays where the server had it, and the device gets `Correction` with where that is ("The server moved your character back." in its log). A server Script that moves the character (a respawn, `PivotTo`) sends a correction too. A modified client moving at twice `WalkSpeed` gets about 15% more than `WalkSpeed` (`a_modified_client_that_moves_at_twice_walk_speed_is_pulled_back_by_the_server`). A character standing on a part a SplineFollower moves (Phase 73) has as far as that part went since the last update taken off its movement first, so a lift faster than `WalkSpeed` carries it without corrections ([splines.md](splines.md)).
- **Seats.** The seat a device says its character sits in becomes the seat's `Occupant` on the server, so Scripts see who sits where.
- **Assemblies.** `SetNetworkOwner`, `SetNetworkOwnershipAuto` and the driver of a VehicleSeat give an unanchored assembly to a player (`ScriptRuntime::owned_parts`). The server tells each device which parts it owns (`Ownership`, reliable). The owner simulates them (its VehicleSeat's `Throttle` and `Steer` drive the car at once) and sends them with its character; the server holds them still in its physics and puts them where the owner says, unless that's more than 60 studs from where they were. A server's own player owns nothing remotely: the host simulates it.

## Lag compensation

Phase 81 (`script/src/lag.rs`, `physics::raycast_rewound`). A player sees the server's world late: an update takes half their round trip to arrive, and their device shows parts `DELAY` (0.1 s) behind the newest motion it has. By the time their shot reaches the server, a moving target has moved on.

- **History.** Each frame a hosting `Network::send` calls `ScriptRuntime::record_lag` with the server's clock and, for each player on another device, their round trip (renet's measure) plus `DELAY`, capped at `MAX_REWIND` (1 s). `LagHistory` notes where each part that moved is (only parts whose `motion_revision` changed; it catches up with the Workspace through `World::workspace_moves_since`) and keeps a second of poses per moving part. A part that hasn't moved for a second has no track, so a big still world costs nothing. The host's own player is never compensated.
- **Who's compensated.** A server `workspace:Raycast` with `RaycastParams.CompensateFor = player`, or one made in the handler of a RemoteEvent inside a Tool with `LagCompensated` on (until the handler first waits), tests moving parts where they were that long ago, between the two recorded poses around that moment (angles the short way round). The shooter's own character is tested where it is now. Spherecast, Blockcast, Shapecast and the overlap queries aren't compensated.
- **Proof.** `lag_tests::a_shot_at_a_moving_part_hits_where_the_player_saw_it_only_when_compensated`: over 150 ms each way, a player aims at a 4-stud target moving 10 studs a second; the compensated ray hits it, the same ray uncompensated misses, and the Tool handler's ray misses again after a `task.wait()`.
- `Tool.LagCompensated` is a new class default, so the network protocol is 12.

## Replays

Phase 81 (`net/src/replay.rs`, `script/src/replay.rs`, `player/src/replay_view.rs`). A replay is one device's world as replication shows it, frame by frame: what a player who joined at the start would have been sent, with every moved part's exact pose (f32, not motion's quantized one). Nothing is simulated again on playback, so a frame looks the same each time and on any machine, without the cross-machine determinism the development policy rules out. Single-player records the same way, since its world is a listen server's.

- **Scripts** (`game:GetService("ReplayService")`, both sides): `StartRecording()`, `StopRecording(name)` (saved as `<name>.replay` in the player's data folder under `replays`, a server's beside its saves; names are 1 to 64 letters, digits, spaces, `-` or `_`), `IsRecording`, `BufferSeconds` (0 off, at most 60) and `PlayBuffer(player?)`. Like `NetworkService`, the calls queue `ReplayRequest`s; `Network::send` does them and then notes the frame (`Replays`), so recording costs the device one more `Replicator::frame` and a pass over its parts' motion revisions a frame.
- **Recorder.** The first frame and one every `KEYFRAME_SECONDS` (10) carry a whole snapshot as well, so playback can jump. A buffer keyframes every `BufferSeconds` and keeps only the frames from the last keyframe before that many seconds ago.
- **File.** `AXREPLAY`, the format's version (`REPLAY_VERSION`, 1), then the `Replay` in postcard: the game's name and version, the network protocol, and the frames. A file from another format or protocol is refused with why.
- **Playback** (`Playback`): a keyframe rebuilt in `World::empty_replica` with the game's own Terrain landscapes (as a joining device does), then each frame's update and poses in order. `seek` goes from the keyframe before the moment when it's behind or a keyframe is nearer, else forward.
- **Watching.** `axcenity-player --replay <file> <game>` shows it instead of playing (no scripts start): Space pauses, Left and Right jump 5 s, Up and Down set ¼× to 4×, Return goes back to the start, Tab follows the next player through their character's Head (`eyes_of`), then the fly camera again; a timeline runs along the bottom. `PlayBuffer` shows the buffer over the live game the same way from the next frame, following the given player, until its last frame or Escape (`Network::take_buffer_play`).
- **Proof.** `replay_tests::a_two_minute_match_plays_back_as_it_was_and_the_same_each_time`: a server and two players for two minutes of sliding, spinning, appearing and recoloured parts; the replay, saved and read back, shows the server's world exactly at five moments, played through, jumped to in either order, and stepped at 2×. `a_kill_cam_shows_the_last_five_seconds_from_the_killers_eyes`: a victim's device keeps 5 s and its kill cam shows the killer's view exactly as that device showed it, frame by frame.
- The editor's Play records too, but saves nothing and shows no kill cam: it keeps the newest four replays in memory and logs "Recorded the replay".
- **Not yet:** animation poses (characters show their parts' places but not skinned meshes' bones), sounds, particles and screen GUIs aren't recorded; the timeline isn't clickable.

## Remote calls

RemoteEvents and RemoteFunctions use the same `Message`s as on one device. The runtime keeps a message for another device (to a Player who joined from elsewhere, or from a replica to the server) in `take_remote_messages`; `Network::send` sends it as `Remote` (`wire::WireMessage`: Instances as network IDs, Lua strings as bytes). The receiver hands it to `receive_remote_messages`, and it fires in the next frame's script step.

- `FireClient`, `FireAllClients` (every Player, wherever they play) and `InvokeClient` reach players on other devices; `FireServer` and `InvokeServer` reach the server.
- Ability activations (Phase 76) ride the same path as `MessageKind::Activate` naming the Ability; the host accepts one only for an Ability, and the server serves it only for the player who holds it, checking cost, cooldown and tags itself ([../scripting/api-abilities.md](../scripting/api-abilities.md)). Protocol 7.
- The host takes a message from player *n* as theirs: its Player is the connection's, never what the message says. It must name a RemoteEvent or RemoteFunction outside the server-only services, or it's dropped. An Instance argument a player can't see (server-only, or the device's own) arrives as nil, both ways.

## Hosting and joining

- `axcenity-player --replay <file> <game>` watches a replay ([Replays](#replays)).
- `axcenity-player --host [port] <game>` runs a listen server (port 47800 if not given). `--join address:port` joins one. `--password <text>` sets a host's password, or gives it when joining. A port that's taken, or an address that can't be looked up, stops the player with the reason.
- `axcenity-server <game> [--port <port>] [--password <text>] [--max-players <n>] [--stats <seconds>]` loads a project folder or `.axgame` and runs its Scripts (and the ModuleScripts they require, never LocalScripts) with physics at 60 Hz, with no window, audio or GPU and no player of its own (`ScriptRuntime::set_dedicated`). Its frame is network receive, scripts, `Stepped`, physics, touches, breaks, health, `Heartbeat`, network send. Characters, agents and animation belong to players' devices. On Linux it needs no display; `script` still links `audio`'s library, which needs ALSA's `libasound` installed (not a sound device). `tests/headless.rs` runs the real binary with `DISPLAY` and `WAYLAND_DISPLAY` unset.
- The player prints who joined and left, and every refusal and failure, to stderr (`Network::take_log`).
- The editor's Play doesn't host or join on the network: `Host` and `Join` fire `ConnectionFailed` with a reason, and `FindLanGames` returns an empty list. It plays several clients in the editor instead (below).

## Reconnecting

Multiplayer readiness MP2. A device that joined over UDP (`--join`, `NetworkService:Join`) and loses its connection (the server crashed or stopped, or the network failed: `SessionEvent::Lost`, not `Failed`, which is a join that never got in) keeps its world as it was and tries to rejoin the same address for 60 seconds (`net::REJOIN_SECONDS`; `Network::set_rejoin_seconds`, 0 to give up at once), 1, 2, 4 and then every 8 seconds. The log says "Lost the connection to the server: … Trying to rejoin for 60 seconds." and then "Rejoined the game."; only when the time runs out does `ConnectionFailed` fire, with "Lost the connection to the server and couldn't rejoin: …", and the other players leave `Players`. Each rejoin is a join: a new Player (same name, same UserId, so the server's saved data for them comes back), `PlayerAdded` on the server, a new `Snapshot`, and the device's LocalScripts start again on it. Hosts start their physics, characters and Animators again whenever `Network::follows` changes. A joined device notices a server that went silent when netcode's 15 seconds pass, so a crashed server that starts again on the same port has its players back about 20 to 30 seconds after it went down.

The rejoin Hello carries the key the last Welcome gave. A server that still holds that key's connection (it hasn't noticed the device is gone, for up to 15 seconds) doesn't count it against `MaxPlayers`, drops it once the new one is let in (`Left`, then `Joined`) and gives the player their name back rather than `Bot1`'s `Bot12`. A wrong key is just a new player. The loopback and the editor's Play don't rejoin.

## Play with several clients

Beside Play and Stop, the ribbon's Game group has **Clients** (1 to 8, `play::multi::MAX_CLIENTS`; set before Play) and **Network** (latency, jitter and packet loss, which apply at once, Phase 67). With one client, Play is as before. With more (`play::Play`, `editor/src/play/multi.rs`):

- The first device is the server, with its player on it (a listen server, like `--host`). Each other client is a Play `Session` of its own with its own world (`Session::start` with no scripts, then `join_through` the first's in-memory loopback with the game's LocalScripts and ModuleScripts), so it follows the server as `--join` does: RemoteEvents, replication, motion, smoothing and its own character all go over the loopback, through the emulated network. Client *n* is named `Player<n>` (the host greets connections in the order they came) and has the UserId of the first plus *n* − 1.
- A view menu in the Game group shows **Server** (the server's world from the fly camera, taking no input) or a client by its player's name. The viewport, Explorer and Properties show that device's world, and the shown client gets the keys and mouse; the others stand still. Only the first device is heard.
- Every device runs each editor frame, the server first. Output lines from a client end with its player's name, "(Player2)". Breakpoints, live script reloads (LocalScripts and modules on clients) and changed assets reach every device; Keep at Stop keeps the server's world.
- The Profiler's **Network** section lists each client's connection from the server: ping, bytes sent and received a second, packet loss (renet's numbers) and how many Instances their world holds (`Play::network_stats`).
- `a_remote_event_fired_by_client_2_reaches_the_server_with_their_player_and_fire_all_clients_reaches_all_three` and `with_10_percent_packet_loss_play_stays_usable_and_the_network_section_shows_the_loss` (`editor/src/play/tests.rs`) check it.

## Scale and soak testing

Multiplayer readiness MP1 ([research/multiplayer-readiness.md](../research/multiplayer-readiness.md)). Bots are players' devices as their own processes over real UDP, so a server can be loaded by players on other machines (G13).

- **`axcenity-bots <game> --join <address:port> --count <n>`** (`crates/server/src/bots/`): each bot loads the same game (the handshake checks version and class defaults), joins with the name `Bot<n>` (`Network::set_join_name`) and a UserId counting up from `--user-id`, follows the server's world as a replica (`Sim::follow_server`), runs the game's LocalScripts (`--no-scripts` skips them) and runs the player's frame steps of the shared schedule with nothing drawn or heard. Its made-up input walks forward, turns every 1–4 s, runs 30% of the time, sometimes jumps and turns back once it's `--roam` studs (30) from where it spawned (`--idle` stands still), so the server checks it as it would a person. Bots run on `--threads` threads at 60 frames a second, started `--stagger` ms apart (100). Every `--report` seconds (5) a line sums them up: how many are in and their join times, round trips (p50, p95, max), loss, bytes a second each way per bot, corrections (`Network::corrections`, times the server moved a character back), script errors and the bots' own frame times (if those near 16 ms the bots, not the server, are the limit). `--report-file` writes each as a JSON line and a final one with `"summary": true`; the process fails if a bot never joined. It stops after `--seconds` (60; 0 runs until stopped).
- **`axcenity-server --stats <seconds>`** prints that often: players, frames a second, frame time p50, p95 and max (the work, not the wait), round trips, loss and bytes a second each way (renet's numbers); `--stats-file` writes JSON lines. **`--max-players <n>`** takes up to n players whatever the game's `Players.MaxPlayers` says.
- **`scripts/net-scale.py`**: `run <game> --bots 32` starts the server and bot processes on this machine and writes `target/net-scale/<time>-run-<machine>/report.md`; `join <game> <address> --bots 16` adds bots from another machine; `report <folders>` combines them. Standard library only.
- **Operational tests** (MP2): `--churn <s>` has each bot leave after 0.75 to 1.25 times that and a new install (a new UserId, `--user-id` plus 100,000 a generation) join in its place; the summary counts them (`churned`). `--flood silent|junk|spam|deep` opens bare connections instead of bots: `silent` never sends a join request (the server drops it after the 10-second handshake, `HANDSHAKE_TIMEOUT`), `junk` sends bytes that aren't one (refused and dropped), `spam` joins and then sends about 60 KB of junk a frame on both channels, `deep` joins and sends remote messages with tables nested 200,000 deep ([Validation](#validation)); the process fails if the server kept a silent or junk connection. The server's `--stats` lines also give its Instance count and Lua memory, for leaks. Hosts log with `net::LOG_FILTER` (`warn,renetcode=off`) unless `RUST_LOG` is set: renetcode logs an error for every packet it can't read, which a restarted server's old clients send by the hundred.
- What they found: rejoining after `kill -9` and a restart works with saves kept; churn leaves the server's Instances where they started. Two `spam` connections at renet's full rate (about 3.5 MB/s each, which the server reads at 59 frames a second) cost other players on the same machine about a fifth of their packets, since the junk fills the server's socket between frames; since MP3 they're kicked in about 3 seconds. Silent connections hold the spare slots (`MaxPlayers` plus 4) for up to 10 seconds; MP4's connect tokens stop strangers from opening them.
- Tests: `crates/server/tests/operations.rs` (a server killed and started again: three bots rejoin and each one's saved visit count goes from 1 to 2; four bots churning for 16 s leave the server's Instances and Lua memory where they started; six silent connections are dropped after the handshake time and then players get in; junk is refused; deep-table and spam connections are kicked while players play on and the server stays above 50 frames a second); `net` `rejoin_tests` (a rejoin with the key replaces the stale connection, even when the game is full; a wrong key counts as a new player; a lost connection is `Lost`, a failed join `Failed`); `crates/server/tests/bots.rs` (12 bots in two processes join over UDP, walk and leave; bots past `--max-players` are refused with the reason); `net` `character_tests::players_who_spawn_on_one_spawn_location_stand_apart_and_are_never_moved_back`.

## Chat

`game:GetService("TextChatService")` (a service of `game`, saved with the world, Phase 67; `script/src/chat.rs`):

- `SendMessage(text)` (LocalScripts) and the chat window's Enter send a message as the device's player. A joined device sends it to the server (`Message::Chat`); a host or single-player takes it at once.
- On the server, `OnIncomingMessage = function(message)` gets `message.Text` and `message.Player` and returns the text to send on (changed or not), or nil to drop it. It must return at once; an error keeps the message.
- `DisplaySystemMessage(text)` from a Script goes to every device with no player; from a LocalScript only to its own.
- The server sends each message to every device (`Message::ChatLine`), and each fires `MessageReceived(message)` on both sides there (nil `Player` for a system message), then shows it in the chat window ([../ui.md](../ui.md)). Messages are trimmed and cut at 200 characters, whatever a modified client sends.
- `ChatEnabled` (a property, so the server's value reaches every device) off hides the window and `/` doesn't open it.

## Console commands

A line typed in a joined player's Developer Console for the server goes as `Message::Console`; the host runs it as one of its Scripts' `ConsoleService` commands when the player's `UserId` is in `AllowedUserIds`, and logs it either way ([../developer-console.md](../developer-console.md)).

## Kicking

`player:Kick(reason?)` (Scripts only) takes a player out: a player on another device gets `Refused` with the reason (their `ConnectionFailed` fires with it, "You were kicked from the game." without one), the connection closes a second later and `PlayerRemoving` fires on the server. The server's log says "Kicked Player2: reason". Kicking the player on the host's own device ends the game: the player quits with the reason on stderr, and the editor stops Play with it in Output (`Network::take_kicked`).

## Validation

Multiplayer readiness MP3 (decision D4 of [research/multiplayer-readiness.md](../research/multiplayer-readiness.md)). A modified client can send anything, so the host holds each player's device to what a game client sends.

- **Budgets** (`net::limits`): each player has a token bucket per kind of message, full when they join: every byte on both channels (256 KB/s, bursts of 1 MiB), remote calls (240 a second, 600 at once), chat (2, 8), console lines (5, 20), `StreamAround` requests (10, 30) and unreliable packets (180, 360). A walking player sends about 13 KB/s and a few packets a frame, so a game never meets one. A message over its budget is dropped before it's read (`Host::update`).
- **Unreadable and wrong-way messages** are dropped: bytes that aren't a message, a message only the server sends (`Welcome`, `Left`, …), and a remote message with tables nested more than 32 deep (`MAX_TABLE_DEPTH`, refused as postcard reads it, `wire::nested_table`; a script sending one gets an error). Before MP3 a 600 KB message of tables nested 200,000 deep overflowed the server's stack.
- **Flags**: each drop flags the player (`SessionEvent::Flagged`), at most once a second for each reason. The host logs "Player2 was flagged: their device …", fires `Players.PlayerFlagged(player, reason)` in Scripts, and kicks a player flagged `net::KICK_FLAGS` (5) times in a minute, with the reason ("Your device sent more data than a game client does."). `axcenity-server --kick-flags <n>` changes it (0 never kicks; `Network::set_kick_flags`), and `--stats` lines count flags. A device spamming junk at renet's full rate is kicked in about 3 seconds; until then its junk fills the server's socket between frames and the other players lose some packets.
- Tests: `net` `limits` (buckets), `validation_tests` (200,000-deep tables flagged unreadable and the host carries on; chat past its budget and server-only messages flagged once each), `multiplayer_tests` (a client firing a RemoteEvent 600 times a second is held to the budget, flagged and kicked; with `--kick-flags 0` it stays), `wire_tests` (decoding stops at 33 deep), `script` `client_server_tests` (sending 33 deep is an error), and `crates/server/tests/operations.rs` (`--flood deep` and `--flood spam` connections kicked while two players play on).

## LAN discovery

A host answers on UDP port 47801 (`DISCOVERY_PORT`, `discovery.rs`). `FindLanGames` broadcasts a question to `255.255.255.255:47801` and to `127.0.0.1:47801` (a broadcast may not come back to the computer that sent it), asks again every 0.3 s, and after one second lists the hosts of the same game, with their version, address, players, `MaxPlayers` and whether they need a password. A host found at two addresses is listed once, by its network address. Only the first host on a computer gets the discovery port; another still takes joins by address and logs a warning. Tests: `find_lan_games_lists_a_game_hosted_on_this_computer`, and `a_search_from_the_network_lists_the_game_at_its_network_address_and_joins_it` (a question arriving at this computer's network address, as one from another computer does). Two real computers are checked by hand with the ignored `a_game_hosted_on_another_computer_shows_in_a_lan_search` ([development.md](../development.md)).

## Lua and blocks

`game:GetService("NetworkService")` (also `game.NetworkService`, on both sides):

- `Host(port?, password?)`, `Join(address, password?)`, `Disconnect()`.
- `FindLanGames()` pauses the script and returns `{ Name, Version, Address, Players, MaxPlayers, HasPassword }` tables.
- `ConnectionFailed(reason)`.

Blocks (in **More**): "host game on port *n*", "join game at *address*", "leave game", and the event "when connection fails" (`NetworkService:Host(n)`, `NetworkService:Join(address)`, `NetworkService:Disconnect()`, `NetworkService.ConnectionFailed:Connect(function(reason) … end)`).

## Frame order

Network receive comes first in the frame: `NetworkService` requests from last frame, then what arrived (roster, the world, remote messages). Network send (`Network::send(world, scripts)`) comes after the frame's scripts, physics and UI layout, just before rendering: the world's changes, then remote messages, so a message never names an Instance its receiver doesn't have yet. See [frame-loop.md](frame-loop.md).
