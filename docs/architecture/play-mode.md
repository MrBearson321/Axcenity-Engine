# Play mode

What Play and Stop do in the editor, including audio during Play.

Play runs in-process on a **deep copy** of the edit world, and Stop drops the copy. Before Play: autosave. During Play: the Lua watchdog stops a script that runs 3 seconds without pausing (the editor freezes that long, then the error appears in Output and the game carries on; see `docs/scripting/execution.md`), and Rust panics are caught at the Play boundary and reported to the Output panel.

A project's own loading screen (a ScreenGui chosen in File > Build Game) shows during Play as in the built game: `Session::start` takes the project's `LoadingScreen`, and the viewport draws `Session::loading_screen` over the other UI. The Axcenity splash is not shown in Play.

### Decided in Phase 12

- **Controls**: **▶ Play** and **■ Stop** at the left of the toolbar, only one enabled at a time, and **F5** / **Shift+F5** as in Studio (chosen by the developer). A green "Playing" label shows at the end of the toolbar.
- **The copy**: `World` derives `Clone`. The arena has no pointers, so a clone is a full deep copy where every Instance keeps its `InstanceId`. The selection and open Explorer branches carry over to the Play world and back. A fresh `ScriptRuntime` and `Physics` are made for each Play, so nothing (connections, waiting threads, bodies) survives into the next one. After Stop, a selection that only existed in the game is cleared.
- **Levels** (Phase 48): Play runs the open level, and `LevelService` gets every level (the others read from their files after the autosave); the Levels panel's **Play from start level** starts it in the start level instead. A level loaded during Play shows the loading screen again. See `docs/project/levels.md`.
- **Autosave** (chosen by the developer): Play saves `world.json` first **only if there are unsaved changes**; otherwise the file already matches, and Play doesn't rewrite it. If saving fails, Play doesn't start and Output says why. The undo history is kept across Play.
- **Scripts** are read again from their files at Play (`project::read_script`), so Play runs exactly what's on disk (Play's autosave writes unsaved script tabs first). A file that can't be read is reported and left out; the rest still run. During Play, a script whose file changes (a tab's Save, or another editor) runs again in place, and the rest of the game carries on: `docs/editor/scripts.md` (Live scripts).
- **Read-only during Play** (chosen by the developer): the Explorer, Properties and viewport show the live game world. You can select and inspect (values update every frame), open and close Explorer branches, and move the camera. The transform tools, dragging, inserting, the right-click menu, Explorer rename, undo and redo are all off. File > Save still saves the edit world. Opening another project stops the game.
- **Except Properties** (changed in Phase 16, chosen by the developer, like Studio): during Play the Properties panel edits the game's world (`Session::world_mut`), so the game's scripts see the change (`Changed` fires at the next frame). These edits make no undo step, don't count as unsaved, and are gone at Stop, unless kept. The panel says so above the values.
- **Keeping Play edits** (unified Phase 24; `play/kept.rs`, `EditorApp::keep_play_edits`): each value edited in Properties during Play gets a **Keep** pin beside its name (`EditorApp::change_in_play` notes which values an edit changed). Right-clicking an object in the Explorer during Play offers **Keep changes to <name>**, which keeps the whole object: every value that differs from the edit world at Stop, whatever changed it (Properties, a script or physics), and pins its edited values. Unpinning one of them goes back to keeping only the pinned values. At Stop, the kept values, as the game has them then, are copied into the edit world as one undo step ("Keep Play changes to Pad"), which counts as unsaved; Output says how many. Values that weren't kept are discarded as before, and kept objects made during Play are gone with the game (Output says so).
- **Frame**: each editor frame during Play runs the frame steps with the real time since the last one (capped at 0.1 s, like the player), then draws; the editor repaints continuously while playing. When a `ThirdPersonController` or `FirstPersonController` in the Workspace has a body, Play follows it (from behind, zoomed by the wheel over the viewport, or at its eyes) and WASD or the arrows walk or run it, Space jumps and C crouches (right-drag orbits or looks). The fly camera is left where it was and returns on Stop. With no such controller, the fly camera still moves. A LocalScript's CameraType other than Custom (Phase 31) is drawn the same way: the viewport shows `Session::shown_camera`, the fly camera neither moves nor flies meanwhile, and Stop shows it where it was. See `docs/scripting/api-character.md`.
- **Audio** (Phase 29): script contexts queue `SoundAction`s (`Play` restarts, `Stop` resets); the host passes them to the session's `GameAudio` after script steps, which also syncs every Sound each frame: `Playing` pauses, resumes and starts (so a Sound saved playing starts with the game), and `Volume`, `PlaybackSpeed` and `Looped` apply live. A Sound with `Spatial` on is an emitter on a Kira spatial track: the listener is the camera (including a LocalScript's move, applied before the frame is drawn), and the emitter is the nearest ancestor `Part`, `MeshPart` or `Terrain`, or `Sound.Position` otherwise. Kira pans it in stereo; the engine sets its track's volume each frame from its `RollOffMode` curve between `RollOffMinDistance` and `RollOffMaxDistance` (`core::sound::RollOff`, roadmap G8), gliding over 60 ms. Occlusion: before `GameAudio::update`, the host steps `Sim::occlusion` (`sim::Occlusion`), which casts rays from the listener to at most 8 playing spatial Sounds in earshot a frame, in turn (at most 6 rays each), counting anchored solid parts and Terrain up to 3, and passes the counts on with `GameAudio::set_walls`. Each wall halves the Sound and lowers the low-pass on its track (`core::sound::muffle`). `SoundService.Occlusion` off clears them. `Spatial` defaults off, so a sound with no position stays the same in both ears. Sounds that played to their end come back from `update`, and the host fires their `Ended` (`ScriptRuntime::fire_sounds_ended`). The audio output opens only when a sound first plays, and a file that can't be played is reported once, not every frame. Dropping editor Play drops its `GameAudio` and silences its sounds; the player keeps its own until the game exits. Outside Play, the Properties panel's ▶ next to `SoundId` previews a Sound with its own short-lived engine (stopped by ■, or by Play); a spatial preview follows the viewport camera.
- **Saves** (unified Phase 17): `SaveService` writes slots to the player's data for the game, the same folder as the built game (`docs/architecture/saves.md`), never the project. Stop still drops the Play world, so a save or load during Play leaves the edit world and project files as they were; the next Play can load the slot.
- **Output**: `print` lines are Info, script errors (`path:line: message`) are Error.
- **Breakpoints** (v2 Phase 4): the editor's Play runtime has the debugger on (`ScriptRuntime::enable_debugger`, see `docs/scripting/execution.md`) with the script tabs' breakpoints; the player never turns it on. When a script reaches a breakpoint line, before it runs, the game **pauses**: `Session::frame` stops there and does nothing more until Continue (no scripts, physics, animation or events; sounds already playing carry on), and the editor stops repainting continuously. Output says where, the script's tab opens at that line with an arrow and an amber background, and a panel under the code lists each script function on the paused call stack with its locals (the breakpoint's own open). The header badge turns amber "Paused", and Play becomes **Continue** (button, the panel's Continue, or **F5**). Continue runs the script on from that line, then whatever waited for it, and the next frame's time starts fresh. A breakpoint hit again pauses again. Clearing the breakpoint Play is paused at continues (not when a step or an error paused it); Stop ends the game as usual. A Console command typed while paused waits for Continue (it says so). A breakpoint in a script's first run pauses during Play's start, and the scripts after it start on Continue. Breakpoints changed during Play apply at once.
- **Stepping, errors and watches** (roadmap G6): while paused, **Step Over** (F10) runs the line and pauses at the next one in that function (or where it returns to), **Step Into** (F11) pauses at the next line run, inside a function the line calls too (in another script, such as a ModuleScript's), and **Step Out** (Shift+F11) pauses once the function returns. A call that is the last thing on its line returns to the next line. The panel has the four buttons; a step pause doesn't print to Output. A step that waits (`task.wait`) lets the game run until the script carries on, then pauses there; another coroutine runs through a step without pausing, and a breakpoint it reaches first pauses there and ends the step. With **Pause on errors** (the ribbon's Clients group, or the command palette; off by default, and it applies at once during Play), a script error pauses Play at the failed line with that script's call stack and locals, and its message in red; that script can't run on, so only Continue is offered. The panel lists each frame's upvalues ("From outside this function", such as a script's own locals used in it) under its locals, and **Watches**: expressions typed in its box, worked out in the innermost frame at each pause (`Play::evaluate`), seeing its locals, upvalues and globals. Watches can call functions and change things, under the watchdog, and can't wait; they are kept until the editor closes. With several clients, a step steps the device whose pause is shown.
- **Visual-debug overlays** (v2 Phase 6): Viewport > Overlays (also the Test tab's Overlays menu and Settings > Viewport) can show collider wireframes, recent `workspace:Raycast` lines, Size boxes, and spatial-sound markers. They draw in edit mode and during Play, do not step physics or change ray results or audio, and are absent from the player and exported games. Terrain collider chunks farther than 200 studs from the camera are hidden. Saved between runs, like Light Cones. **Culling** (graphics Phase 12; not saved) holds frustum culling where the camera is when it goes on (`TextureRenderer::freeze_culling`), so flying away shows what's drawn and what's left out: each item's bounding sphere as a circle, green where drawn and red where culled, and the held view's edges out to 60 studs in yellow (`viewport/overlays.rs::paint_culling`).
- **Mixer** (Phase 52; `mixer.rs`, `app/mixer.rs`): a dockable panel (closed at first; View > Panels opens it beside the Console) lists the SoundGroups as a tree under an **Output** level meter (the whole game's sound; not called Master, which is what most projects name their top SoundGroup). During Play each group's meter shows its peak level (falling 30 dB a second), and Mute and Solo buttons change what's heard (`GameAudio::set_monitor`; solo keeps a soloed group, the groups inside it and the groups it goes out through, and silences Sounds played straight into those outer groups). They never change the world, and Stop clears them. Outside Play it shows the edit world's groups with empty meters.
- **Profiler** (v2 Phase 5; `profiler.rs`): a dockable panel (a tab beside the Console and Assets; View > Panels) shows what the game costs, averaged over the last 120 frames (about two seconds), in three tabs. **Game**: frame rate, CPU time (the game frame plus drawing it, with the peak) and the viewport's GPU time; the editor process's memory (`memory-stats`, asked every 15 frames) and both Lua heaps; physics (CPU, fixed steps per frame, bodies); audio (CPU, sounds playing; Kira mixes on its own thread, which isn't counted); scripts and animation; **Posing by thread** (unified Phase 93: how long each thread spent posing skeletons, the main thread and the animation pool's `Thread 1`, `Thread 2`…, shown only when something was posed; `PosingThreads`, from `Animators::thread_times`); and the network. **Graphics** (graphics Phase 37): the viewport's `RenderStats`, described in `docs/rendering/performance.md`. **Memory** (roadmap G7): the editor process, what the game holds (counted) and the GPU's total; then the game by kind: Lua, Instances, Models (triangles, levels of detail, hulls), Textures (decoded pixels and cooked mip levels, those inside models too, each image once), Sky and probes (skies, probe bakes, color lookups, palettes), Sounds (decoded samples) and Physics (rapier's bodies and colliders, mesh and hull shapes included), each with how many; then the 12 classes whose Instances hold the most, with the rest counted. `Session::memory` builds it (`Sim::memory`, from `World::memory`, `Assets::memory` and `Physics::memory` in `core::memory`'s types, plus `GameAudio::memory`) every 15 frames while live, since it walks every Instance and cache. The numbers estimate each part's heap, so they add up to less than the process, which also holds the editor, fonts and the allocator's spare room. A bar graph shows each recent frame's CPU time against a 60 fps line. The numbers are what the frame loop already passes through: `Session::frame` reads the clock between its steps (`Session::cost`, `Session::load`), and the viewport times building the draw list and recording the GPU's work and adds `TextureRenderer::stats`. They're taken whether or not the panel is open; the panel only reads them, so closing it changes nothing. Readings start fresh at Play, skip frames paused at a breakpoint, and freeze at Stop (however Play ends), marked "Stopped: last Play's readings". GPU time shows "not available on this GPU" where the adapter can't take timestamps. The player has no profiler.
- **Run** (roadmap G14, like Studio's Run; `PlaySettings::run`, `Session::begin`): **Run** beside Play (the ribbon's Game group, **F8**, the `run` Console command or the command palette) starts the game as Play does (autosave, a copy of the world, Stop and kept edits the same) but as a server with no player of its own, the way `axcenity-server` runs it (`ScriptRuntime::set_dedicated`): Scripts, physics, animation and sounds run; no Player joins, so `PlayerAdded` doesn't fire and no character spawns (one placed in the Workspace stays where it is, moved only by physics); LocalScripts don't start; the loading screen doesn't show; and the view is the fly camera, which flies as in edit mode, with no input for the game (the server view, `PlayView::Server`). The Clients setting is ignored (one device), the view menu offers only Server, and the badge reads **Running**. F5 is still Play. The MCP `game_run` tool always plays with a player. Test: `run_steps_scripts_and_physics_with_no_player_local_scripts_or_input`.
- **Several clients** (Phases 64 and 67): the Game group's **Clients** (1–8) and **Network** (latency, jitter, packet loss) settings, the view menu (Server, or each client by name), and the Profiler's Network section: see [networking.md](networking.md), Play with several clients. With one client, Play is as described here.
- **Chat** (Phase 67): `/` over the viewport opens the game's chat window, Enter sends the line and Esc closes it, as in the player ([../ui.md](../ui.md)). Kicking the player here (`Player:Kick`) stops Play, with the reason in Output.
- **Panics** (`catch_unwind` around `Session::start` and `Session::frame`): the session is thrown away, Output shows "The engine crashed during Play: <message>...", and the editor is back in edit mode. The panic's location goes to the terminal (Rust's default panic message). Panics while *drawing* the Play world aren't caught yet. In debug builds, **Debug > Panic during Play** makes the next frame panic, to test this (chosen by the developer); release builds have no Debug menu.
