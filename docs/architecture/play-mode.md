# Play mode

What Play and Stop do in the editor, including audio during Play.

Play runs in-process on a **deep copy** of the edit world, and Stop drops the copy. Before Play: autosave. During Play: the Lua watchdog stops a script that runs 3 seconds without pausing (the editor freezes that long, then the error appears in Output and the game carries on; see `docs/scripting/execution.md`), and Rust panics are caught at the Play boundary and reported to the Output panel.

### Decided in Phase 12

- **Controls**: **▶ Play** and **■ Stop** at the left of the toolbar, only one enabled at a time, and **F5** / **Shift+F5** as in Studio (chosen by the developer). A green "Playing" label shows at the end of the toolbar.
- **The copy**: `World` derives `Clone`. The arena has no pointers, so a clone is a full deep copy where every Instance keeps its `InstanceId`. The selection and open Explorer branches carry over to the Play world and back. A fresh `ScriptRuntime` and `Physics` are made for each Play, so nothing (connections, waiting threads, bodies) survives into the next one. After Stop, a selection that only existed in the game is cleared.
- **Autosave** (chosen by the developer): Play saves `world.json` first **only if there are unsaved changes**; otherwise the file already matches, and Play doesn't rewrite it. If saving fails, Play doesn't start and Output says why. The undo history is kept across Play.
- **Scripts** are read again from their files at Play (`project::read_script`), so Play runs exactly what's on disk (Play's autosave writes unsaved script tabs first). A file that can't be read is reported and left out; the rest still run.
- **Read-only during Play** (chosen by the developer): the Explorer, Properties and viewport show the live game world. You can select and inspect (values update every frame), open and close Explorer branches, and move the camera. The transform tools, dragging, inserting, the right-click menu, Explorer rename, undo and redo are all off. File > Save still saves the edit world. Opening another project stops the game.
- **Except Properties** (changed in Phase 16, chosen by the developer, like Studio): during Play the Properties panel edits the game's world (`Session::world_mut`), so the game's scripts see the change (`Changed` fires at the next frame). These edits make no undo step, don't count as unsaved, and are gone at Stop. The panel says so above the values.
- **Frame**: each editor frame during Play runs the frame steps with the real time since the last one (capped at 0.1 s, like the player), then draws; the editor repaints continuously while playing. When a `ThirdPersonController` in the Workspace has a body, Play follows it and WASD or the arrows walk or run it (right-drag orbits). The fly camera is left where it was and returns on Stop. With no such controller, the fly camera still moves. See `docs/scripting/api-character.md`.
- **Audio** (Phase 29): script contexts queue `SoundAction`s (`Play` restarts, `Stop` resets); the host passes them to the session's `GameAudio` after script steps, which also syncs every Sound each frame: `Playing` pauses, resumes and starts (so a Sound saved playing starts with the game), and `Volume`, `PlaybackSpeed` and `Looped` apply live. A Sound with `Spatial` on is an emitter on a Kira spatial track: the listener is the camera (including a LocalScript's move, applied before the frame is drawn), and the emitter is the nearest ancestor `Part`, `MeshPart` or `Terrain`, or `Sound.Position` otherwise. Kira pans it in stereo and attenuates from full at `RollOffMinDistance` to silent at `RollOffMaxDistance`. `Spatial` defaults off, so a sound with no position stays the same in both ears. Sounds that played to their end come back from `update`, and the host fires their `Ended` (`ScriptRuntime::fire_sounds_ended`). The audio output opens only when a sound first plays, and a file that can't be played is reported once, not every frame. Dropping editor Play drops its `GameAudio` and silences its sounds; the player keeps its own until the game exits. Outside Play, the Properties panel's ▶ next to `SoundId` previews a Sound with its own short-lived engine (stopped by ■, or by Play); a spatial preview follows the viewport camera.
- **Output**: `print` lines are Info, script errors (`path:line: message`) are Error.
- **Breakpoints** (v2 Phase 4): the editor's Play runtime has the debugger on (`ScriptRuntime::enable_debugger`, see `docs/scripting/execution.md`) with the script tabs' breakpoints; the player never turns it on. When a script reaches a breakpoint line, before it runs, the game **pauses**: `Session::frame` stops there and does nothing more until Continue (no scripts, physics, animation or events; sounds already playing carry on), and the editor stops repainting continuously. Output says where, the script's tab opens at that line with an arrow and an amber background, and a panel under the code lists each script function on the paused call stack with its locals (the breakpoint's own open). The header badge turns amber "Paused", and Play becomes **Continue** (button, the panel's Continue, or **F5**). Continue runs the script on from that line, then whatever waited for it, and the next frame's time starts fresh. A breakpoint hit again pauses again. Clearing the breakpoint Play is paused at continues; Stop ends the game as usual. A Console command typed while paused waits for Continue (it says so). A breakpoint in a script's first run pauses during Play's start, and the scripts after it start on Continue. Breakpoints changed during Play apply at once.
- **Visual-debug overlays** (v2 Phase 6): View > Overlays (also the View ribbon tab and Settings > Editor layout) can show collider wireframes, recent `workspace:Raycast` lines, Size boxes, and spatial-sound markers. They draw in edit mode and during Play, do not step physics or change ray results or audio, and are absent from the player and exported games. Terrain collider chunks farther than 200 studs from the camera are hidden. Saved between runs, like Light Cones.
- **Profiler** (v2 Phase 5; `profiler.rs`): a dockable panel (a tab beside the Console and Assets; View > Panels) shows what the game costs, averaged over the last 120 frames (about two seconds): frame rate, CPU time (the game frame plus drawing it, with the peak) and the viewport's GPU time; the editor process's memory (`memory-stats`, asked every 15 frames) and both Lua heaps; rendering (CPU, GPU, draw calls, triangles, items, lights); physics (CPU, fixed steps per frame, bodies); audio (CPU, sounds playing; Kira mixes on its own thread, which isn't counted); and scripts and animation. A bar graph shows each recent frame's CPU time against a 60 fps line. The numbers are what the frame loop already passes through: `Session::frame` reads the clock between its steps (`Session::cost`, `Session::load`), and the viewport times building the draw list and recording the GPU's work and adds `TextureRenderer::stats`. They're taken whether or not the panel is open; the panel only reads them, so closing it changes nothing. Readings start fresh at Play, skip frames paused at a breakpoint, and freeze at Stop (however Play ends), marked "Stopped: last Play's readings". GPU time shows "not available on this GPU" where the adapter can't take timestamps. The player has no profiler.
- **Panics** (`catch_unwind` around `Session::start` and `Session::frame`): the session is thrown away, Output shows "The engine crashed during Play: <message>...", and the editor is back in edit mode. The panic's location goes to the terminal (Rust's default panic message). Panics while *drawing* the Play world aren't caught yet. In debug builds, **Debug > Panic during Play** makes the next frame panic, to test this (chosen by the developer); release builds have no Debug menu.
