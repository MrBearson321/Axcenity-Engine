# Asset files

How model and texture files are read, and what a path is allowed to name.

- The `assets` crate is the asset system: it reads every asset file, only from inside the project folder. A `MeshId`, or a URI inside a model, that is absolute, has a drive or scheme (`C:`, `file:`) or a `..` part is refused (`assets::safe_path`), so a world file or script can't read anything else. `data:` URIs embedded in a model are fine.
- `Assets` is a cheap shared handle (one per open project) that loads each model the first time it's asked for, keeps it, and remembers failures so each is reported once (`take_errors`: the editor shows them in Output, the player prints `error:` lines). The project still loads and runs without the model. The editor's Asset Check (`project::check_assets`) lists missing files, invalid references, import failures, and broken dependencies together without writing the project, and `project::plan_fix` works out a fix for them without writing either; see `docs/editor/assets.md`. `Assets::forget` drops a changed file from the cache, and `forget_failures` lets every failed load be tried again.
- Files are read and decoded with the `Assets` lock released (roadmap M5, `assets/src/loading.rs`): the lock is held only to look a file up and to keep the result, so two files decode at once and asking for something already loaded never waits for a decode. A file is read once however many threads ask; the others wait on its `LoadTicket`, not the lock. A file changed while it's being read (`forget`, `reload`) is read again before anything is kept, and a value handed over meanwhile (`insert`, `put_*`) wins. A reload leaves the last good version in use until the new one is in.
- Two ways to load. `model_blocking` (and `texture`, `material` and the rest) returns the result, waiting for the file if it must; a file still in the queue is read on the calling thread rather than waiting behind the queue. The non-blocking way is `request_model`, `request_texture`, `request_sky_image`, `request_material` (the material and every texture it uses), `request_texture_pixels` (a texture with its pixels decoded too, for a terrain layer's map: a cooked texture otherwise decodes them only when asked) or `request` (any project file, by its name): each queues the file for the asset workers (every core but two, from 4 to 8 threads) and returns a `LoadTicket` straight away, with `status`, `is_finished` and `wait`. `model_ready` gives a model only if it's already in, and `progress` and `generation` say how far the workers are and whether anything new has arrived. A script's way in is `ContentProvider:PreloadAsync` ([../scripting/api-core.md](../scripting/api-core.md)). Drawing and Animators use `model_slot`, which never waits once `load_textures_in_background` is on (the player and the editor): a model not in yet draws nothing, with no placeholder, and appears on the first frame after it has loaded. A file being read again keeps its last version on screen, and only a model with no file or a bad one is the grey box. Without background loading (tests, tools), `model_slot` reads the file before it returns. Physics still uses `model_blocking`, since a part needs its real collision shape.
- A texture file with a current cooked copy in `.axcenity/imported/textures/` (BC7 mip levels the editor made ahead, roadmap L2) is read from that instead of being decoded, for `texture` and for a model's textures alike; its pixels are decoded from the file only if something asks for them (`Image::rgba`). How copies are made and checked: [../rendering/textures.md](../rendering/textures.md).
- A reference can be a file's asset ID (`ax://…`, maybe with a model's `#pick`) instead of its path: `Assets::resolve` turns it into the path first, and safety, kinds and caching then go by that path ([../editor/assets.md](../editor/assets.md)). An ID no file has is read as a missing file.
- A `MeshId`'s extension says how it's read: `.gltf` and `.glb` are glTF 2.0, `.fbx` is FBX (binary or ASCII, any version). Anything else is refused ("MeshId must name a model file: …").
- `assets::load_model` never crashes on a bad file: errors name the problem ("it isn't a valid glTF file: …", "it isn't a valid FBX file: …", "it uses `x.bin`, which isn't there", "a mesh in it lists a corner that isn't there"), and a panic inside the `gltf` or `ufbx` crate is caught and reported as "the file is damaged".
- FBX textures are looked for inside the model's folder only: at the path the file gives relative to the model, then by file name next to the model, then in a `textures` folder next to it (FBX files often name a texture by where it was on another machine). Embedded textures are used as they are, and importing copies each out (its bytes as they are) to the model's folder as `textures/<its file name>` (`embedded1.png`… if it has none; a number is added if taken), so a model with embedded textures is always imported into a folder of its own (Phase 20). A glTF's embedded images (in a `.glb`, or `data:` URIs) are copied out the same way since Phase 21, named after the image (or `image<N>`), so every map a model uses is a file a SurfaceAppearance can name; a loaded `Image` remembers its file (`Image::file`, relative to the model's folder). PNG, JPEG, TGA and BMP decode; a texture that's missing or in another format (`.psd`, `.dds`) doesn't stop the model loading: it's reported once ("The model `…` is drawn without its texture `wood.psd`: …", `Model::warnings`) and the material's color is used.
- Model files aren't checked for changes while the editor runs; they're read again when the project is opened.
