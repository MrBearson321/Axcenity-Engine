# Collaborate 2.0: persistent projects, Git sync and automatic host handoff

Paul's brief "Axcenity Collaborate 2.0 – Persistent Collaboration & Automatic Host Handoff" (2026-11-12) asks that a Collaborate project stop depending on the computer that started its session: anyone may leave, the session carries on under another host, and the project can be picked up later from a Git remote when nobody is online. This document is phase 0 of that brief: an audit of how host-dependent Collaborate is today, and the design and plan for phases 1–7 (here called **P1–P7**, so they don't clash with C1–C12 of [collaborate.md](collaborate.md)). The decisions are [ADR-0022](../../wiki/Architecture/Architecture-Decisions/ADR-0022-Persistent-Collaborate-Projects-Git-Sync-And-Host-Handoff.md).

- **Status:** P0 (this document) done. P1–P6 built (§8.1–8.6). P7 follows §6.
- **Date:** 2026-11-12
- **Engine:** `main` at `eac9e61` (PR #207)
- **Relies on:** ADR-0020 (one session authority, host-ordered operations, epochs), ADR-0021 (live `yrs` scripts, Tailscale, identity seam), the [development policy](../development-policy.md) (no infrastructure before it's needed, local tests).

## 1. Summary

- **Live state is already replicated; authority is not.** Every member's editor holds the whole session World (as of the last transaction it got), its own unconfirmed edits, a `yrs` copy of every live script it has open, and a folder of the session's files. What only the host has: the *order* (sequence numbers and the journal), the members list, the session's checkpoints, and the network endpoint (its certificate and address are pinned in every invite).
- **So host handoff is mostly a question of who may take the authority and how members find them,** not of copying the project. The plan: the host shares, while it's up, what a successor needs (the members list and each would-be host's address and certificate); when it leaves or vanishes, every member works out the same successor from the same ordered list; the successor starts a host *from its own copy* as a new epoch; the others reconnect to it with the certificate they already know. Everything TC6 built for a restarted host (new epoch → fresh snapshot, unconfirmed edits re-sent with remapped IDs, documents merged by state vector) carries over unchanged.
- **The one gap in the replicated state** is the last few transactions a crashed host broadcast to some members but not to the successor. P4 closes it: each member keeps the transactions of the current epoch it has applied (a bounded tail), and a new host asks the members who are ahead for what it lacks before it opens for edits.
- **Git is persistence, not live sync.** A project may be linked to a Git remote (GitHub first). Only the current session host commits and pushes during a session (its copy is authoritative); outside a session each person's editor syncs their own copy. Commits are automatic checkpoints, batched, never forced; a merge that git can't do cleanly stops and asks.
- **Ownership is separate from hosting.** The Owner is a role in the members list, which every eligible member keeps a copy of. A handoff changes who hosts, never who owns.

## 2. Audit: what depends on the host today

| Responsibility | Where | Host-only today? | Survives the host leaving? |
|---|---|---|---|
| Authoritative World and the order of edits | `collab::Host` (`host.rs`), sequence numbers per epoch | Yes | Members keep their copies and keep editing offline; nothing is ordered until a host returns. A host that *ended* turns copies read-only (`ToClient::Ended`) |
| Journal and crash recovery | `journal.rs` in the host's `.axcenity/teamcreate` | Yes | Only when the *same* host restarts |
| Members, roles, invites | `access.rs`, members file in the host's data folder (`hosted::members_file`) | Yes (never sent to members) | No: another computer can't admit anyone |
| Network endpoint | `socket::Listener` on port 47810 with the host's `HostCert`; invites pin its fingerprint (`access::Invite`) | Yes | No: members only know the one address and certificate |
| Session identity | `hosted::session_id(cert, project path)`; names each member's mirror folder | Derived from the host's certificate and path | A new host would get another ID, so members would start a new folder |
| Files | Host's `FolderStore`; each member's `Mirror` folder | Host holds the bytes of record; members hold copies of everything synced | Yes, the content: every member has the files |
| Live scripts and stylesheets | `live.rs` on the host; each member's `yrs` copy (`client.rs`) | No: CRDT state is on every copy that opened it | Yes: a new host can merge the copies by state vector |
| Presence, chat | `presence.rs`, host memory | Yes | Lost (by design: chat is memory only) |
| Checkpoints and restores (C9) | `history.rs` in the host's `.axcenity/teamcreate/history` | Yes | Only on that computer |
| Tailscale | `tailscale.rs` reads the local client; invites name the host's MagicDNS name | Per computer | Any member with Tailscale can be reached the same way |
| Version History | `project/src/versions.rs`, per computer | Per computer | Yes, but local only |
| Remote history | None | — | — |

**Conclusion:** the project's *content* doesn't depend on the host (every member has it); its *authority* (order, members list, endpoint, journal, checkpoints) does. Nothing is rewritten: P3 makes identity and membership portable, P4 moves the authority, and Git (P1, P2) adds persistence for when nobody is online.

**Live editing stays as it is.** The existing protocol is host-ordered operations plus `yrs` for scripts (ADR-0020, ADR-0021). The brief asked whether that already replicates enough for a host failure: for documents yes (CRDT), for the World almost (§4.3 adds the tail).

## 4. Design

### 4.1 Project identity and the project file (P3)

- **Project ID.** The first session of a project writes `collaborate.json` at the project's root: `{ "project": "<16 hex>", "name": "…", "repository": { "provider": "github", "url": "https://github.com/o/r.git", "branch": "main" } | null }`. Nothing secret: no keys, members or tokens (the repo may be public). It syncs to members like any settings file and is committed with the project, so a fresh clone knows its project ID and remote.
- The ID is the existing `session_id` of the first host (so mirror folders made before this change keep their names), and from then on it's read from the file: every later host, the first one or a successor, hosts under the same ID, and every member keeps one folder per project.
- **Each computer's record** of the projects it collaborates on: `<data folder>/Collaborate/records/<id>.json` (`projects/` already holds the members files): name, the folder, the members list as last received (§4.2), the would-be hosts last known (§4.4), the last epoch and transaction seen (P4), and the session state. This is what "Rejoin" reads when no invite is at hand.

### 4.2 Ownership and membership travel with the session (P3)

- The host sends the members list (public keys, names, colours, roles; never invites' secrets) to every member allowed to host (`ToClient::Members`, on joining and whenever it changes). Keys are public; this is what lets a successor admit people by key with the existing handshake.
- **Ownership** is the Owner role in that list. A successor hosts with the list it received, so the Owner stays Owner, roles stay as they were, and only the Owner can change them, wherever the session is hosted. Invites stay with the host that made them (their secrets aren't copied); a successor makes its own, and only when its own role may invite (the Owner): a session an Editor hosts takes back its members but no new people.
- A member removed while offline but present in an older copy can't sneak back: every copy is stamped with the host's change counter, and a host replaces its list only with a newer one.

### 4.3 What a host keeps so others can take over (P4)

- **Host cards.** On joining, each member who may host sends its card: the address others should use (its Tailscale name if Tailscale is running, else its LAN address) and port, and the fingerprint of its own host certificate (made on first need, as today). The host checks the card is the member's own (signed with the member key as part of the message) and lists them.
- **Successors.** The host keeps an ordered successor list and sends it with every roster change (`ToClient::Successors`). Order (the brief's priority): an explicitly named **backup host** (chosen by the Owner, or by the host when it's the Owner); then the longest-connected eligible member; then the lowest member ID. Eligible: role Editor or Owner, a card, "Let others host from my computer" on in Settings (on by default), and caught up (has applied the host's latest transaction within the last few seconds).
- **Transaction tail.** Each member keeps the transactions of the current epoch it has applied, as they came (`ToClient::Accepted`), up to the last 2,000 or 32 MiB, cleared by a snapshot. That's what a new host needs to rebuild anything a crashed host sent to some members only.

### 4.4 Handoff (P4)

**Graceful** (the host leaves or quits with others connected):

1. The host stops taking new edits (members' edits stay pending on their side, as during any reconnect), finishes writing its journal, and makes a final Git checkpoint and push if a repository is linked (§4.6), with a time limit (10 s) so leaving never hangs.
2. It sends `ToClient::HandingOff { to, last_seq }` to everyone: the successor and the transaction number everyone must reach. Members that are behind still have the earlier `Accepted` in their socket, so they catch up before acting.
3. The successor starts a host from its own copy: its World as of `last_seq`, its mirror folder as the file store, its live documents' `yrs` state, the members list, the project ID, a fresh epoch. It listens on its card's address.
4. Everyone else reconnects to the successor's card with the certificate fingerprint they already have. The existing handshake admits them by key. Their `Hello` names the old epoch, so they get a snapshot and re-send their pending edits with IDs moved into new blocks (TC6), and their documents merge by state vector (C7).
5. The panel says "Paul left. Sam is hosting now." The project's Owner doesn't change.

**Unexpected** (crash, power cut, network or Tailscale down):

1. **Detection.** The socket's silence timer (15 s today, `socket::SILENCE`) is the heartbeat; the client already counts a quiet connection as lost. The election adds a **grace period** (default 20 s, Settings): a reconnect to the old host is tried first, in case it was a short drop.
2. When the grace period ends, each member takes the first reachable successor in the list it last received. Members never vote: they all hold the same list, so they all pick the same one. If the first successor doesn't answer within its own timeout (default 15 s), they move to the next.
3. The successor starts as in step 3 above but in **Recovering** state: it accepts connections but not edits. Each joining member's `Hello` tells it the old epoch's newest transaction it applied. If any member is ahead of the successor, the host asks it for the missing transactions from its tail (`ToClient::SendTail { after }` → `ToHost::Tail(Vec<Accepted>)`), applies them in order (they were already accepted by the old host, so they're replayed, not re-checked against roles), then opens for edits. The wait is bounded (members who haven't reconnected within 10 s are left to catch up later by snapshot); whatever can't be recovered is listed, never guessed: "Transactions 812–815 from Paul's host couldn't be recovered: nobody online had them."
4. **Split brain.** If the old host comes back while a successor is hosting, its own members list says it's no longer the host (it sees a newer epoch from the successor's card when it reconnects as a client). The old host's editor never starts hosting by itself after a crash: it joins the session as a member, and its unsent edits are re-sent like anyone's. Two hosts can still exist if the network splits in two; when they meet again, the project's Git history and the conflict tools (§4.7) are the backstop.
5. **Nobody eligible is left:** members' copies stay editable offline, their edits are kept in the existing recovery file, and the session is **Offline** for them; anyone can start it again later (§4.5).

### 4.5 Sessions without a fixed host (P3)

States, shown in the panel, kept in the project record:

| State | Meaning |
|---|---|
| Offline | No session is running for this project that this computer can see |
| Starting | This computer is starting a session (as first host or successor) |
| Active | Collaborating |
| Handoff | The host is changing |
| Recovering | A new host is rebuilding the latest state before opening for edits |
| Sync Pending | Collaboration is over or paused and changes still have to reach the remote |

- **Everyone leaves:** the last host saves the World into its folder, makes a "[Collaborate] Session ended" checkpoint and pushes (§4.6), and ends the session. Every member's record keeps the project ID, folder, members list and remote.
- **Rejoin** (Collaborate panel or start screen, no invite needed): try the known hosts' cards in order; if one answers, join it (the handshake admits members by key). If none does, pull the remote (if linked) and offer **Start session** from this copy as host, with the members list it has. The original creator never has to approve.
- **A new person** still needs an invite, from a session the Owner hosts (§4.2).
- **Expiry:** project records nobody opened in 90 days are listed as old in the panel; nothing is deleted automatically.

### 4.6 Repository integration and automatic checkpoints (P1, P2)

- **Git through the installed `git`.** Clone, fetch, pull (merge, never rebase of published commits), commit, push (never `--force`), branch and default-branch detection (`git ls-remote --symref`), log, `merge-tree --write-tree` for conflict checks (git 2.38+, checked at start with a plain message if older), `git lfs` when installed. Credentials are passed to each git command through a one-off credential helper reading an environment variable of the child process, so a token never appears on a command line, in `.git/config`, in the remote URL, or in a log line (`git::redact` scrubs output before it's logged).
- **GitHub sign-in:** OAuth device flow (the user opens github.com/login/device and types a code; no web server or redirect). Scope `repo` (the narrowest OAuth scope that covers private repositories; a GitHub App with per-repository permissions is a later option). The OAuth App's client ID is set at build time (`AXCENITY_GITHUB_CLIENT_ID`) or in Settings; official builds carry Axcenity's. Without one, Axcenity uses a signed-in GitHub CLI (`gh auth token`) or a pasted fine-grained token. The token goes into Git's credential store for `https://github.com` (`git credential approve`), which is the OS credential store on a usual Git install (Git Credential Manager on Windows, the Keychain on macOS); so `git` itself, and any other Git tool, can use it. Where Git has no credential helper (a bare Linux install) the token stays in memory for that run and the window says so. Disconnect removes it (`git credential reject`) and links to GitHub's page to revoke the app. If the user's Git is already signed in to GitHub (Git Credential Manager's own browser sign-in), that works as it is.
- **Linking:** connect an existing repository (owner/name or URL; the default branch is read from GitHub), or create one (private by default). An empty remote gets the project pushed; a non-empty one is fetched and, if its history and the folder differ, the folder is **adopted** onto the remote branch without touching the files (`git reset --mixed`), so the first checkpoint shows exactly what differs. Unlinking removes `collaborate.json`'s repository and the git remote, never the files or `.git`. A project inside another repository's work tree (the engine's `examples/`, say) can't be linked: the message says why.
- **`.gitignore` and LFS:** linking writes a `.gitignore` if there's none (`.axcenity/`, `*.tmp`, thumbnails) and, with `git lfs` installed, `.gitattributes` tracking models, textures, audio and video (`*.glb`, `*.fbx`, `*.png`, `*.jpg`, `*.ktx2`, `*.wav`, `*.ogg`, `*.mp3`, …). Without LFS a one-line warning names the largest files.
- **Who commits:** during a session, the host only (members' folders are copies); outside a session, each editor its own project.
- **When:** dirty when the project changed on disk (`git status --porcelain`, checked after saves and every 30 s); a checkpoint at most every 10 minutes while dirty (Settings), and on: a member leaving (`User left session`), the host handing off (`Session handoff`), the session ending, the editor closing, and **Sync now** (`Manual checkpoint`). Messages are `[Collaborate] Automatic checkpoint` etc. with trailers `Axcenity-Checkpoint: auto|left|handoff|ended|manual` and `Axcenity-Participants: Paul, Sam` (from the host's attribution); the commit author is the person whose editor made it. Commits without the trailer are the user's own and are shown as such. Nothing is committed when nothing changed.
- **Integration:** commit → fetch → if the remote moved: `merge-tree` to check; clean → merge (`--no-edit`, message `[Collaborate] Merge remote changes`); conflicts → stop, keep the local commit, state **Conflict** (§4.7) → push → confirm the remote branch is at our commit (`ls-remote`) → **Synced**. A push refused as non-fast-forward goes back to fetch, at most three times.
- **Offline:** any network failure leaves the commits local, the state **Offline** ("Saved on this computer, not uploaded yet"), and retries with backoff (30 s up to 10 min) and at once when the network returns. The chip never says Synced unless the remote's SHA was confirmed.
- **Restore:** a checkpoint restore checks out that commit's tree into the folder and commits it as `[Collaborate] Restore checkpoint "<subject>"` on top: history is never rewritten, and the restore itself can be undone by restoring the checkpoint before it. In a session, the host restores (Owner only), then the files go to everyone through the session as a C9 restore does.

### 4.7 Conflicts and recovery (P5)

| Files | During a session | Between Git copies |
|---|---|---|
| Lua scripts, stylesheets | Live `yrs` merge (C7) | Git's text merge; conflict → both kept |
| World (`world.json`, `levels/`) | Host-ordered operations | `world.json` is one JSON document: merged by git only when the changes touch different lines, otherwise both kept and compared |
| Block scripts, graphs, materials, data tables | Document locks | Git's text merge; conflict → both kept |
| Models, textures, audio (LFS or binary) | Content-addressed, compare-and-swap | Never merged: both kept |
| `project.json`, `input.json`, other settings | Owner-only, compare-and-swap | Git's merge; conflict → both kept |
| `collaborate.json` | Host only | Ours kept for the ID; the remote's repository settings shown |

- **Detect before touching anything:** `git merge-tree --write-tree --name-only` lists conflicting paths without changing the folder. The authors come from `git log -1` on each side.
- **Keep both:** the remote's version of each conflicting file is written beside the local one as `<name>.remote-<short sha>.<ext>` (the `files.rs` conflict-copy naming), the merge isn't made, and sync is paused for those files only. Nothing is overwritten.
- **Resolve** per file: keep mine, keep theirs, keep both (theirs renamed), with a side-by-side text compare for text files and sizes/dates for binary ones. Once every file is decided, the merge commit is made with those choices and sync resumes. Each resolution is appended to `<data folder>/Collaborate/projects/<id>.conflicts.jsonl`.
- **Interrupted sync:** a crash mid-merge leaves `.git/MERGE_HEAD`; on open, sync sees it, aborts the half-made merge (`git merge --abort`, which keeps the local commit) and starts again. A crash mid-commit leaves the index; `git status` decides. Local uncommitted changes are always committed before any fetch, so there's nothing to lose.

### 4.8 Interface (P6)

The Collaborate panel gains a **Project** section above Collaborators: name, Owner, host ("Hosted by Sam" / "No one is hosting"), participants, and a repository line with the sync chip (Synced · Syncing · Pending · Offline · Conflict · Error), last sync time, branch and latest checkpoint; buttons **Sync now**, **History** (Git checkpoints beside C9's session checkpoints), **Manage repository…** (connect, create, disconnect, sign in/out), **Backup host** (Owner: pick a member), **Leave** and **Rejoin**. Words: "checkpoint", "upload", "history", "changes from others"; never "commit", "push", "rebase" outside a Details line. The title bar chip shows the sync state when it isn't Synced.

| Constraint | How |

| Old projects and sessions | No `collaborate.json` → today's session ID; a member on an older build is refused at the handshake as today (protocol bump) |

## 7. Risks

- **Two hosts after a network split.** Election is deterministic but can't see across a split. Mitigated by the epoch check on rejoin and Git conflicts as the backstop; a quorum would need a third party, which the brief rules out.
- **A successor behind a firewall.** On Windows the first listen prompts the firewall (as for any host). The card is only advertised after the member's editor has listened once successfully; until then it isn't eligible.
- **GitHub OAuth App client ID.** Device flow needs a registered OAuth App with device flow enabled. Paul registers it once (Settings → Developer settings → OAuth Apps → "Enable Device Flow") and sets the ID; until then the `gh` and token routes work.
- **Large worlds in Git.** `world.json` is text and diffs well; a 10,000-part world is a few MB. Binary assets go through LFS when installed.
- **Commits by a successor who isn't signed in to GitHub.** Its checkpoints stay local (Sync Pending) and upload when that person signs in, or when a later host who is signed in takes over; the panel says so.

## 8. Built

### 8.1 P1: repository integration

- **`crates/repo`** (no engine dependency, no new third-party crate): `git.rs` runs the installed `git` through `Runner` (background-safe: no terminal or window prompts, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, no console window on Windows, a timeout). A token goes only to commands that reach the remote, through a one-off credential helper reading `AXCENITY_GIT_TOKEN` from that child's environment; every error is scrubbed (`secret::redact`). Pushes are `HEAD:refs/heads/<branch>`, never forced; a rejected push comes back as `Pushed::Behind`. `merge_check` uses `git merge-tree --write-tree` (git 2.38+, `Git::is_recent_enough`).
- **GitHub** (`github.rs`): device flow (`start_sign_in`, `poll_sign_in` with pending, slow-down, denied and expired), `user`, `repository` (default branch, push permission), `create_repository` (private by default, empty), reference parsing (`owner/name`, HTTPS, SSH forms). The OAuth App's client ID comes from `AXCENITY_GITHUB_CLIENT_ID` (running or at build time); without one the editor offers `gh auth token` (`credentials::github_cli_token`) or a pasted token, both checked with `/user` before they're kept.
- **Credentials** (`credentials.rs`): `git credential approve/fill/reject` for `https://github.com`, so the token lands in whatever store Git uses (Git Credential Manager, Keychain, libsecret); `Stored::MemoryOnly` when Git has no helper.
- **Linking** (`repository.rs`, `manager.rs`): as §4.6, plus: a remote with commits and a folder with no history is *adopted* and its differences listed; nothing is uploaded until the person picks **Upload my version** (`upload_my_version`: a checkpoint on top of the remote's) or **Use the repository's version** (`take_remote_version`: the folder's own files go into a Git stash first). A folder whose history is unrelated to the remote's is refused, and the remote is put back as it was. An existing `origin` naming another URL is kept unless replacing is chosen. Unlinking removes the remote only.
- **`collaborate.json`** (`crates/project/src/collaborate_file.rs`): project ID, name, repository (provider, URL, branch); refuses to write a URL with credentials in it; removed when empty.
- **Tests** (37): `repo`'s run the real `git` against bare `file://` remotes with the machine's Git settings shut out (`testing::ConfigRunner`): first upload, adoption with and without differences, both choices after adopting, the remote's default branch, a project inside another repository, another remote kept, unrelated history refused, an unreachable remote changing nothing, unlink and relink, LFS attributes; GitHub over a fake `Http` (device flow states, repository lookup and creation, 401, offline); the token never in arguments, errors or the project folder; credentials round-tripping through a helper and memory-only without one. `project`'s `collaborate_file` tests.

### 8.2 P2: automatic sync and checkpoints

- **`repo::sync`**: `sync_once` is one pass (§4.6): a half-made merge left by a crash is aborted first (`recover_interrupted`; a stale `index.lock` older than two minutes too); what changed is checkpointed (no empty commits); fetch; when the remote moved, `merge-tree` decides: clean → merge (fast-forward when possible, else `[Collaborate] Merge remote changes`), conflicts → `State::Conflict(files)` with the local checkpoint kept and nothing in the folder touched; push (never forced; a lost race fetches again, three tries); then **Synced only when `ls-remote` shows the remote's branch at our commit**. No network → `Offline` with the checkpoint kept locally. `Schedule` decides when (changes batched for the interval, 10 minutes by default; leaving, handoff, session end, closing and Sync now at once and ahead of the timer; failures retried after 30 s, doubling to 10 minutes; the network coming back retries at once; a conflict waits until someone asks again). `Worker` runs passes on the `collaborate-sync` thread.
- **`repo::checkpoint`**: kinds (auto, left, handoff, ended, closing, manual, restore, merge) with the brief's subjects and the `Axcenity-Checkpoint` / `Axcenity-Participants` trailers; `history` tells checkpoints from people's own commits; `restore` checkpoints outstanding changes ("Before restoring"), puts the old tree back with `git read-tree --reset -u` (files added since go; ignored per-computer files stay) and commits it as `[Collaborate] Restored checkpoint: "…"` on top, so a restore is itself restorable.
- **Editor** (`crates/editor/src/app/collab_repo.rs`): a project is linked when `collaborate.json` names a repository (read again every 5 s). The computer that commits is the one not in a session, or the host; a member never commits. A save marks the project changed (`repo_changed` in `save`); `repo_checkpoint(kind)` asks now (the Console's `checkpoint [label]` is Sync now until P6's panel has a button); closing the editor runs a last `Closing` (or `Ended` in a session) pass and waits up to 10 s. While hosting, the session's World is written to `world.json` before a checkpoint. What a pass brings in from the remote is read again by the file watcher. The commit author is the Collaborate name with the person's own `user.email` if set.
- **Tests:** `repo::sync` (checkpoint, upload and confirm; no empty checkpoints; someone else's upload merged in, both directions; a conflict keeps both and leaves the remote's; offline keeps the checkpoint then uploads when the remote is back; a half-made merge undone; the schedule's batching, priorities, backoff and conflict wait; the worker), `repo::checkpoint` (messages and trailers, history, restore and restoring it back), and the editor's `collab_repo_tests` (saves become checkpoints on the remote; Sync now; a project without a repository never runs `git`; closing uploads).

### 8.3 P3: projects that outlive their sessions

- **`collab::project`**: `project_id` (from `collaborate.json`, else the first host's old session ID; only `0-9a-z`, as it names folders), `MembersList` (members, the next member number, and a `version` the host's `Access` bumps on every change of who's a member or their role, name or colour; older members files read as version 0), `SessionState` and its `Event`s (§4.5), `HostCard` and `ProjectRecord` (`records/<id>.json` in the Collaborate data folder, written owner-only; `all` lists them newest first, `is_old` after 90 days).
- **The list travels:** `HostSession` sends `ToClient::Members` (wire format 8, its own `WireMembers` shape for postcard) to each member whose role `may_host` (Editor, Owner) when they join and to everyone who may host whenever the version changes; a Viewer never gets it. `Client::members_list` keeps the newest. `Access::from_list` starts a host from a list; `take_list` brings a members file up to date with a newer one.
- **Editor** (`crates/editor/src/app/collab_project.rs`): hosting reads or writes the project ID into `collaborate.json` before the files are read (so it syncs) and hosts under it, so members' folders are `Projects/<id>` whoever hosts. The host starts from its members file, updated by a newer list in its record, else the record's list (a member's copy), else the Owner alone; someone not in the list can't host. Hosting with an invite needs the Owner; `host_for_members` (Console `host`) hosts for the members only. Host and members write their record (folder, members, host card first, state); leaving marks it Offline, or Sync Pending while checkpoints wait to upload. `rejoin_project` (Console `rejoin <name>`, `projects` lists them) joins the record's host by key with no invite, and refuses if this computer's key isn't in the list. `collab-server` hosts under the same ID.
- **Tests:** `collab`: the list version and `from_list`/`take_list` (`access`), records and states (`project`), the wire round trip (`wire_fuzz_tests`), and over real sockets that the Owner and an Editor keep the list, a Viewer never gets it, and a role change reaches everyone (`net_tests`). Editor `collab_project_tests`: the ID is written and used, Sam's computer records the project, leaves, **rejoins without an invite**, edits; Paul ends; Sam's copy may not invite but **hosts for the members** under the same ID, and **Paul rejoins Sam's session as Owner** and gets Sam's part; someone removed can neither rejoin nor host.
- **Not yet:** trying every host a record knows in turn when rejoining from a closed editor, the epoch and transaction last seen in the record. (Successors and handoff in a running session: §8.4.)

### 8.4 P4: host election and handoff

- **`collab::election`**: `rank` orders the successors (the backup host the Owner named, then the longest connected, then the lowest member number; connected Editors and the Owner with a card only, never the member whose editor hosts; at most 8). `after_loss(lost_for, timing, successors, me)` is what every member computes from the same list: within the grace period (20 s) wait for the old host; then successor `n` has its turn from `grace + n × 15 s`; once it's mine I host and stay hosting; past the end of the list, `Alone`.
- **Host** (`collab/src/host/handoff.rs`): `ToHost::HostCard { address, cert }` (from members who may host, budget 5 then one every 5 s) fills the member's card; the list goes to everyone whenever it or the next Instance ID changes (`ToClient::Successors { hosts, next_id }`), and to each joiner. "Connected longest" counts new connections only, so a resync doesn't move a member down. `hand_off` writes live documents' typing to the files, records it in the audit log ("New host"), sends `HandingOff { to, last_seq }` and from then drops new edits (members keep them pending and send them to the new host). `recover_from(old_epoch, have, wait)` starts a host from a lost one: it skips 64 ID blocks (the old host may have handed some out after its last list), asks each member whose `Hello` shows it ahead in the old epoch for its tail (`SendTail { after }` → `Tail(entries)`), replays the entries that continue its own count without checking them again (the old host accepted them), and holds everyone's new edits until every member asked has answered or the wait is over (10 s); what nobody online had is in the audit log and `unrecovered()`. `HostSession::set_backup` names the backup host (P6 adds the picker). Wire format 9.
- **Client**: keeps the last 2,000 accepted transactions of the current epoch (`TAIL_KEPT`; an answer to `SendTail` holds at most 16 MiB of them, oldest first, so it fits the host's message limit, and `Tail` has a budget of 3 then one every 10 s), moved aside when a new epoch's Welcome arrives so it can answer `SendTail`; `confirmed()` is the World, graveyard and files as the host confirmed them, without this editor's own pending edits (they're sent again to the new host like anyone's).
- **Editor** (`crates/editor/src/app/collab_handoff.rs`): once joined, a member who may host sends its card (its Tailscale name, else its LAN address, on port 47810, with its host certificate's fingerprint; members and keys stay in the Collaborate data folder). **Leave** and quitting while hosting hand the session to the first successor when there is one (a saved host ends its journal cleanly; unsaved, the journal stays until a save, as before); **End for everyone** in the panel ends it as before. A member told it's next hosts once it has every transaction up to `last_seq`; the others reconnect to its card by key. When the host goes quiet (the socket's silence timer), members follow `after_loss`; the successor hosts from `confirmed()`, its mirror folder as the file store, the members list it was sent, the project ID and the old host's next ID, on its card's port, and records the project as hosted by it. A successor that can't host (no folder, the port taken) turns its card off so the next one has its turn.
- **Differences from §4.3–4.4:** the card isn't signed separately: it comes over the member's own authenticated connection. "Caught up" isn't a condition for being listed: a successor that's behind gets what it missed from the others' tails. Live documents restart from the files on the new host (the old host wrote its typing back when it left; after a loss, typing not yet written back is in members' own tabs and merges back by state vector when they reopen them). The old host coming back after a crash doesn't look for a successor yet: it opens with its journal as before (TC6), and its owner can rejoin from **projects**.
- **Tests:** `election` (the order; everyone picks the same successor and moves on when it doesn't come up), `collab` `handoff_tests` (the list's order and who's on it; scenario A: the host leaves with an edit on its way and the successor's own pending edit, and both land at the new host; scenario B: the host is lost after some members got its last transactions, and the new host recovers them from a member's tail before taking the held edits), `security_tests` (both new messages from a Viewer and a removed member). Editor `collab_handoff_tests`: three editors over real sockets on 127.0.0.1; **Paul leaves**, Sam hosts, Kim's edit made during the handoff and Sam's after it reach everyone, Kim stays an Editor; **Paul's host stops without a word**, after the grace period Sam hosts from his copy and Kim's edit made while the host was gone reaches him.
- **Hand checks for Paul:** two or three computers on Tailscale or one LAN: host, have the others join, then (1) **Leave** on the host: the others should say who hosts now within a second or two and keep editing; (2) pull the host's network cable (or close its lid): after about 20 s plus the reconnect the first successor should say it's hosting, and everyone's edits made meanwhile should be there; (3) **End for everyone** still ends it for all. A firewall must let the successor listen on port 47810.

### 8.5 P5: conflicts and recovery

- **`repo::conflicts`**: when a sync pass finds conflicts (`git merge-tree`, nothing touched), `keep_copies` writes the repository's version of each file beside this one as `<stem>.remote-<commit>.<ext>` (`scripts/Door.server.remote-1a2b3c4.lua`, `world.remote-1a2b3c4.json`; no loader takes it for a script), checked out from a temporary index so line endings and LFS come out as they would in a checkout, and lists the copies in the repository's own `info/exclude` so no checkpoint uploads them. A file the repository deleted gets no copy. `list` says, per file, who last changed it on each side and when, its size or that it's gone, and whether it's text (not LFS, and `git diff --numstat` counts lines). `resolve` takes a choice for **every** conflicting file (keep mine, keep theirs, keep both: mine at the path, theirs committed as the copy), checkpoints anything changed since first, makes the merge with those choices as one checkpoint (`[Collaborate] Merge remote changes: conflicts resolved`, with a line per file, "Kept mine: a.txt"…), removes the other copies, and appends each choice to `<repository's Git folder>/axcenity/conflicts.jsonl` (`history`). A missing choice changes nothing. If anything fails partway, the merge is undone and the copies are written again. Mine stays in the history whatever is chosen: the local checkpoint is one of the merge's parents.
- **Interrupted:** a resolve the editor never finished leaves a half-made merge; the next pass undoes it (`recover_interrupted`, as in P2), the conflicts and their copies come back, and nothing is lost.
- **Editor** (`crates/editor/src/app/collab_conflicts.rs`): the warning says the repository's versions are beside each file; the Console's `conflicts` lists them with both sides, `resolve mine|theirs|both [file]` chooses (every file without one), and once every file has a choice the merge is made and uploaded at once (`Schedule::resolved`). Only where this computer commits (no session, or hosting) and never while a pass runs. P6's panel puts a Resolve window with a side-by-side compare on the same calls.
- **Differences from §4.7:** the record of resolutions is kept in the repository's own Git folder rather than the Collaborate data folder, so it sits with the history it describes, needs no project ID and is never uploaded; the merge checkpoint carries the same choices for everyone. Sync is paused for the whole project while files are in conflict (as P2), not per file; edits made meanwhile are kept and checkpointed by the resolve.
- **Tests:** `repo` `conflicts_tests` (copy names; a conflict writes theirs beside mine and never uploads it; four files resolved as mine, theirs, both and a deletion, with an edit made meanwhile kept, the checkpoint's lines, the record, and the upload reaching the other copy; a binary file kept both ways byte for byte; an unfinished resolve undone and asked again), and the editor's `collab_repo_tests::a_file_changed_on_both_sides_keeps_both_until_someone_chooses` (Sam uploads first; the Console lists two conflicts, one choice waits for the other, the merge uploads with Sam's script as the copy). The test helpers' temp folders now live under one `axcenity-repo-<process>` folder, and runs that ended are swept.
- **Hand checks for Paul:** link a project, change the same script on two computers while both are outside a session, sync both: the second should report a conflict with `Name.remote-xxxxxxx.lua` beside the script; `resolve both` keeps both and uploads.

### 8.6 P6: interface

- **Collaborate panel, Project section** (`crates/editor/src/app/collab_repo_ui.rs`, drawn above the rest of the panel in and out of a session): the project's name and Owner; who hosts ("Hosted by this editor", the host's address, or "No one is hosting" with who hosted last); **Rejoin** when this computer's record knows a host; while hosting, who hosts next if this editor leaves, and for the Owner a **Backup host** picker (`HostSession::set_backup`; "Usual order" clears it); for a member who may host, **Let others host from my computer** (also in Settings > Collaborate > Hosting, kept between runs; turning it off withdraws this computer's card at once: an empty `HostCard` takes it off the successor list).
- **Repository**: the sync chip (Synced, Syncing, Pending, Offline, Conflict, Error, each with its icon and colour), the sentence that explains it, the branch (the URL on hover), the last upload, and **Sync now**, **History…**, **Resolve…** (while in conflict) and **Manage…**; without a repository, **Connect a repository…**. In a session only the host's computer syncs, and the section says so.
- **Project Repository window**: GitHub's sign-in (the device code to type at github.com/login/device when this build has an OAuth client ID, else the GitHub CLI's token or a pasted one, each checked before it's kept in Git's credential store); connect an existing GitHub repository, create a new one (private by default), or any other Git host by URL and branch; when the repository already had files, nothing uploads until **Upload my version** or **Use the repository's version** (this project's files go to Git's stash first); **Disconnect…** with a confirmation (the files and history stay). Network calls run on a `collaborate-repository` thread; the frame polls.
- **Project History window**: checkpoints newest first (Axcenity's and people's own commits), with who and when; **Restore…** with a confirmation, outside a session and with everything saved (the session's own History covers a session); a restore is a new checkpoint, uploaded at once, and the project is opened again from its files.
- **Resolve Conflicts window**: each file's two sides (who, when, size, or deleted), Keep mine / Keep theirs / Keep both, **Compare** side by side for text (the first 256 KiB), and **Resolve and upload** once every file is chosen (`choose_resolution`, as the Console's `resolve`).
- **Title bar**: a sync chip beside the session chip whenever the project's repository isn't Synced; it opens the Collaborate panel.
- **Panel buttons while hosting:** **Leave session** hands the session on (P4); **End for everyone** ends it.
- **Tests** (editor `collab_repo_tests`): the section draws the repository's state and buttons, History lists the first checkpoint with Restore, Manage shows "Not signed in" and Disconnect for a linked project; a project without a repository offers to connect one, and the hosting offer is kept in the settings text; the Resolve window lists a conflict, counts the choices and merges with them until Synced. `collab` `handoff_tests`: a withdrawn card takes a member off the list.
